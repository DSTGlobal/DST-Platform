# 8. Компонентная система

Этот документ описывает компонентную архитектуру DST Platform — основной механизм модульности, инкапсуляции и расширяемости. Компонент представляет собой автономный функциональный модуль (например, `shop`, `users`, `forum`), объединяющий контроллер, модель, шаблоны и события в единое целое.

Связанные разделы:
- **«Паттерн MVC и жизненный цикл запроса»** — обработка запросов внутри компонента
- **«Система событий и обработчики»** — межкомпонентное взаимодействие
- **«Создание компонентов»** — руководство по разработке новых модулей

---

## 8.1. Архитектурные принципы

Компонент — это **самодостаточная единица функциональности**, которая может включать любую комбинацию следующих элементов:

| Элемент | Обязательный | Назначение |
|--------|--------------|------------|
| Фронтенд-контроллер | Нет | Обработка публичных HTTP-запросов |
| Бэкенд-контроллер | Нет | Административный интерфейс |
| Модель | Нет | Доступ к данным и бизнес-логика |
| Виджеты | Нет | Переиспользуемые UI-блоки |
| Обработчики событий | Нет | Реакция на действия других компонентов |

Такая гибкость позволяет создавать:
- **Полнофункциональные модули** (например, `shop`)
- **Сервисные компоненты** (например, `api` — только модель + контроллер, без шаблонов)
- **Компоненты-слушатели** (например, `notifications` — только `hooks.php`)

В отличие от традиционных MVC-фреймворков, платформа DST позволяет компонентам существовать с любым сочетанием этих элементов. Такая гибкость позволяет создавать специализированные компоненты, такие как:

- Сервисные компоненты: Компоненты, использующие только модель и предоставляющие API для доступа к данным.
- Компоненты обработчика событий: контроллеры, которые реагируют только на системные обработчики.
- Компоненты для презентаций: компоненты, предназначенные только для внешнего интерфейса, для статического или вычисляемого контента.

## 8.2. Именование и расположение 

### Правила именования компонентов
- Только строчные латинские буквы, цифры и символ подчёркивания (`_`)
- Должно начинаться с буквы
- Минимум 3 символа
- Уникально в рамках приложения

✅ Допустимые: `shop`, `user_auth`, `geo`  
❌ Недопустимые: `Shop`, `user-auth`, `2fa`, `my`

### Расположение
Все компоненты размещаются в:
```
/system/controllers/{component_name}/
```

Пример:
```
/system/controllers/shop/
/system/controllers/users/
/system/controllers/my_component/
```

### Структура каталогов

Компоненты расположены исключительно в каталоге `<каталог>` /system/controllers/. Имя каталога напрямую соответствует имени компонента:

```
/system/controllers/
├── shop/                    # E-commerce component
├── users/                   # User management
├── content/                 # Universal content manager
├── partner/                 # Vendor dashboard
├── api/                     # REST API
└── my_component/            # Custom component
```

## 8.3. Автозагрузка и соглашения об именовании классов

DST Platform использует **соглашение вместо конфигурации**: имя класса однозначно определяет путь к файлу.

### Правила автозагрузки

<img src="https://github.com/DSTGlobal/DST-Platform/blob/main/images/50.png" alt="DST Platform">

### Сопоставление префиксов

| Префикс | Путь шаблона | Пример |
|--------|---------------|--------|
| `cms` | `/system/core/{name}.php` | `cmsCore` → `core.php` |
| `field` | `/system/fields/{name}.php` | `fieldDate` → `date.php` |
| `model` | `/system/controllers/{component}/model.php` | `modelUsers` → `users/model.php` |
| `modelBackend` | `/system/controllers/{component}/backend/model.php` | `modelBackendShop` → `shop/backend/model.php` |
| *(без префикса)* | `/system/controllers/{component}/frontend.php` | `shop` → `shop/frontend.php` |

### Именование контроллеров

- **Фронтенд**: `class {component} extends cmsFrontend`  
  Файл: `/system/controllers/{component}/frontend.php`

- **Бэкенд**: `class backend{Component} extends cmsBackend`  
  Файл: `/system/controllers/{component}/backend/controller.php`

> **Примечание**: `{Component}` — имя компонента в PascalCase, даже если каталог в нижнем регистре.  
> Пример: компонент `my_shop` → класс `myShop`.

В контроллерах внешнего интерфейса имя компонента используется в качестве имени класса без префикса:

```
// File: /system/controllers/shop/frontend.php
class shop extends cmsFrontend {
    // Controller implementation
}
```

Именование бэкенд-контроллеров

Контроллеры бэкэнда расположены в backend/подкаталоге и используют имя компонента в качестве имени класса:

```
// File: /system/controllers/shop/backend/controller.php
class shop extends cmsBackend {
    // Backend controller implementation
}
```

## 8.4. Жизненный цикл компонентов и инициализация

Процесс начальной загрузки

<img src="https://github.com/DSTGlobal/DST-Platform/blob/main/images/51.png" alt="DST Platform">

Механизм загрузки компонентов

Компоненты загружаются по запросу, cmsCore когда на них перенаправляется URL-адрес. Основной сервисный локатор управляет созданием экземпляров компонентов.

Компоненты загружаются **лениво**, по запросу:

1. Анализ URI: `/shop/item/123` → компонент = `shop`
2. Автозагрузка: `shop` → `/system/controllers/shop/frontend.php`
3. Создание экземпляра: `$controller = new shop($request)`
4. Вызов действия: `$controller->actionItem(123)`
5. (Опционально) Загрузка модели: `$this->model` или `$this->loadModel('users')`

Модели также создаются лениво и кэшируются в рамках запроса.

## 8.5. Уровень контроллера

### Фронтенд-контроллеры

Фронтенд-контроллеры обрабатывают запросы, поступающие от внешних пользователей, и наследуют от cmsFrontend:

<img src="https://github.com/DSTGlobal/DST-Platform/blob/main/images/52.png" alt="DST Platform">

Местоположение файла: /system/controllers/{component}/frontend.php

### Фронтенд-контроллер
```php
// /system/controllers/shop/frontend.php
class shop extends cmsFrontend {

    public function actionIndex() {
        $items = $this->model->getPublishedItems();
        return $this->render('index', ['items' => $items]);
    }

    public function actionItem($id) {
        $item = $this->model->getItemById($id);
        return $this->render('item_view', ['item' => $item]);
    }
}
```

Доступные свойства:
- `$this->db` — подключение к БД
- `$this->model` — модель текущего компонента
- `$this->user` — данные пользователя
- `$this->cache` — кэш

### Бэкенд-контроллер

```php
// /system/controllers/shop/backend/controller.php
class backendShop extends cmsBackend {

    public function actionIndex() {
        // Админка: список товаров
    }
}
```

Особенности:
- Автоматическая проверка прав администратора
- Генерация CRUD-интерфейсов
- Интеграция с административным меню

<img src="https://github.com/DSTGlobal/DST-Platform/blob/main/images/53.png" alt="DST Platform">

## 8.6. Слой модели

В DST Platform модели не являются сущностями ORM, а представляют собой вспомогательные классы, предоставляющие методы доступа к данным. Каждая модель наследует от cmsModelкомпонента и соответствует ему.

### Модель архитектуры

<img src="https://github.com/DSTGlobal/DST-Platform/blob/main/images/54.png" alt="DST Platform">

Местоположение файла: /system/controllers/{component}/model.php

Модели — это **сервисные классы**, а не объекты сущностей. Они предоставляют методы для работы с данными.

### Базовая структура
```php
// /system/controllers/shop/model.php
class modelShop extends cmsModel {

    protected $default_table = 'shop_products';

    public function getPublishedItems($limit = 20) {
        return $this->select('*')
                    ->filterEqual('is_published', 1)
                    ->orderBy('date_pub', 'DESC')
                    ->limit($limit)
                    ->getItems();
    }
}
```

### Query Builder: ключевые методы

| Метод | Пример | SQL-аналог |
|-------|--------|------------|
| `select($table, $fields)` | `->select('shop_products')` | `SELECT * FROM shop_products` |
| `filterEqual($field, $value)` | `->filterEqual('category_id', 5)` | `WHERE category_id = 5` |
| `filterLike($field, $pattern)` | `->filterLike('title', '%phone%')` | `WHERE title LIKE '%phone%'` |
| `orderBy($field, $dir)` | `->orderBy('date_pub', 'DESC')` | `ORDER BY date_pub DESC` |
| `limit($n)` | `->limit(20)` | `LIMIT 20` |
| `getItem()` / `getItems()` | `->getItem()` | `fetch()` / `fetchAll()` |

### Модели бэкенда

Расширяют фронтенд-модель:
```php
// /system/controllers/shop/backend/model.php
class modelBackendShop extends modelShop {

    public function getStatistics() {
        // Аналитика: продажи, просмотры и т.д.
    }
}
```

## 8.7. Шаблоны

Шаблоны физически отделены от логики компонентов и находятся в каталоге темы. Такое разделение позволяет осуществлять наследование шаблонов и переключение тем без изменения кода.

### Разрешение шаблонного файла

<img src="https://github.com/DSTGlobal/DST-Platform/blob/main/images/55.png" alt="DST Platform">

### Структура каталогов шаблонов

```
/templates/{theme}/controllers/{component}/
├── *.tpl.php              # View templates
├── styles.css             # Component-specific styles
├── scripts.js             # Component-specific scripts
├── backend/               # Admin templates
│   ├── *.tpl.php
│   └── forms/
│       └── *.tpl.php
└── widgets/               # Widget templates
    └── {widget_name}.tpl.php
```
	
### Именование файлов шаблонов

Файлы шаблонов должны соответствовать .tpl.php соглашениям об использовании расширений. Распространенные шаблоны именования:

| Назначение шаблона | Имя файла | Создано действием контроллера |
|--------------------|-----------|-------------------------------|
| **Вид по умолчанию** | `index.tpl.php` | `index()` |
| **Список элементов** | `list.tpl.php` или `{type}_list.tpl.php` | `list()` |
| **Детали товара** | `item.tpl.php` или `item_view.tpl.php` | `item()` |
| **Форма редактирования** | `form.tpl.php` или `item_edit.tpl.php` | `edit()` |
| **Частичное представление** | `_{partial}.tpl.php` | Включено в другие шаблоны |

### Организация по управлению

Компонентные ресурсы размещаются совместно с шаблонами:

CSS-файлы: /templates/{theme}/controllers/{component}/styles.css

- Загружается автоматически при активации компонента (при условии его надлежащей регистрации).
- Можно добавить вручную через$this->addControllerCSS('styles.css', 'component_name')

Файлы JavaScript: /templates/{theme}/controllers/{component}/scripts.js

- Включено вручную через$this->addControllerJS('scripts.js', 'component_name')

Шаблоны физически отделены от логики и находятся в каталоге темы:

```
/templates/{theme}/controllers/{component}/{template}.tpl.php
```

### Приоритет загрузки

1. Текущая тема: `/templates/custom/...`
2. Родительская тема: `/templates/default/...`
3. Компонент по умолчанию: `/system/controllers/{component}/templates/...`

### Соглашения об именовании

| Назначение | Имя файла |
|-----------|-----------|
| Главная страница | `index.tpl.php` |
| Список | `list.tpl.php` |
| Детальная страница | `item_view.tpl.php` |
| Форма редактирования | `form_edit.tpl.php` |
| Частичный шаблон | `_partial.tpl.php` |

### Пример шаблона

```php
<?php
// /templates/default/controllers/shop/item_view.tpl.php
$this->addCSS('controllers/shop/item.css');
$this->addJS('controllers/shop/item.js');
?>
<div class="product-detail">
    <h1><?= $item['title'] ?></h1>
    <div class="price"><?= $item['price'] ?> руб.</div>
</div>
```

Переменные (`$item`) передаются из контроллера через `render()`.  
`$this` — экземпляр `cmsTemplate`.

## 8.8. Примеры компонентов с DST Platform

### Пример 1: Компонент полного стека (маркетплейс)

Данный shop компонент демонстрирует полную реализацию компонента:

```
/system/controllers/shop/
├── frontend.php           # class shop extends cmsFrontend
├── model.php              # class modelShop extends cmsModel
├── hooks.php              # Event handlers
├── options.form.php       # Configuration form
├── backend/
│   ├── controller.php     # class shop extends cmsBackend
│   └── model.php          # class modelBackendShop extends modelShop
└── widgets/
    ├── products.php       # Featured products widget
    └── cart.php           # Mini cart widget

/templates/default/controllers/shop/
├── index.tpl.php          # Shop homepage
├── category_list.tpl.php  # Product listing
├── item_view.tpl.php      # Product detail page
├── cart.tpl.php           # Shopping cart
├── styles.css             # Shop-specific styles
├── backend/
│   ├── index.tpl.php      # Admin dashboard
│   └── products.tpl.php   # Product management
└── widgets/
    ├── products.tpl.php   # Product widget template
    └── cart.tpl.php       # Cart widget template
```
	
Основные характеристики:

- Полная реализация MVC
- Отдельная серверная часть с расширенной моделью
- Несколько виджетов для многократного использования блоков
- Расширенные возможности шаблонизации для различных представлений.

### Пример 2: Сервисный компонент (API)

Этот api компонент предоставляет RESTfull - интерфейсы без традиционных представлений:

/system/controllers/api/
├── frontend.php           # class api extends cmsFrontend
└── model.php              # class modelApi extends cmsModel

/templates/default/controllers/api/
└── (minimal or no templates, returns JSON)

Основные характеристики:

- Методы контроллера возвращают JSON через$this->json($data)
- Модель обеспечивает преобразование данных для ответов API.
- Отсутствует традиционный рендеринг шаблонов.

### Пример 3: Компонент, управляемый событиями

Некоторые компоненты существуют в первую очередь для обработки событий от других компонентов:

/system/controllers/notifications/
├── frontend.php           # User-facing notification center
├── model.php              # Notification storage and delivery
└── hooks.php              # Listen to user_login, content_published, etc.

Файл hooks.phpсодержит обработчики событий:

```
public function hookUserLogin($user) {
    // Send welcome notification
}

public function hookContentPublished($content) {
    // Notify subscribers
}
```

## 8.9. Модули

Модули (виджеты) — это переиспользуемые UI-блоки, привязанные к компоненту.

### Структура

```
/system/controllers/{component}/widgets/{widget_name}.php
/templates/{theme}/controllers/{component}/widgets/{widget_name}.tpl.php
```

### Пример виджета

```php
// /system/controllers/shop/widgets/products.php
class products extends cmsWidget {

    public function run() {
        $model = cmsCore::getModel('shop');
        $products = $model->getPublishedItems($this->getOption('limit', 5));
        return ['products' => $products];
    }
}
```

Вызов в шаблоне:
```php
<?= $this->renderWidget('shop.products', ['limit' => 3]) ?>
```

## 8.10. Взаимодействие компонентов

Компоненты **не вызывают друг друга напрямую**. Вместо этого используется система событий.

### Обработчики событий
Файл: `/system/controllers/{component}/hooks.php`

```php
class notifications {

    public function hookUserLogin($user) {
        // Отправить уведомление о входе
    }

    public function hookContentPublished($content) {
        // Уведомить подписчиков
        return $content; // обязательно вернуть данные
    }
}
```

### Вызов события
```php
// В любом месте кода
cmsEventsManager::hook('user_login', $user);
```

События автоматически доставляются всем компонентам, имеющим соответствующий метод.

## 8.11. Конфигурация компонентов

### Регистрация в БД

Компоненты, имеющие бэкенд, регистрируются в таблице `controllers`:

| Поле | Назначение |
|------|------------|
| `name` | Идентификатор (`shop`) |
| `title` | Отображаемое имя (`Интернет-магазин`) |
| `is_enabled` | Включён/выключен |
| `options` | JSON с настройками |

### Форма настроек

Файл: `/system/controllers/{component}/options.form.php`

Возвращает объект `cmsForm`, определяющий поля конфигурации (чекбоксы, текстовые поля, выпадающие списки).  
Настройки сохраняются в поле `options`.

## 8.12. Примеры компонентов

### 1. Полнофункциональный компонент (`shop`)
- Фронтенд + бэкенд
- Модель + модель бэкенда
- Шаблоны для всех сценариев
- Виджеты (корзина, рекомендации)
- Обработчики событий

### 2. Сервисный компонент (`api`)
- Только контроллер и модель
- Возвращает JSON: `return $this->json($data);`
- Без шаблонов

### 3. Компонент-слушатель (`fraud_detection`)
- Только `hooks.php`
- Реагирует на события: `order_created`, `payment_success`
- Не имеет собственных URL

| Элемент | Обязательный | Путь | Класс | Назначение |

| Шаблоны | Нет | `/templates/{theme}/controllers/{component}/*.tpl.php` | — | Представление |

## 8.14. Заключение

Компонентная система DST Platform обеспечивает:
- **Модульность**: каждая функция — независимый модуль
- **Инкапсуляцию**: логика, данные и представление объединены
- **Расширяемость**: через события и наследование
- **Гибкость**: от простых слушателей до полноценных приложений

Эта архитектура позволяет эффективно разрабатывать, тестировать и поддерживать как типовые CMS-сценарии, так и сложные enterprise-решения.
