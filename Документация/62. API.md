# Часть I. Введение и обзор

## 62.1. Назначение и область применения

Компонент `api` реализует лёгкий REST-интерфейс между DST Platform и внешними потребителями: мобильными приложениями, сторонними сайтами, сервисами синхронизации (1С, CRM), микросервисами и внутренними фоновыми задачами.

API **не дублирует** бизнес-логику компонентов, а выступает тонким адаптером: он принимает HTTP-запрос, валидирует его, вызывает действие (action) соответствующего компонента и формирует JSON-ответ. Это следует принципам, заложенным в архитектуре платформы (см. раздел *«Базовая архитектура»*): компонент владеет своей логикой, API — лишь точка входа.

| Характеристика | Реализация |
|---|---|
| Формат ответа | **Только JSON** (UTF-8, RFC 8259) |
| Протокол | HTTP/1.1 и HTTP/2, только через HTTPS в продакшене |
| Методы | GET, POST (для операций чтения и записи соответственно) |
| Точки входа | `/api/method/{METHOD_NAME}` и `/api/execute` |
| Аутентификация | API-ключ (`api_key`), опционально — подпись (`sig`), IP-фильтр, CSRF |
| Логирование | Встроенное, с фильтрацией по методу, ключу, IP, коду ошибки |

> ⚠️ **Только JSON.** Даже при ошибке 404 или 500 ответ формируется в JSON — это упрощает обработку на клиенте. Партнёры, ожидающие HTML-ошибки, должны быть предупреждены.

## 62.2. Ключевые преимущества

| Преимущество | Что это даёт интегратору |
|---|---|
| **Единая точка входа** | Один базовый URL для всех методов — упрощает конфигурацию клиента |
| **Универсальный `execute`** | Пакетная отправка до N методов за один HTTP-запрос — снижает round-trip latency |
| **Удобная обработка ошибок** | Всегда HTTP 200, ошибка в теле — детерминированная обработка на клиенте |
| **Логирование из коробки** | Прозрачная диагностика на стороне платформы (см. 62.6) |
| **Автоматическая валидация** | Параметры проверяются ядром (`cmsRequest`, `cmsForm`) до бизнес-логики |
| **Модульность** | Метод принадлежит компоненту — границы ответственности очевидны |
| **Совместимость с платформенной моделью** | Права доступа, события, кэш работают так же, как в вебе |

## 62.4. Терминология и соглашения

| Термин | Значение |
|---|---|
| **Метод API** | Идентификатор вида `content.get.news` |
| **Контроллер** | Компонент платформы (первая часть имени метода) |
| **Действие (action)** | Вторая часть имени метода |
| **CTYPE** | Тип контента (третья, опциональная часть) |
| **Ключ API** | `api_key` — 32-символьный идентификатор клиента |
| **Подпись** | `sig` — HMAC-подпись запроса (опционально) |
| **`execute`** | Универсальный метод пакетного вызова |
| **`paging`** | Блок метаданных пагинации в ответе |

**Соглашения по именованию параметров:** `snake_case` (`per_page`, `date_from`, `show_all`). Временные метки — `Y-m-d H:i:s` (UTC) либо UNIX timestamp, если явно указано в описании метода.

# Часть II. Руководство для внешних разработчиков

## 62.5. Быстрый старт

**Шаг 1. Получите ключ.** Админка → **Компоненты** → **API** → **Ключи доступа** → **Создать**. Ключ генерируется автоматически (32 символа), его можно изменить и ограничить по IP и методам.

**Шаг 2. Выполните тестовый запрос.**

```bash
curl -s "https://example.com/api/method/content.get.news?api_key=ВАШ_КЛЮЧ&per_page=3"
```

**Шаг 3. Разберите ответ.**

```json
{
  "success": true,
  "result": {
    "count": 42,
    "items": [
      { "id": 101, "title": "Новость 1", "date_pub": "2024-01-15 14:30:00" }
    ]
  },
  "paging": { "page": 1, "per_page": 3, "has_next": true }
}
```

**Шаг 4. Проверьте ошибку.**

```bash
curl -s "https://example.com/api/method/content.get.news?api_key=INVALID"
```

```json
{ "error": { "error_code": 101, "error_msg": "Неверный ключ доступа", "request_params": [] } }
```

> 💡 **Совет.** Настройте логирование успешных и ошибочных запросов (см. 62.6), прежде чем передавать ключ мобильной команде — это сократит цикл диагностики с часов до минут.

**Установка:** Админка → **Компоненты** → **Установить** → **API** → **Установить**.

## 62.7. Аутентификация и безопасность

### 62.7.1. Механизмы и уровни защиты

| Механизм | Обязательность | Уровень | Где задаётся |
|---|---|---|---|
| **API-ключ** | всегда | базовый | Админка → API → Ключи |
| **IP-фильтр** | опционально | средний | Поле ключа |
| **HMAC-подпись (`sig`)** | рекомендуется для write | высокий | `enable_sig_check` |
| **CSRF-токен** | для write-методов | высокий | Автоматически |
| **HTTPS** | обязательно в продакшене | критический | Веб-сервер |

### 62.7.2. Передача ключа

Ключ может передаваться **тремя способами** (в порядке убывания предпочтения):

1. **Заголовок** `Authorization: Bearer <api_key>` — **рекомендуется** (не попадает в логи прокси и access-log).
2. **Заголовок** `X-API-Key: <api_key>` — альтернатива.
3. **Параметр запроса** `?api_key=...` — допустимо только для read-методов по HTTPS.

```bash
# Предпочтительно
curl -H "Authorization: Bearer a1b2c3d4e5f6..." \
     "https://example.com/api/method/content.get.news"

# Допустимо
curl -H "X-API-Key: a1b2c3d4e5f6..." \
     "https://example.com/api/method/content.get.news"

# Не рекомендуется (но поддерживается)
curl "https://example.com/api/method/content.get.news?api_key=a1b2c3d4e5f6..."
```

> ❌ **Никогда** не передавайте ключ в URL без HTTPS: он попадёт в access-log веб-сервера, логи прокси и историю браузера.

### 62.7.3. IP-фильтрация

Если в ключе задан список IP, платформа принимает запрос только с этих адресов. Для определения реального IP за прокси/балансировщиком передавайте параметр `ip` (см. 62.15) **или** настройте доверенные прокси на веб-сервере.

### 62.7.4. HMAC-подпись (`sig`)

Для критичных методов (платежи, изменение данных, выдача персональных данных) используйте подпись. Механизм построен на **HMAC-SHA256** и сравнении за постоянное время (`hash_equals`) — см. раздел *«Вопросы безопасности»*.

**Формула:**

```
sig = HMAC_SHA256(secret, METHOD_NAME + "\n" + canonical_query + "\n" + timestamp)
```

где `canonical_query` — отсортированные по имени параметры `name=value`, склеенные через `&`, **без** `api_key` и `sig`.

**Пример на PHP:**

```php
function buildSig(string $secret, string $method, array $params, int $ts): string {
    unset($params['api_key'], $params['sig']);
    ksort($params);
    $pairs = [];
    foreach ($params as $k => $v) {
        $pairs[] = rawurlencode($k) . '=' . rawurlencode((string)$v);
    }
    $canonical = $method . "\n" . implode('&', $pairs) . "\n" . $ts;
    return hash_hmac('sha256', $canonical, $secret);
}

$ts  = time();
$sig = buildSig($secret, 'content.add_item.news', ['title' => 'Привет'], $ts);
// В запросе передайте: sig=$sig&ts=$ts
```

**Пример на JavaScript (Node.js):**

```js
const crypto = require('crypto');

function buildSig(secret, method, params, ts) {
  const { api_key, sig, ...rest } = params;
  const canonical = Object.keys(rest).sort()
    .map(k => encodeURIComponent(k) + '=' + encodeURIComponent(rest[k]))
    .join('&');
  const payload = `${method}\n${canonical}\n${ts}`;
  return crypto.createHmac('sha256', secret).update(payload).digest('hex');
}
```

**Проверка на сервере** (в `api_actions`):

```php
if ($this->check_sig) {
    $ts = (int)$this->request->get('ts', 0);
    if (abs(time() - $ts) > 300) { // окно 5 минут
        return $this->error(115, 'Просроченная подпись (ts)');
    }
    $expected = buildSig($this->api_secret, $this->method_name, $this->request->getAll(), $ts);
    if (!hash_equals($expected, (string)$this->request->get('sig', ''))) {
        return $this->error(115, 'Неверная подпись');
    }
}
```

### 62.7.5. CSRF-токен

Для методов, изменяющих состояние (`*.add_*`, `*.update_*`, `*.delete_*`), платформа может требовать CSRF-токен. Получите его через метод `users.get_sig` или из ответа метода, возвращающего форму. Передавайте в заголовке `X-CSRF-Token` **или** параметром `csrf_token`.

Валидация выполняется через `hash_equals`, как описано в разделе *«Вопросы безопасности»* (62.7 → CSRF).

## 62.8. Синтаксис запросов

### 62.8.1. Базовый URL

```
https://<host>/api/method/<METHOD_NAME>?<PARAMS>
https://<host>/api/execute?<PARAMS>
```

### 62.8.2. Структура `METHOD_NAME`

```
<component>.<action>[.<ctype>]
```

| Часть | Обязательность | Пример |
|---|---|---|
| `component` | да | `content`, `shop`, `users` |
| `action` | да | `get`, `add_item`, `update_item` |
| `ctype` | опционально | `news`, `articles`, `products` |

**Пример:** `content.get_datasets.articles` — компонент `content`, действие `get_datasets`, тип контента `articles`.

### 62.8.3. Параметры

| Группа | Где | Пример |
|---|---|---|
| Параметры метода | query / body | `page=2&per_page=10` |
| Ключ | header / query / body | `api_key=...` |
| Подпись | query / body | `sig=...&ts=...` |
| IP клиента | query / body | `ip=8.8.8.8` |

**Правила:**

- Значения — **UTF-8**.
- GET — до ~2 КБ; при больших данных — **POST** с `Content-Type: application/json` или `application/x-www-form-urlencoded`.
- Вложенные структуры передаются JSON-сериализованно (`items=[{...}]`).
- Булевы значения: `1/0`, `true/false`, `yes/no`.

### 62.8.4. Примеры

**GET (чтение):**

```bash
curl -s "https://example.com/api/method/content.get_datasets.articles?api_key=KEY&show_all=1"
```

**POST (запись, JSON):**

```bash
curl -s -X POST "https://example.com/api/method/shop.add_order" \
  -H "Authorization: Bearer KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotence-Key: $(uuidgen)" \
  -d '{
    "user_id": 123,
    "items": [
      {"product_id": 456, "quantity": 2},
      {"product_id": 789, "quantity": 1}
    ]
  }'
```

**POST (запись, form-urlencoded):**

```bash
curl -s -X POST "https://example.com/api/method/content.add_item.news" \
  -H "Authorization: Bearer KEY" \
  -d "title=Заголовок&content=Текст&is_published=1"
```

### 62.8.5. Идемпотентность

Для `*.add_*` используйте заголовок `Idempotence-Key` (по аналогии с YooKassa, см. раздел *«Интеграция платежного шлюза»*). Повторный запрос с тем же ключом вернёт тот же результат без создания дубликата.

```bash
curl -X POST "https://example.com/api/method/shop.add_order" \
  -H "Authorization: Bearer KEY" \
  -H "Idempotence-Key: order-2024-01-15-001" \
  -d '{...}'
```

## 62.9. Формат ответов

### 62.9.1. Успешный ответ

```json
{
  "success": true,
  "result": { ... },
  "paging": { "page": 1, "per_page": 20, "has_next": true }
}
```

| Поле | Наличие | Описание |
|---|---|---|
| `success` | всегда | `true` |
| `result` | всегда | Данные метода (объект/массив/скаляр) |
| `paging` | при списках | Метаданные пагинации |
| `meta` | опционально | Доп. данные (время генерации, версия API) |

### 62.9.2. Ответ с ошибкой

```json
{
  "error": {
    "error_code": 101,
    "error_msg": "Неверный ключ доступа",
    "request_params": [
      { "key": "method", "value": "content.get.news" }
    ]
  }
}
```

**Всегда HTTP 200.** Клиент обязан проверять наличие поля `error` в теле — это отличает ошибку от успеха. Такой подход выбран осознанно: он упрощает обработку на мобильных клиентах, где перехват HTTP-кодов не всегда удобен.

| Поле | Описание |
|---|---|
| `error_code` | Числовой код (см. 62.10) |
| `error_msg` | Текст на языке локали (`cmsConfig::get('locale')`) |
| `request_params` | Массив `{key, value}` — для валидационных ошибок |

### 62.9.3. Пагинация

Объект `paging` присутствует во всех list-методах:

| Поле | Тип | Описание |
|---|---|---|
| `page` | int | Номер текущей страницы (с 1) |
| `per_page` | int | Размер страницы |

## 62.14. Универсальный метод `execute`

Позволяет выполнить несколько методов за один HTTP-запрос, сохраняя промежуточные результаты.

**Формат:** `GET /api/execute?code=<JSON-encoded-array>&api_key=...`

**Структура `code`:**

```json
[
  { "method": "content.get.news", "params": { "page": 1 } },
  { "method": "shop.get_cart", "params": {} }
]
```

**Пример:**

```bash
curl -G "https://example.com/api/execute" \
  --data-urlencode 'code=[{"method":"content.get.news","params":{"page":1}},{"method":"shop.get_cart"}]' \
  --data-urlencode 'api_key=KEY'
```

**Ответ:**

```json
{
  "success": true,
  "result": [
    { "method": "content.get.news", "result": { "count": 10, "items": [ ... ] } },
    { "method": "shop.get_cart", "result": { "items_count": 3, "total": 4500 } }
  ]
}
```

**Ограничения и правила:**

| Параметр | Значение |
|---|---|
| Максимум методов в пакете | 20 |
| Общий таймаут | 30 секунд |
| Вложенный `execute` | **запрещён** |
| Write-методы в пакете | разрешены (каждый получает свой CSRF/sig) |
| Частичная ошибка | если один метод упал, остальные выполняются; в `result` будет `error` для упавшего |

**Пример с частичной ошибкой:**

```json
{
  "success": true,
  "result": [
    { "method": "content.get.news", "result": { ... } },
    { "method": "shop.get_cart", "error": { "error_code": 71, "error_msg": "Требуется авторизация" } }
  ]
}
```

> ⚠️ **JSON должен быть валидным по RFC 8259.** Никаких одинарных кавычек, завершающих запятых, комментариев. Это частая причина ошибки `8` («Неверный запрос»).

## 62.15. Определение IP посетителя

Если запросы к API идут с одного сервера (например, backend-скрипт), но нужно, чтобы платформа видела **реальный IP конечного пользователя** (для геолокации, антифрода, rate limiting), передайте его параметром `ip`:

```bash
curl "https://example.com/api/method/geo.get_current_country?api_key=KEY&ip=8.8.8.8"
```

**Правила:**

- Параметр `ip` **учитывается только** если запрос пришёл с IP, входящего в белый список «доверенных прокси» (настраивается в компоненте).
- Значение валидируется (`filter_var(..., FILTER_VALIDATE_IP)`).
- Неверный IP → код `777`.

## 62.16. Версионирование и обратная совместимость

### 62.16.1. Стратегия версионирования

API DST Platform **не использует URL-версионирование** (`/v1/`, `/v2/`). Вместо этого применяется **эволюционное версионирование методов**:

- Новые поля добавляются в ответы — **без** ломания существующих клиентов.
- Удаление полей и изменение типов — **только** через новую версию метода (`content.get.news_v2`) при сохранении старого.
- Изменение поведения — через флаг (`deprecated=true` в ответе + HTTP-заголовок `Warning: 299 - "Deprecated method"`).

### 62.16.2. Гарантии обратной совместимости

| Изменение | Совместимо | Комментарий |
|---|---|---|
| Добавление поля в `result` | ✅ | Клиенты должны игнорировать незнакомые поля |
| Добавление нового метода | ✅ | Не влияет на существующие |
| Добавление необязательного параметра | ✅ | — |
| Удаление поля | ❌ | Только через `_v2` |
| Изменение типа поля | ❌ | Только через `_v2` |
| Изменение кода ошибки | ⚠️ | Считается breaking change |
| Изменение семантики параметра | ❌ | Только через `_v2` |

### 62.16.3. Политика deprecated

Метод помечается как `deprecated` минимум за **6 месяцев** до удаления. В ответе появляется:

```json
{
  "success": true,
  "result": { ... },
  "meta": { "deprecated": true, "sunset": "2025-12-31" }
}
```

Заголовок: `Warning: 299 - "This method is deprecated and will be removed on 2025-12-31"`.

### 62.16.4. Рекомендации клиентам

1. **Всегда** игнорируйте неизвестные поля в ответе.
2. Не полагайтесь на порядок полей в JSON.
3. Обрабатывайте `meta.deprecated` и переключайтесь на новую версию заранее.
4. Логируйте `Warning`-заголовки — они сигнализируют о скором breaking change.

## 62.17. Rate limiting

### 62.17.1. Механизм

Ограничение частоты реализовано через `cmsCache` (Redis/Memcached) — см. раздел *«Вопросы безопасности»*. Лимит задаётся на ключ и на IP.

| Уровень | По умолчанию | Настраивается |
|---|---|---|
| На ключ | 100 запросов/мин | `rate_limit_per_minute` |
| На IP | 300 запросов/мин | Глобально |
| На `execute` | 20 методов/запрос | Жёстко |
| На метод (индивидуально) | — | В `api_docs/*.json` |

### 62.17.2. Заголовки ответа

При каждом запросе платформа возвращает:

```
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 47
X-RateLimit-Reset: 1700000060
Retry-After: 30          (только при 429)
```

### 62.17.3. Обработка на клиенте

При получении `error_code: 429`:

1. Прочитайте `Retry-After`.
2. Подождите указанное время **или** примените **экспоненциальный backoff** (как в разделе *«Интеграция платежного шлюза»*).

```php
function callWithRetry(callable $fn, int $maxRetries = 5): mixed {
    $attempt = 0;
    while (true) {
        try {
            $result = $fn();
            if (isset($result['error']) && $result['error']['error_code'] === 429) {
                throw new RateLimitException($result['error']['error_msg']);
            }
            return $result;
        } catch (RateLimitException $e) {
            if (++$attempt > $maxRetries) throw $e;
            $delay = min(60, 2 ** $attempt); // 2, 4, 8, 16, 32 сек
            sleep($delay);
        }
    }
}
```

### 62.17.4. Лучшие практики

- **Не ретрайте** на `4xx`, кроме `429`.
- Ретрайте на `5xx` и сетевые ошибки — с backoff.
- Ограничивайте общий бюджет ретраев (например, 5 минут).
- Используйте идемпотентные ключи (`Idempotence-Key`) для write-методов при ретраях.

## 62.18. Кэширование ответов

### 62.18.1. Серверное кэширование

Для тяжёлых list-методов (`content.get.*`, `shop.get_products`) платформа кэширует ответы через `cmsCache`. Управление — в `api_docs/*.json`:

```json
{
  "method": "content.get.news",
  "cache_ttl": 300,
  "cache_key_params": ["page", "per_page", "filter"]
}
```

`cache_ttl` — время жизни в секундах. При изменении контента кэш инвалидируется через хуки (см. 62.24).

### 62.18.2. HTTP-кэширование

Платформа возвращает заголовки:

```
Cache-Control: private, max-age=60
ETag: "abc123"
Last-Modified: Mon, 15 Jan 2024 14:30:00 GMT
```

Клиент может использовать **условные запросы**:

```bash
curl -H "If-None-Match: \"abc123\"" \
     "https://example.com/api/method/content.get.news?api_key=KEY"
# → 304 Not Modified, тело пустое
```

### 62.18.3. Рекомендации клиентам

- Для справочников (страны, регионы, категории) — кэшируйте на клиенте надолго (часы/дни).
- Для списков товаров — 1–5 минут.
- Для карточек — до 1 часа.
- Для корзины/заказов — **не кэшируйте**.

## 62.19. Асинхронные операции и очереди

### 62.19.1. Долгие операции

Ряд методов (экспорт каталога, массовое обновление цен, генерация YML) не могут выполняться синхронно за разумное время. Для них используется **асинхронный паттерн** (тот же, что в вебхуках YooKassa, см. раздел *«Интеграция платежного шлюза»*):

1. Клиент вызывает метод (`shop.export_start`).
2. Платформа создаёт задачу в очереди и **немедленно** возвращает `task_id`.
3. Клиент периодически опрашивает `shop.export_status?task_id=...` **или** получает вебхук по завершении.

**Пример:**

```bash
# 1. Запуск
curl -X POST "https://example.com/api/method/shop.export_start" \
  -H "Authorization: Bearer KEY" \
  -d '{"type":"products","format":"xlsx"}'
```

```json
{ "success": true, "result": { "task_id": "task_a1b2c3d4", "status": "queued" } }
```

```bash
# 2. Опрос
curl "https://example.com/api/method/shop.export_status?task_id=task_a1b2c3d4&api_key=KEY"
```

```json
{
  "success": true,
  "result": {
    "task_id": "task_a1b2c3d4",
    "status": "completed",
    "progress": 100,
    "file_url": "/upload/exports/products_2024-01-15.xlsx",
    "created_at": "2024-01-15 14:30:00",
    "completed_at": "2024-01-15 14:32:11"
  }
}
```

**Статусы:** `queued` → `running` → `completed` / `failed`. При `failed` — поле `error`.

### 62.19.2. Вебхуки (исходящие уведомления)

Если платформа настроена отправлять вебхуки (аналогично YooKassa), клиент регистрирует endpoint:

```bash
curl -X POST "https://example.com/api/method/webhooks.register" \
  -H "Authorization: Bearer KEY" \
  -d '{"url":"https://client.example.com/dst-webhook","events":["task.completed","order.paid"]}'
```

**Требования к endpoint:**

- Отвечать HTTP 200 за < 5 сек.
- Быть идемпотентным (события могут дублироваться).
- Проверять подпись `X-DST-Signature` (HMAC-SHA256 тела).
- Логировать все входящие события.

**Проверка подписи:**

```php
$payload = file_get_contents('php://input');
$expected = hash_hmac('sha256', $payload, $webhookSecret);
if (!hash_equals($expected, $_SERVER['HTTP_X_DST_SIGNATURE'] ?? '')) {
    http_response_code(403); exit;
}
```

## 62.20. Тестирование интеграции

### 62.20.1. Postman-коллекция

Импорт: **API → Экспорт коллекции Postman** (в админке). Коллекция содержит:

- Переменные окружения (`base_url`, `api_key`, `user_id`, `csrf_token`).
- Pre-request скрипты для автогенерации `sig` и `ts`.
- Тесты на коды ошибок.

**Пример pre-request script (Postman):**

```js
const crypto = require('crypto-js');
const ts = Math.floor(Date.now() / 1000).toString();
const method = pm.request.url.getPath().replace('/api/method/', '');
const params = pm.request.url.query.all()
    .filter(p => !['api_key','sig','ts'].includes(p.key))
    .sort((a,b) => a.key.localeCompare(b.key))
    .map(p => encodeURIComponent(p.key) + '=' + encodeURIComponent(p.value))
    .join('&');
const payload = `${method}\n${params}\n${ts}`;
const sig = crypto.HmacSHA256(payload, pm.environment.get('api_secret')).toString();
pm.request.addQueryParams([{key:'ts',value:ts},{key:'sig',value:sig}]);
```

## 62.21. Диагностика типовых ошибок

| Симптом | Вероятная причина | Что делать |
|---|---|---|
| `error_code: 101` | Неверный/устаревший ключ | Проверить `api_key`, перевыпустить |
| `error_code: 8` | Невалидный JSON в `code` | Проверить RFC 8259, убрать trailing comma |
| `error_code: 115` | Подпись не сходится | Пересчитать `sig`, проверить `ts`, `canonical_query` |
| `error_code: 777` | Неверный `ip` | Проверить валидность IPv4/IPv6 |
| `error_code: 429` | Rate limit | Backoff + `Retry-After` |
| `success:true`, но пустой `items` | Фильтры слишком узкие | Убрать `filter`, увеличить `per_page` |
