# 11. Бизнес-компоненты

В этом документе представлен подробный обзор функциональных компонентов платформы DST Platform, реализующих её двойную архитектуру: электронную коммерцию (маркетплейс, B2B) и социальные функции (сообщества, взаимодействие). Все компоненты реализованы как автономные модули в соответствии с архитектурой MVC и размещены в каталоге `/system/controllers/`.

> **Терминологическое примечание**: В контексте данного документа термины *«бизнес-компонент»*, *«функциональный модуль»* и *«компонент»* используются как синонимы. Официальное название в архитектуре платформы — **компонент** (см. раздел *«Компонентная система»*).

Для углублённого изучения отдельных областей рекомендуется:
- **Электронная коммерция**: раздел *«Маркетплейс и электронная коммерция»*
- **Интеграция с маркетплейсами**: *«Интеграция с внешними торговыми площадками»*
- **Управление поставщиками**: *«Система для партнёров и поставщиков»*
- **Социальные функции**: *«Функции социальных платформ»*
- **Архитектура компонентов**: *«Компонентная система»*

## 11.1. Архитектурные принципы компонентов

Каждый компонент представляет собой **самодостаточную функциональную единицу**, инкапсулирующую логику определённой предметной области. Компонент может включать любую комбинацию следующих элементов:

| Элемент | Обязательность | Расположение | Назначение |
|--------|----------------|--------------|------------|
| Фронтенд-контроллер | Опционально | `/system/controllers/{name}/frontend.php` | Обработка публичных запросов |
| Бэкенд-контроллер | Опционально | `/system/controllers/{name}/backend/controller.php` | Административный интерфейс |
| Модель (фронтенд) | Опционально | `/system/controllers/{name}/model.php` | Доступ к данным, бизнес-логика |
| Модель (бэкенд) | Опционально | `/system/controllers/{name}/backend/model.php` | Расширение модели для админки |
| Шаблоны | Опционально | `/templates/{theme}/controllers/{name}/` | Визуальное представление |
| Виджеты | Опционально | `/system/controllers/{name}/widgets/` | Переиспользуемые UI-блоки |
| Обработчики событий | Опционально | `/system/controllers/{name}/hooks.php` | Реакция на события других компонентов |

**Ключевые принципы**:
- **Модульность**: каждый компонент изолирован и может быть включён/отключён независимо.
- **Слабая связанность**: взаимодействие через события (`cmsEventsManager`), а не прямые вызовы.
- **Единые соглашения**: строгие правила именования классов и файлов (см. раздел *«Компонентная система»*).
- **Гибкость структуры**: компонент может содержать только модель (сервисный компонент) или только `hooks.php` (слушатель событий).

Каждый бизнес-модуль находится в отдельной директории /system/controllers/{module_name}/ и использует единые правила именования:

- Класс контроллера: наследует от cmsController, cmsFrontend, или cmsBackend
- Класс модели: наследует от cmsModel, названный model{ModuleName}
- Шаблоны: .tpl.php файлы в /templates/{theme}/controllers/{module_name}/

## 11.2. Структура каталогов компонента

```
/system/controllers/shop/
├── frontend.php               # class shop extends cmsFrontend
├── model.php                  # class modelShop extends cmsModel
├── hooks.php                  # Обработчики событий
├── options.form.php           # Форма настроек компонента
├── backend/
│   ├── controller.php         # class backendShop extends cmsBackend
│   └── model.php              # class modelBackendShop extends modelShop
└── widgets/
    ├── cart.php               # class shopCart extends cmsWidget
    └── products.php
```

**Особенности**:
- Фронтенд-контроллер: файл `frontend.php`, класс `{имя_компонента}` (в нижнем регистре, например `shop`).
- Бэкенд-контроллер: файл `backend/controller.php`, класс `backend{ИмяВPascalCase}` (например `backendShop`).
- Модель: класс `model{ИмяВPascalCase}` (например `modelShop`).
- Все пути к шаблонам разрешаются с учётом наследования тем (см. *«Система шаблонов»*).

<img src="https://github.com/DSTGlobal/DST-Platform/blob/main/images/65.png" alt="DST Platform">

Основные характеристики:

Модульность: каждая бизнес-область инкапсулирована в собственный контроллер.
Разделение ответственности: логика (контроллер/модель) отделена от представления (шаблоны).
Дополнительные компоненты: Модули могут содержать только фронтенд, только бэкенд, только модель или любую их комбинацию.

Интеграция, управляемая событиями: модули взаимодействуют через cmsEventsManager хуки.

## 11.4. Модель взаимодействия компонентов

Компоненты взаимодействуют через три основных механизма:

1. **Общие синглтон-сервисы**  
   Все компоненты получают доступ к ядру через `cmsCore::getInstance()`:
   ```php
   $user = cmsUser::getInstance();      // Текущий пользователь
   $db   = cmsCore::getInstance()->db;  // Подключение к БД
   $perm = cmsPermissions::getInstance(); // Проверка прав
   ```

2. **Событийная шина (`cmsEventsManager`)**  
   Пример интеграции `shop` и `search`:
   ```php
   // В компоненте shop (model.php)
   $item = cmsEventsManager::hook('shop_after_add_item', $item);
   
   // В компоненте search (hooks.php)
   public function hookShopAfterAddItem($item) {
       $this->model->indexProduct($item); // Индексация в поиске
       return $item;
   }
   ```

3. **Наследование моделей**  
   Специализированные модели расширяют базовые:
   ```php
   // /system/controllers/partner/model.php
   class modelPartner extends modelShop {
       // Дополнительные методы для логики продавца
       public function getVendorStatistics($vendor_id) { ... }
   }
   ```

На следующей диаграмме показано взаимодействие бизнес-модулей посредством общих основных сервисов и системы событий:

<img src="https://github.com/DSTGlobal/DST-Platform/blob/main/images/66.png" alt="DST Platform">

Основные модели интеграции:

1. Общие сервисы: доступ ко всем модулям cmsUser осуществляется cmsConfig через синглтон cmsPermissions.cmsCore
2. Коммуникация, управляемая событиями: модули запускают события через cmsEventsManager; другие модули подписываются на эти хуки.
3. Наследование моделей: Модели, специфичные для предметной области, расширяют cmsModel другие специализированные модели (например, modelPartner расширяют modelShop).
4. Междоменные возможности: универсальные модули (например comments, reviews) могут подключаться к нескольким доменам.
5. Сервисные модули: Интеграционные модули ( market, api), считывающие данные из доменных моделей без их изменения.

## 11.6. Экосистема электронной коммерции: детализация взаимодействий

```
┌─────────────┐
│   Покупатель │
└──────┬──────┘
       │
       ▼
┌───────────────────────────────────────────────────────┐
│                    КОМПОНЕНТ shop                     │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐   │
│  │   Каталог   │  │   Корзина   │  │ Оформление  │   │
│  │ (товары)    │  │             │  │   заказа    │   │
│  └──────┬──────┘  └──────┬──────┘  └──────┬──────┘   │
└─────────┼─────────────────┼────────────────┼──────────┘
          │                 │                │
          ▼                 ▼                ▼
    ┌───────────┐     ┌───────────┐    ┌───────────┐
    │  partner  │     │  payment  │    │ delivery  │
    │ (продавец)│     │ (платежи) │    │(доставка) │
    └─────┬─────┘     └─────┬─────┘    └─────┬─────┘
          │                 │                │
          ▼                 ▼                ▼
    ┌───────────┐     ┌───────────┐    ┌───────────┐
    │  orders   │◄────┤  market   │    │  stocks   │
    │ (заказы)  │     │ (Я.Маркет)│    │ (акции)   │
    └───────────┘     └───────────┘    └───────────┘
```

**Ключевые интеграции**:
- `partner` расширяет `modelShop` для работы с товарами конкретного продавца.
- `payment` использует SDK ЮKassa (`yoomoney/yookassa-sdk-php`) для обработки платежей.
- `delivery` интегрируется с CDEK через `sanmai/cdek-sdk` для расчёта стоимости и отслеживания.
- `market` генерирует YML-фиды через фоновые задачи (`cron_yml_create.php`).
- `search` индексирует товары через событие `shop_after_add_item`.

Модули электронной коммерции образуют тесно интегрированную экосистему, центром которой является shop контроллер:

<img src="https://github.com/DSTGlobal/DST-Platform/blob/main/images/68.png" alt="DST Platform">

Ключевые взаимоотношения:

- shop Контроллер: Центральный узел, /system/controllers/shop/ содержащий логику каталога, корзины, оформления заказа и обработки заказов.
- modelShop Основная модель данных, расширяющая существующую cmsModel, доступна по адресу /system/controllers/shop/model.php
- partner контроллер: интерфейс поставщика, расширяющий функциональность магазина через modelPartner extends modelShop
- Интеграция платежных систем: payment контроллер использует SDK YooKassa для обработки транзакций.
- Интеграция с системой доставки: delivery контроллер использует SDK CDEK для выполнения логистических расчетов.
- Внешние каналы: market контроллер генерирует YML-каналы shopModel данных с помощью заданий cron.
- Экспорт данных: Данные о товарах экспортируются в Excel с cron_export.php с помощью библиотеки Box Spout.

**Особенности**:
- `activity` агрегирует события из `comments`, `reviews`, `forum`, `photos` через систему хуков.
- `comments` и `reviews` могут быть привязаны к любому типу контента (товары, статьи, посты).
- `groups` предоставляет изолированные пространства с собственными правилами доступа и контентом.
- `cmsUser` (синглтон ядра) управляет сессией и правами, но не является частью компонента `users`.

Модули социальных платформ предоставляют возможности для создания сообществ и взаимодействия:

Ключевые взаимоотношения:

- users Контроллер: Управление профилями /system/controllers/users/, внедрение панели управления покупателя.
- cmsUser Синглтон: Основной сервис для /system/core/user.php поддержания текущего состояния пользовательской сессии.

- comments Контроллер: Система комментариев, которую можно прикрепить и интегрировать с любым типом контента.
- content контроллер: Универсальный конструктор контента в /system/controllers/content/
- Производные типы контента: news, posts, help расширяют базовую content функциональность

## 11.8. Механизмы расширения компонентов

Бизнес-модули предоставляют множество механизмов расширения для настройки без изменения основного кода:

| Тип расширения | Расположение | Пример использования | Рекомендации |
|----------------|--------------|----------------------|--------------|
| **Хуки событий** | `hooks.php` | Добавление логики при оплате заказа: `hookShopOrderPaid()` | Предпочтительный способ; не требует изменения исходного кода |
| **Наследование модели** | `model.php` | `class modelMyShop extends modelShop` | Для глубокой кастомизации бизнес-логики данных |
| **Переопределение шаблона** | `/templates/{theme}/controllers/{name}/` | Кастомизация карточки товара | Сохраняйте структуру данных; используйте наследование тем |
| **Создание виджета** | `widgets/{name}.php` | Виджет «Популярные товары» | Используйте `$this->getOption()` для настройки параметров |
| **Расширение бэкенда** | `backend/controller.php` | Добавление кастомного отчёта в админку | Наследуйте от `backend{Component}` |
| **Кастомный контроллер** | `frontend.php` | Изменение логики оформления заказа | Используйте осторожно; предпочтительнее хуки |

**Пример хука для уведомления продавца**:
```php
// /system/controllers/partner/hooks.php
class partner {
    public function hookShopOrderPaid($order) {
        // Получаем данные продавца
        $vendor = $this->model->getVendorByProductId($order['items'][0]['product_id']);
        
        // Отправляем уведомление
        $this->model->sendNotification(
            $vendor['id'],
            'Заказ #' . $order['id'] . ' оплачен',
            'Требуется подготовить товар к отправке'
        );
        
        // Обогащаем данные для последующих хуков
        $order['notified_vendor'] = true;
        return $order; // Обязательно возвращаем данные
    }
}
```

## 11.9. Конфигурация и схема данных

Как правило, каждый бизнес-модуль хранит конфигурацию в базе данных и поддерживает собственную схему таблиц.

### Регистрация компонента
Компоненты с административной частью регистрируются в таблице **`controllers`** (не `cms_components`):
```sql
INSERT INTO controllers (name, title, is_enabled, options) 
VALUES ('my_custom_module', 'Мой модуль', 1, '{"param1":"value1"}');
```

### Структура таблиц
- **Префикс таблиц**: Задаётся в глобальной конфигурации (`config.php`), по умолчанию `cms_`.
- **Именование таблиц компонента**: `{префикс}{имя_компонента}_{сущность}`  
  Примеры:
  - `cms_shop_products` — товары магазина
  - `cms_users_profiles` — профили пользователей
  - `cms_content_items` — записи контента
  - `cms_groups_members` — членство в группах

### Доступ к данным
Все операции с БД выполняются через модель:
```php
// В контроллере или модели
$item = $this->model->getItem('shop_products', $id); // Безопасный SELECT
$this->model->update('shop_products', $id, ['price' => 1000]); // UPDATE
$this->model->delete('shop_products', $id); // DELETE

// Query Builder
$products = $this->model->select('shop_products')
    ->filterEqual('category_id', 5)
    ->filterGt('price', 1000)
    ->orderBy('date_pub', 'DESC')
    ->limit(10)
    ->getItems();
```

### Настройки компонента
```php
// В контроллере
$apiKey = $this->getOption('api_key'); // Настройки компонента
$debugMode = cmsConfig::get('debug');  // Глобальная конфигурация
```

## 11.10. Фоновые задачи (Cron) и компоненты

Для автоматизации нескольких бизнес-модулей предусмотрены соответствующие задания cron:

<img src="https://github.com/DSTGlobal/DST-Platform/blob/main/images/70.png" alt="DST Platform">

| Скрипт | Событие | Компонент-обработчик | Назначение |
|--------|---------|----------------------|------------|
| `cron_export.php` | `cron_export_products_job` | `shop` | Экспорт товаров в Excel/CSV (Box Spout) |
| `cron_yml_create.php` | `cron_yml_create_files` | `shop` | Генерация YML-фида для внутреннего использования |
| `cron_yml_market_create.php` | `cron_yml_market_create_files` | `market` | Генерация YML-фида для Яндекс.Маркета |
| `cron_partner_import.php` | `cron_partner_import_job` | `partner` | Импорт данных от внешних поставщиков |
| `cron_test_run_set_change_price.php` | `cron_set_change_price` | `shop` | Автоматическое обновление цен по расписанию |

**Архитектура выполнения**:
1. Скрипт получает файловую блокировку (предотвращает параллельный запуск).
2. Инициализирует ядро через `bootstrap.php` (без сессии).
3. Вызывает событие: `cmsEventsManager::hook('cron_export_products_job')`.
4. Все подписанные компоненты выполняют свою логику.
5. Блокировка снимается; скрипт завершается.

Каждый скрипт cron:

1. Получает блокировку файла для предотвращения одновременного выполнения.
2. Запускает систему с помощью bootstrap.php
3. Вызывает метод-перехватчик в целевом контроллере.
4. Передает бизнес-логику модулю.

> Подробнее: раздел *«Архитектура планировщика Cron»*.

## 11.11. Интеграция с внешними сервисами

Бизнес-модули интегрируются с внешними сервисами посредством зависимостей, управляемых Composer.

| Компонент | Внешняя зависимость | Composer-пакет | Назначение |
|-----------|---------------------|----------------|------------|
| `shop`, `orders` | Box Spout | `box/spout:^3.3` | Экспорт/импорт Excel, CSV |
| `delivery` | CDEK SDK | `sanmai/cdek-sdk:^0.6.22` | Расчёт доставки, ПВЗ, отслеживание |
| `payment` | ЮKassa SDK | `yoomoney/yookassa-sdk-php:^2.1` | Приём платежей, возвраты, чеки |
| `auth`, `fraud` | GeoIP2 | `geoip2/geoip2:~2.0` | Геолокация по IP, антифрод |
| Все компоненты | Guzzle | `guzzlehttp/guzzle:~6.0` | HTTP-клиент для внешних API |
| Все компоненты | phpFastCache | `phpfastcache/phpfastcache:^7.1` | Абстракция кэширования |

## 11.12. Создание кастомного компонента

### Шаг 1: Декларативный подход (рекомендуется для простых сущностей)
1. Перейдите в админку → **Генератор контента**.
2. Создайте новый тип контента (например, «Каталог оборудования»).
3. Настройте поля, категории, шаблоны.
4. Система автоматически создаст:
   - Таблицу в БД
   - CRUD-интерфейс в админке
   - Шаблоны фронтенда
   - Поддержку комментариев, тегов, SEO

### Шаг 2: Императивный подход (для сложной логики)
```bash
# 1. Создайте структуру каталогов
mkdir -p /system/controllers/my_equipment/{backend,widgets}
mkdir -p /templates/default/controllers/my_equipment/backend

# 2. Создайте фронтенд-контроллер
# /system/controllers/my_equipment/frontend.php
<?php
class my_equipment extends cmsFrontend {
    public function actionIndex() {
        $items = $this->model->getPublishedItems();
        return $this->render('index', ['items' => $items]);
    }
}

# 3. Создайте модель
# /system/controllers/my_equipment/model.php
<?php
class modelMyEquipment extends cmsModel {
    protected $table_name = 'my_equipment_items';
    
    public function getPublishedItems() {
        return $this->select($this->table_name)
            ->filterEqual('is_published', 1)
            ->orderBy('date_pub', 'DESC')
            ->getItems();
    }
}

# 4. Создайте шаблон
# /templates/default/controllers/my_equipment/index.tpl.php
<?php $this->addCSS('controllers/my_equipment/styles.css'); ?>
<div class="equipment-list">
    <?php foreach($items as $item): ?>
        <div class="equipment-item">
            <h3><?= htmlspecialchars($item['title']) ?></h3>
            <p><?= htmlspecialchars($item['description']) ?></p>
        </div>
    <?php endforeach; ?>
</div>

# 5. (Опционально) Зарегистрируйте в БД
INSERT INTO controllers (name, title, is_enabled) 
VALUES ('my_equipment', 'Каталог оборудования', 1);
```

### Требования к именованию компонента
- Начинается со строчной латинской буквы
- Содержит только буквы, цифры, подчёркивание
- Минимальная длина — 3 символа
- Уникальное имя в системе  
✅ Допустимые: `shop`, `my_equipment`, `b2b_portal`  
❌ Недопустимые: `Shop`, `my-equipment`, `2fa`, `my`

## 11.13. Рекомендации и лучшие практики

### ✅ Рекомендуется
- Использовать **хуки** для расширения существующих компонентов (не правьте ядро!).
- Для кастомизации внешнего вида — **переопределять шаблоны** в теме, а не в `/system/`.
- Валидировать и санитизировать все входные данные через методы `cmsModel` или `cmsRequest`.
- Кэшировать тяжёлые запросы через `cmsCache::getInstance()`.
- Документировать события, которые генерирует ваш компонент.

### ❌ Избегайте
- Прямых SQL-запросов в шаблонах или контроллерах (используйте модель).
- Жёстких зависимостей между компонентами (предпочитайте события).
- Изменения файлов в `/system/core/` — используйте наследование или хуки.
- Хранения секретов (ключи API) в коде — используйте `config.php` или переменные окружения.
