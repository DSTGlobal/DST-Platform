# 6. Базовая архитектура

Этот документ описывает фундаментальные архитектурные принципы DST Platform: паттерны проектирования, организацию ядра, механизмы взаимодействия компонентов и стратегии расширяемости. Он служит основой для понимания всех остальных подсистем — от маршрутизации до бизнес-логики.

Для деталей по конкретным аспектам см.:
- **«Загрузка и инициализация системы»** — последовательность запуска
- **«Шаблон MVC и жизненный цикл запроса»** — обработка запросов
- **«Система компонентов»** — структура модулей
- **«Система событий и обработчиков»** — слабосвязанная интеграция

## 6.1. Архитектурные паттерны

DST Platform построена на трёх ключевых паттернах:

| Паттерн | Реализация | Цель |
|--------|------------|------|
| **Singleton** | Все базовые сервисы (`cmsConfig`, `cmsCache`, `cmsUser` и др.) | Гарантирует единственный экземпляр критически важных объектов |
| **Service Locator** | `cmsCore::getInstance()` | Централизованный доступ к системным сервисам без жёстких зависимостей |
| **Model-View-Controller (MVC)** | Контроллеры, модели, шаблоны в `/system/controllers/{component}/` | Чёткое разделение логики, данных и представления |

Архитектура поддерживает **гибридную двойную модель**: единое ядро обслуживает как социальные функции (сообщества, активность), так и бизнес-процессы (торговля, логистика).

---

## 6.2. Локатор сервисов (`cmsCore`)

Класс `cmsCore` выступает в роли центрального указателя сервисов, обеспечивая доступ ко всем основным компонентам системы. Все основные сервисы реализованы как синглтоны, доступ к которым осуществляется через статические getInstance() методы.

<img src="https://github.com/DSTGlobal/DST-Platform/blob/main/images/28.png" alt="DST Platform">

Диаграмма: Основной локатор сервисов и зависимости-синглтоны

Класс `cmsCore` выступает центральным **service locator’ом**. Он предоставляет доступ ко всем системным сервисам через свойства:

```php
$core = cmsCore::getInstance();

$core->db;          // cmsDatabase
$core->config;      // cmsConfig
$core->user;        // cmsUser
$core->template;    // cmsTemplate
$core->cache;       // cmsCache
$core->events;      // cmsEventsManager
$core->permissions; // cmsPermissions
```

### Преимущества
- **Слабая связанность**: компоненты не зависят напрямую от реализаций.
- **Тестируемость**: можно подменить любой сервис в тестах.
- **Единая точка инициализации**: все сервисы создаются в `bootstrap.php`.

---

## 6.3. Синглтоны ядра

Все базовые сервисы реализованы как синглтоны и доступны глобально.

### Обязательные синглтоны (инициализируются при загрузке)

| Класс | Файл | Доступ | Ответственность |
|-------|------|--------|------------------|
| `cmsCore` | `/system/core/core.php` | `cmsCore::getInstance()` | Локатор сервисов, оркестратор |
| `cmsConfig` | `/system/core/config.php` | `cmsConfig::getInstance()` | Глобальная конфигурация |
| `cmsCache` | `/system/core/cache.php` | `cmsCache::getInstance()` | Абстракция кэширования |
| `cmsEventsManager` | `/system/core/eventsmanager.php` | `cmsEventsManager::getInstance()` | Система событий |
| `cmsUser` | `/system/core/user.php` | `cmsUser::getInstance()` | Сессия, аутентификация |
| `cmsTemplate` | `/system/core/template.php` | `cmsTemplate::getInstance()` | Рендеринг шаблонов |
| `cmsPermissions` | `/system/core/permissions.php` | `cmsPermissions::getInstance()` | RBAC, проверка прав |

### Не-синглтоны (инициализируются через `cmsCore`)

| Класс | Файл | Доступ | Ответственность |
|-------|------|--------|------------------|
| `cmsDatabase` | `/system/core/database.php` | `$core->db` | Низкоуровневый доступ к MySQL |
| `cmsRequest` | `/system/core/request.php` | `$core->request` | Парсинг и санитизация входящих данных |

> **Примечание**: `cmsDatabase` и `cmsRequest` не являются синглтонами в классическом смысле, но существуют в единственном экземпляре через `cmsCore`.

## 6.4. Последовательность инициализации

Процесс начальной загрузки (bootstrap process - bootstrap.php) инициализирует всю систему в определенном порядке, чтобы обеспечить доступность зависимостей при необходимости.

<img src="https://github.com/DSTGlobal/DST-Platform/blob/main/images/29.png" alt="DST Platform">

Диаграмма: Последовательность инициализации

Процесс загрузки (`bootstrap.php`) следует строгому порядку:

1. Определение `PATH`, `ROOT`
2. Установка кодировки: `mb_internal_encoding('UTF-8')`
3. Загрузка автозагрузчика Composer
4. Регистрация пользовательского автозагрузчика
5. Инициализация `cmsConfig`
6. Настройка обработки ошибок (в зависимости от `debug`)
7. Проверка состояния установки (`is_installed`)
8. Условная инициализация сессии (`SESSION_START`)
9. Инициализация `cmsCore`
10. Подключение к БД (`$core->connectDB()`)
11. Инициализация кэша (`cmsCache::start()`)
12. Вызов события `core_start`
13. Загрузка локализации

Эта последовательность гарантирует, что каждый сервис инициализируется **только после своих зависимостей**.

## 6.5. Механизм автозагрузки

DST Platform использует собственный механизм автозагрузки, определенный в файле, /system/config/autoload.phpкоторый следует соглашениям об именовании для поиска файлов классов.

<img src="https://github.com/DSTGlobal/DST-Platform/blob/main/images/30.png" alt="DST Platform">

Диаграмма: Автоматическая загрузка сопоставления шаблонов

Платформа использует **два уровня автозагрузки**:

### 1. Composer (PSR-4)
Загружает сторонние пакеты и пользовательские namespace:

```json
"autoload": {
    "psr-4": {
        "shopUtils\\": "system/controllers/shop/utils/"
    }
}
```

### 2. Пользовательский автозагрузчик

Определён в `/system/config/autoload.php`, регистрируется через `spl_autoload_register()`.

| Префикс | Шаблон пути | Пример |
|--------|--------------|--------|
| `cms` | `/system/core/{name}.php` | `cmsCore` → `core.php` |
| `model` | `/system/controllers/{component}/model.php` | `modelShop` → `shop/model.php` |
| `field` | `/system/fields/{name}.php` | `fieldDate` → `date.php` |
| `widget` | `/system/widgets/{name}/widget.php` | `widgetMenu` → `menu/widget.php` |

## 6.6. Иерархия базовых классов

Все компоненты наследуются от абстрактных базовых классов:

```
cmsController
├── cmsFrontend   → фронтенд-контроллеры
└── cmsBackend    → админка

cmsModel          → все модели

cmsWidget         → все виджеты

cmsFormField      → все типы полей форм
```

Это обеспечивает:
- Единый интерфейс для всех контроллеров (`$this->db`, `$this->user`, `$this->cache`)
- Возможность переопределения поведения через наследование
- Безопасное расширение без модификации ядра

На следующей диаграмме показаны отношения наследования между базовыми классами, определяющими структуру фреймворка.

## 6.7. Интеграция компонентов

Компоненты интегрируются с ядром через четко определенные точки расширения и внедрение зависимостей.

<img src="https://github.com/DSTGlobal/DST-Platform/blob/main/images/32.png" alt="DST Platform">

Диаграмма: Интеграция компонентов с основными сервисами

Каждый компонент — автономный модуль в `/system/controllers/{name}/`.

### Типичная структура
```
/system/controllers/shop/
├── controller.php          # class shop extends cmsFrontend
├── model.php              # class modelShop extends cmsModel
├── backend/
│   ├── controller.php     # class backendShop extends cmsBackend
│   └── model.php          # class modelBackendShop extends modelShop
├── widgets/
│   └── cart/
│       ├── widget.php     # class shopCart extends cmsWidget
│       └── widget.tpl.php
└── hooks.php              # обработчики событий
```

### Доступ к сервисам
Внутри контроллера или модели:

```php
$this->db;        // cmsDatabase
$this->config;    // cmsConfig
$this->user;      // cmsUser
$this->cache;     // cmsCache
$this->events;    // cmsEventsManager
```

Эти свойства автоматически внедряются через `cmsController::__construct()`.

## 6.8. Вспомогательные библиотеки

В процессе начальной загрузки загружается несколько вспомогательных библиотек, предоставляющих служебные функции, используемые во всем приложении.

На этапе загрузки подключаются глобальные утилиты:

| Библиотека | Файл | Назначение |
|-----------|------|------------|
| `html.helper` | `/system/libs/html.helper.php` | Генерация и экранирование HTML |
| `strings.helper` | `/system/libs/strings.helper.php` | Работа со строками (slug, trim) |
| `files.helper` | `/system/libs/files.helper.php` | Операции с файловой системой |
| `spyc.class` | `/system/libs/spyc.class.php` | Парсинг YAML |

Функции из этих файлов доступны глобально без создания объектов.

Библиотеки загружаются cmsCore::loadLib() и предоставляют процедурные вспомогательные функции, дополняющие основные объектно-ориентированные классы.

## 6.9. Режимы работы и отладка

Система обеспечивает два режима работы, управляемых следующими параметрами cmsConfig:

<img src="https://github.com/DSTGlobal/DST-Platform/blob/main/images/33.png" alt="DST Platform">

Диаграмма: Схема настройки режима отладки

Поведение системы зависит от параметра `debug` в `config.php`:

| Режим | `debug = false` (production) | `debug = true` (development) |
|-------|-------------------------------|------------------------------|
| Ошибки PHP | Подавлены (`error_reporting(0)`) | Отображаются (`display_errors = 1`) |
| SQL-запросы | Не логируются | Логируются в `cmsDebugging` |
| Профилирование | Отключено | Включено (время, память) |
| Кэш шаблонов | Включён | Может быть отключён |

Рекомендуется **никогда не включать отладку в production**.

## 6.10. Управление сессиями и часовым поясом

Сессия инициализируется только если определена константа `SESSION_START` (в `index.php`, но не в `cron_*.php`).

Особенности:
- Домен cookie берётся из `config.php`
- Часовой пояс пользователя сохраняется в сессии
- Если задан, он **переопределяет** системный `time_zone` на время запроса
- После этого вызывается `date_default_timezone_set()`

Это позволяет поддерживать персонализированный временной контекст без изменения глобальной конфигурации.

## 6.11. Подключение к базе данных

Процесс подключения к базе данных включает обработку ошибок:

<img src="https://github.com/DSTGlobal/DST-Platform/blob/main/images/34.png" alt="DST Platform">

Диаграмма: Проверка подключения к базе данных

Выполняется через `$core->connectDB()`. При ошибке:
1. Загружаются языковые файлы
2. Отображается локализованная страница ошибки
3. Выполнение прерывается

Подключение использует **единственный экземпляр** `cmsDatabase`, который:
- Поддерживает подготовленные выражения
- Предоставляет query builder
- Управляет транзакциями
- Обеспечивает повторное использование соединения

## 6.12. Инициализация кэша

Запускается сразу после подключения к БД:

```php
cmsCache::getInstance()->start();
```

Поддерживаемые бэкенды (в порядке приоритета):
- Redis (`ext-redis`)
- Memcached (`ext-memcached`)
- APCu (`ext-apcu`)
- Файлы (`/cache/`)

Конфигурация берётся из `config.php` → секция `'cache'`.

Система кэширования доступна всем компонентам через $this->cache контроллеры или напрямую через cmsCache::getInstance().

## 6.13. Событие `core_start`

Первое системное событие, вызываемое после инициализации основных сервисов:

```php
cmsEventsManager::hook('core_start');
```

Используется компонентами для:
- Проверки миграций БД
- Подогрева кэша
- Инициализации внешних SDK
- Регистрации кастомных обработчиков ошибок

Обработчик определяется в `hooks.php`:

```php
// /system/controllers/search/hooks.php
class search {
    public function onCoreStart() {
        // инициализация поискового индекса
    }
}
```

## 6.14. Локализация

На финальном этапе загружаются языковые файлы:

```php
cmsCore::loadLanguage();
```

Процесс:
1. Загрузка массивов из `/system/languages/{locale}/`
2. Установка локали PHP: `setlocale(LC_TIME, ...)`
3. Настройка локали MySQL для сообщений об ошибках

Языковые строки доступны через глобальный массив `LANG`:

```php
echo LANG['USER_LOGIN']; // "Войти"
```

## 6.15. Архитектурные принципы

| Принцип | Реализация | Выгода |
|--------|------------|--------|
| **Единая ответственность** | Каждый класс решает одну задачу | Простота поддержки и тестирования |
| **Соглашение вместо конфигурации** | Автозагрузка по именам | Минимум boilerplate-кода |
| **Ленивая инициализация** | Сервисы создаются при первом обращении | Экономия ресурсов |
| **Внедрение зависимостей** | `$this->db`, `$this->cache` в контроллерах | Тестируемость, гибкость |
| **Слабая связанность** | События вместо прямых вызовов | Расширяемость без модификации ядра |
| **Единое ядро для двух доменов** | Социальный + бизнес через одни сервисы | Гибридные сценарии (маркетплейсы с отзывами) |

## 6.16. Заключение

Базовая архитектура DST Platform обеспечивает:
- **Стабильность** через строгую последовательность инициализации
- **Расширяемость** через события и наследование
- **Производительность** через кэширование и ленивую загрузку
- **Безопасность** через централизованную инициализацию и санитизацию
- **Гибкость** через поддержку двух доменов в едином ядре

Эта основа позволяет эффективно разрабатывать как простые CMS-сайты, так и сложные enterprise-платформы.
