# 4. Разработка на DST Platform

DST Platform спроектирована для расширения: ядро не модифицируется, а вся кастомизация выполняется через три уровня разработки — от конфигурации без кода до компонентов с полным контролем над SQL. Разработчику доступны открытый исходный код, техническая документация, REST API и полный набор инструментов прямо в административной панели. Проект можно вести силами IT-отдела заказчика, стороннего подрядчика или команды DST Global — без привязки к вендору.

---

## 4.1. Философия разработки: три уровня, один континуум

DST Platform отказывается от дихотомии «простая CMS против сложного фреймворка»: функциональность создаётся ровно на том уровне сложности, который требуется задаче, и эволюционирует между уровнями по мере роста проекта.

**Уровень 1. Конфигурация (без кода).** Типы контента, формы и шаблоны отображения создаются через административный интерфейс с использованием универсального компонента `content`. Созданная сущность сразу получает админку, фронтенд, SEO, кэширование, поиск и права доступа. Подходит для типовых сущностей — статей, новостей, каталогов, портфолио, базы знаний, объявлений.

**Уровень 2. Расширение.** Кастомизация существующей логики через подписку на события (`cmsEventsManager`) и наследование классов — моделей, контроллеров, виджетов. Ядро и чужие компоненты не правятся, но их поведение меняется под специфику заказчика.

**Уровень 3. Разработка.** Полноценные компоненты с нуля в `/system/controllers/{name}/`: собственная бизнес-логика, оптимизированные SQL-запросы, API-эндпоинты, нестандартные интерфейсы. Для сложной логики — платежи, глубокие интеграции, уникальные процессы.

**Континуум, а не выбор один раз.** Типовой сценарий: начать с генератора — получить работающий CRUD с админкой и фронтендом — и затем расширять кодом по мере необходимости: кастомный контроллер для нестандартных действий, расширение модели под сложную выборку, хуки для интеграции с другими компонентами. Между уровнями нет принципиальной границы: код уровня 2 и 3 может работать поверх сущности, созданной декларативно, и наоборот.

**Когда какой уровень:**

| Задача | Уровень | Примеры из практики |
|--------|---------|---------------------|
| Типовая CRUD-сущность с каталогом | Декларативный | База знаний, каталог оборудования, портфолио |
| Изменить поведение существующего компонента | Хуки и наследование | Своя логика оформления заказов, авторасчёт статусов |
| Связать компоненты без их правки | Хуки | Обработка заказов реагирует на события магазина |
| Новая бизнес-логика, платежи, API | Императивный | Модуль оплаты, обмен с ERP, нестандартный личный кабинет |

## 4.2. Инструментарий и материалы

- **REST API** — компонент `api` для мобильных приложений и внешних интеграций: работа с сущностями платформы через эндпоинты без обращения к внутреннему коду.
- **Техническая документация** — описание ядра, компонентов, моделей, шаблонов, хуков и структуры файловой системы; поддерживается в актуальном состоянии.
- **Открытый исходный код** — официальный репозиторий [github.com/DSTGlobal](https://github.com/DSTGlobal). Разработка ведётся в рамках стандартных соглашений платформы: компонентная архитектура, REST API и система хуков.
- **Готовые примеры интеграций** — модули для платёжных систем (ЮKassa, Robokassa, Т-Банк), служб доставки (CDEK и другие), картографии, верификации, рассылок, аналитики — в составе коробочных решений и каталога дополнений.
- **Каталог дополнений** — расширение функциональности готовыми модулями; для нестандартных задач модуль разрабатывается силами DST Global или IT-команды заказчика.

## 4.3. Инструменты разработчика в административной панели

Полное управление проектом — из одной панели, без набора внешних утилит:

- **Генератор компонентов** — каркас нового компонента создаётся автоматически: структура файлов, стандартные контроллеры и модель.
- **Встроенный FTP-клиент и файловый менеджер** — работа с файлами проекта прямо из панели.
- **Администрирование базы данных** — просмотр и управление таблицами без сторонних клиентов.
- **SSH/SFTP-доступ и почтовый сервер** — управление окружением и исходящими письмами.
- **Отладка, мониторинг, логирование** — диагностика и наблюдение за состоянием системы в процессе разработки.

## 4.4. Работа с компонентами

Компонент — автономный функциональный модуль с чёткой структурой файлов:

- Расположение: `/system/controllers/{component}/`.
- Состав: `frontend.php` (публичная часть), `backend.php` (административная часть), `model.php` (данные), `hooks.php` (обработчики событий), `widgets/` (виджеты компонента), `backend/` (файлы админ-контроллеров, форм, моделей).
- Не обязательно все части: компонент может быть full-stack, headless/service (только модель — для API и служебной логики), event handler (только обработчики хуков) — или любой комбинацией.
- **Именование:** латинские буквы нижнего регистра, цифры, подчёркивание; минимум 3 символа, начинается с буквы.
- Для обработчиков событий рекомендуется выбирать имена, не конфликтующие с существующими компонентами (например, `content_hooks`) — «чистые» имена остаются свободными для полноценных компонентов, если они появятся в проекте.

---

## 4.5. Контроллеры

Контроллер — центральный элемент компонента, точка входа для логики. Он отвечает за:

- приём HTTP-запросов (GET, POST и других);
- валидацию входных данных;
- вызов методов модели;
- подготовку данных для отображения;
- возврат ответа (HTML, JSON, редирект и так далее).

Каждый компонент может иметь два контроллера:

- **Frontend** — для публичной части сайта;
- **Backend** — для административной панели.

Контроллер не пишет прямые SQL-запросы: он обращается к методам модели (`getItems()`, `saveItem()` и другим). Это обеспечивает безопасность, централизацию логики данных и возможность замены СУБД без изменения контроллеров.

---

## 4.6. Работа с моделями

Модель наследуется от `cmsModel` и инкапсулирует работу с данными компонента:

- Расположение: `/system/controllers/{component}/model.php`; имя класса — `model{Component}`.
- Бэкенд-модель: `/system/controllers/{component}/backend/model.php`, класс `modelBackend{Component}` (с версии 2.14.2).
- Основные методы: `insert()`, `update()`, `delete()`, `getItem()`, `getItems()`, `filter()` — с автоматической фильтрацией входных данных и защитой от SQL-инъекций через подготовленные выражения.
- Для сложных выборок доступны прямые оптимизированные SQL-запросы (см. «Технологии и архитектура», раздел о работе с данными).

> **Модель — не ORM.** Модель DST Platform — это не объект отдельной записи, а утилитарный класс, предоставляющий методы для работы с таблицами БД. ORM (Eloquent, Doctrine и подобные) не используется: прозрачность запросов и полный контроль над SQL сохраняются.

Пример структуры модели и наследования:

```php
// /system/controllers/shop/model.php
class modelShop extends cmsModel {
    // Собственные методы модели
}

// /system/controllers/partner/model.php
class modelPartner extends modelShop {
    // Все методы modelShop + собственные методы
}
```

Пример работы через Query Builder (в контроллере):

```php
$products = $this->model->select('shop_products')
    ->filterEqual('category_id', $categoryId)
    ->filterEqual('is_published', 1)
    ->orderBy('date_pub', 'DESC')
    ->limit(20)
    ->getItems();
```

## 4.7. Работа с шаблонами

- Шаблоны в `/templates/{theme}/`; файлы — `.tpl.php`; наследование тем через `inherit.php`.
- **Переопределение без копирования:** дочерняя тема переопределяет только нужные файлы (TPL, CSS, JS), остальные берутся из родительской. Отдельные страницы переопределяются и по URL, и по ID категории.
- Подключение CSS/JS — через методы `cmsTemplate` (см. 4.8); управление мета-тегами — в контроллерах, вывод в `head()`.
- Логика данных строго разделена с шаблонами: только HTML-разметка и минимальный PHP (условия, циклы, форматирование).

**Методы макета.** Внутри `main.tpl.php` используются:

```php
$this->renderHead() / $this->head()   // вывод CSS, JS, мета
$this->body()                          // основной контент (результат контроллера)
$this->widgets('position_name')        // виджеты в указанной позиции
$this->hasWidgetsOn('position_name')   // проверка наличия виджетов
cmsUser::getSessionMessages()          // системные уведомления
$this->breadcrumbs()                   // навигационная цепочка
```

**Справочник ключевых файлов шаблона:**

| Файл | За что отвечает |
|------|-----------------|
| `/main.tpl.php` | Общий каркас сайта |

| `/controllers/shop/index.tpl.php` | Витрина магазина |

| `/controllers/shop/compare.tpl.php` | Сравнение товаров |
| `/controllers/users/profile_template.tpl.php` | Обёртка профиля (меню ЛК) |
| `/controllers/users/profile/orders.tpl.php` | История заказов |

## 4.8. Работа с CSS/JS (assets)

Ресурсы подключаются через методы `cmsTemplate` — с учётом наследования темы, объединения и минификации:

```php
$this->addMainCSS('templates/mytheme/css/style.css'); // в <head>, участвует в слиянии
$this->addCSS('templates/mytheme/css/custom.css');    // в конец списка стилей
$this->addControllerCSS('styles.css', 'shop');        // автоматический поиск CSS компонента
$this->addMainJS('templates/mytheme/js/main.js');     // в <head>
$this->addJS('templates/mytheme/js/custom.js');       // перед </body>
```

- `addControllerCSS('styles.css', 'component_name')` — автоматический поиск CSS-файла компонента с учётом наследования темы.
- `getTplFilePath('js/script.js')` — корректный путь с учётом наследования.
- `getLangJS(['LANG_YES', 'LANG_NO'])` — передача языковых констант из PHP в JS-переменные.
- Встроенные настройки объединения и минификации CSS/JS сокращают количество HTTP-запросов без сторонних сборщиков.

## 4.9. SEO-методы контроллера

Мета-данные страниц задаются в контроллерах:

```php
$this->setPageTitle('Карточка товара');
$this->setMeta('keywords', $item['tags']);
$this->setPageDescription($item['description']);
$this->addHead('<link rel="canonical" href="' . $item['url'] . '">');
```

`addHead()` поддерживает Open Graph, canonical и произвольные теги; шаблоны мета-тегов для динамических страниц (карточки товаров, категории) настраиваются без кода.

## 4.10. Расширение через хуки

Хуки позволяют внедрять логику в жизненный цикл других компонентов без их прямой правки:

```php
// В контроллере или модели инициируется событие
$data = cmsEventsManager::hook('my_component_before_save', $data);

// В hooks.php другого компонента
public function hookMyComponentBeforeSave($data) {
    // Модификация данных: валидация, enrichment, побочные действия
    return $data;
}
```

- Имя метода-обработчика соответствует имени события: `content_before_update` → `hookContentBeforeUpdate`.
- События инициируются компонентами платформы на ключевых этапах жизненного цикла данных — подписка доступна из любого компонента.
- Хуки возвращают изменённые данные в исходный поток выполнения — поведение системы меняется без правки ядра или чужого компонента.

## 4.11. Создание собственных полей

Новые типы полей создаются добавлением класса в `/system/fields/` — например, `fieldColor.php` с классом `fieldColor`. Поля используются в формах и типах контента и наследуют поведение системы: валидация, кэширование, отображение.

---

## 4.12. Автозагрузка и соглашения именования

Платформа использует собственную систему автозагрузки, основанную на соглашениях об именовании и расположении файлов:

| Директория | Префикс имени класса | Пример |
|------------|----------------------|--------|
| `/system/core/` | `cms` | `cmsAction` → `action.php` |
| `/system/fields/` | `field` | `fieldDate` → `date.php` |
| `/system/controllers/NAME/model.php` | `model` | `modelUsers` → `users/model.php` |

Дополнительно поддерживается загрузка классов по пространствам имён (namespaces) — сторонние библиотеки подключаются без конфликтов с классами ядра и компонентов.

Бэкенд-модели (с версии 2.14.2) описываются в `/system/controllers/{component}/backend/model.php` с именем класса `modelBackend{Component}` и наследуются от основной модели.

## 4.13. Рекомендации по разработке

Чек-лист, обеспечивающий поддержку и безопасность проекта на долгой дистанции:

1. **Не изменять ядро** (`/system/core/`). Кастомизация — через хуки, наследование классов и шаблоны: правка ядра осложнит обновления.
2. **Работа с БД** — только через методы `cmsModel` или подготовленные запросы (`$this->db->query($sql, $params)`): защита от SQL-инъекций встроена.
3. **Контроллер не пишет SQL** — прямые запросы должны находиться в модели; контроллер обращается к её методам. Это правило обеспечивает централизацию логики данных.
4. **Входные данные от пользователя** — фильтровать через `cmsRequest::get()`, `cmsRequest::post()` или `$this->request->get()`.
5. **Валидация форм** — через правила (rules) `cmsForm`: правила задаются декларативно для каждого поля — обязательность, формат, диапазон; при нестандартных данных создаётся собственный тип поля (см. 4.11).
6. **Кэширование** — активно использовать `cmsCache` для тяжёлых выборок; продумать TTL по типу данных.
7. **Производительность** — OpCache включён в продакшене; объединение и минификация CSS/JS — через встроенные настройки, без сторонних сборщиков.
8. **Отладка** — инструменты `cmsDebugging`; режим отладки включать только на staging-окружении.
9. **Границы компонентов** — взаимодействие через события, а не прямые вызовы чужих моделей и таблиц.

## 4.14. Интеграции

- **REST API** (компонент `api`) — для мобильных приложений и внешних систем.
- **Готовые модули:** платёжные шлюзы (ЮKassa, Robokassa, Т-Банк), доставка (CDEK и другие), картография, верификация, рассылки, аналитика.
- **Обмен с 1С, CRM, ERP** — типовой обмен реализуется штатными механизмами; кастомизированные конфигурации подключаются после анализа структуры учёта заказчика: согласование схемы обмена, настройка или разработка модуля.
- **Нестандартные системы** — модули интеграции разрабатываются силами DST Global или IT-команды заказчика: исходный код открыт и документирован.

## 4.15. Кто разрабатывает: три сценария

**IT-отдел заказчика.** Полный доступ к коду, документация и инструменты в админке позволяют вести разработку собственными силами — доработки не требуют обращения к вендору.

**Сторонние подрядчики.** Открытый код снимает зависимость от одного исполнителя: при смене команды проект продолжается без потери знаний о системе — структура кода документирована.

**DST Global.** Специалисты компании выполняют доработки и развитие с отчётностью и контролем — см. порядок работ ниже.
