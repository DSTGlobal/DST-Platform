## 9. Система событий и хуков

Этот документ описывает архитектуру событийной коммуникации в DST Platform, реализованную через синглтон `cmsEventsManager`. Система обеспечивает **слабосвязанное взаимодействие компонентов**, позволяя расширять функциональность без модификации исходного кода и поддерживая чёткое разделение ответственности.

Связанные разделы:
- **«Компонентная система»** — организация модулей
- **«Паттерн MVC и жизненный цикл запроса»** — точки интеграции событий
- **«Архитектура планировщика Cron»** — использование хуков в фоновых задачах

---

## 9.1. Архитектурные принципы

Система событий основана на паттерне **Observer** и следует следующим принципам:

| Принцип | Реализация | Выгода |
|--------|------------|--------|
| **Слабая связанность** | Компоненты не знают друг о друге напрямую | Независимая разработка и тестирование |
| **Расширяемость** | Новые компоненты подписываются на существующие события | Добавление функционала без изменения ядра |
| **Конвейер данных** | Данные передаются по цепочке обработчиков | Последовательная модификация (валидация → обогащение → логирование) |
| **Единая точка вызова** | Все события запускаются через `cmsEventsManager::hook()` | Централизованный контроль и отладка |

DST Platform реализует систему событий на основе обработчиков, которая позволяет компонентам:

1. Запускать события в определенных точках жизненного цикла их выполнения.
2. Подписывайтесь на события других компонентов, чтобы расширить или изменить их поведение.
3. Передача данных через цепочки событий, где несколько подписчиков могут обрабатывать их последовательно.
4. Интеграция с запланированными задачами через cron-хуки

Эта архитектура устраняет тесную взаимосвязь между компонентами, обеспечивая при этом мощные точки расширения по всей системе.

## 9.2. Класс `cmsEventsManager`

`cmsEventsManager` — синглтон, управляющий всей системой событий.

### Ответственности
- Автоматическое обнаружение обработчиков в `/system/controllers/{component}/hooks.php`
- Последовательный вызов всех подписчиков события
- Передача и возврат данных по цепочке
- Поддержка как синхронных, так и фоновых (cron) событий

### Инициализация
Создаётся лениво при первом вызове `cmsEventsManager::hook()`.  
Не требует ручной регистрации обработчиков — они обнаруживаются автоматически.

cmsEventsManager класс является синглтоном и управляет всеми запусками событий и выполнением обработчиков в системе. Он расположен по адресу:

system/core/eventsmanager.php

### Обязанности

| Ответственность | Описание |
|----------------|----------|
| **Регистрация на мероприятие** | Загружает файлы-перехватчики из всех включенных компонентов. |
| **Диспетчеризация событий** | При срабатывании события вызывает обработчики у всех подписчиков. |
| **Конвейер обработки данных** | Передаёт данные через цепочку подписчиков, возвращая изменённый результат. |
| **Открытие хука** | Автоматически обнаруживает хуки на основе соглашений об именовании. |

### Инициализация

Инициализация cmsEventsManager происходит во время загрузки системы в рамках инициализации основного фреймворка:

## 9.3. Запуск событий

Любой компонент может инициировать событие:

```php
$result = cmsEventsManager::hook('shop_before_add_item', $item);
```

### Соглашение об именовании событий

| Шаблон | Пример | Время вызова | Типичное использование |
|--------|--------|--------------|------------------------|
| `{component}_before_{action}` | `shop_before_add_item` | До выполнения действия | Валидация, модификация входных данных |
| `{component}_after_{action}` | `shop_after_add_item` | После выполнения | Индексация, уведомления, инвалидация кэша |
| `core_{event}` | `core_start` | На этапе инициализации | Инициализация SDK, проверка миграций |
| `cron_{task}` | `cron_export_products_job` | В фоновых задачах | Экспорт, импорт, генерация фидов |

Имена событий используют **snake_case**.

## 9.4. Подписка на события

Компоненты подписываются на события через файл `hooks.php`.

### Расположение
```
/system/controllers/{component_name}/hooks.php
```

### Соглашение об именовании методов
Метод-обработчик именуется по шаблону:  
`hook` + **PascalCase(имя_события)**

| Событие | Метод-обработчик |
|--------|------------------|
| `shop_before_add_item` | `hookShopBeforeAddItem` |
| `core_start` | `hookCoreStart` |
| `cron_export_products_job` | `hookCronExportProductsJob` |

### Пример файла `hooks.php`
```php
<?php
class search {

    public function hookShopBeforeAddItem($item) {
        // Валидация или модификация
        if (empty($item['title'])) {
            $item['errors'][] = 'Товар должен иметь название';
        }
        return $item; // обязательно вернуть данные
    }

    public function hookShopAfterAddItem($item) {
        // Индексация в поиске
        $this->model->indexProduct($item);
        return $item;
    }
}
```

> **Важно**: метод **всегда должен возвращать** данные (изменённые или нет). Если не вернуть — цепочка прервётся.

## 9.5. Конвейер обработки данных

При срабатывании события данные последовательно проходят через всех подписчиков. Каждый подписчик может изменять данные, и измененная версия передается следующему подписчику.

Диаграмма конвейера обработки данных событий

<img src="https://github.com/DSTGlobal/DST-Platform/blob/main/images/59.png" alt="DST Platform">

При вызове события данные проходят через всех подписчиков **последовательно**:

1. Исходные данные → первый обработчик
2. Результат первого → второй обработчик
3. ... → последний обработчик
4. Финальный результат возвращается вызывающему коду

### Типичные паттерны обработки

| Паттерн | Описание | Пример |
|--------|---------|--------|
| **Валидация** | Проверка корректности данных | Добавление `$data['errors']` |
| **Обогащение** | Добавление вычисляемых полей | `$data['seo_url'] = slugify($data['title'])` |
| **Трансформация** | Изменение формата | Очистка HTML, нормализация цен |
| **Побочные эффекты** | Действия без изменения данных | Отправка email, запись в лог |
| **Инвалидация кэша** | Сброс устаревших данных | `cmsCache::delete('product_' . $id)` |

Важно: независимо от того, возвращает ли метод-перехватчик null что-либо или нет, исходные данные сохраняются. Всегда возвращайте данные (измененные или неизмененные), чтобы поддерживать работоспособность конвейера.

## 9.6. Интеграция с жизненным циклом запроса

События вызываются на ключевых этапах:

| Этап | Событие | Пример использования |
|------|--------|----------------------|
| Инициализация | `core_start` | Загрузка конфигурации, инициализация SDK |
| Перед действием | `{component}_before_{action}` | Проверка прав доступа |
| После действия | `{component}_after_{action}` | Логирование, аналитика |
| Сохранение данных | `content_before_update` | Санитизация, валидация |
| Удаление | `user_before_delete` | Удаление связанных записей |

## 9.7. Крюки Cron

Система cron широко использует обработчики событий для запланированного выполнения задач. Каждый скрипт cron запускает определенный обработчик, на который могут подписаться компоненты.

### Архитектура Крон Хук

<img src="https://github.com/DSTGlobal/DST-Platform/blob/main/images/60.png" alt="DST Platform">

Система cron активно использует события для выполнения задач.

### Универсальный планировщик (`cron.php`)
Читает задачи из БД и вызывает:
```php
$controller->runHook("cron_{$task['hook']}");
```

### Специализированные скрипты
Например, `cron_export.php` вызывает:
```php
cmsEventsManager::hook('cron_export_products_job');
```

### Соглашение об именовании cron-событий
| Скрипт | Событие | Метод-обработчик |
|-------|--------|------------------|
| `cron_export.php` | `cron_export_products_job` | `hookCronExportProductsJob` |
| `cron_partner_import.php` | `cron_partner_import_job` | `hookCronPartnerImportJob` |
| `cron_yml_create.php` | `cron_yml_create_files` | `hookCronYmlCreateFiles` |

Каждый компонент может реализовать свой обработчик, и все они будут вызваны.

### Универсальные и специализированные скрипты Cron

Универсальный планировщик задач (cron.php):

- Конфигурация задач на основе базы данных
- Использует $controller->runHook("cron_{$task['hook']}") шаблон
- Поддерживает динамическое управление задачами через административный интерфейс.

Специализированные скрипты:

- Прямой вызов перехватчика на конкретных контроллерах
- Блокировка на основе файлов для управления параллельным доступом
- Оптимизировано для выполнения приоритетных задач, критически важных с точки зрения производительности.

## 9.8. Межкомпонентная коммуникация

Контроллеры могут как инициировать события, так и подписываться на них. cmsController Базовый класс предоставляет методы для выполнения обработчиков событий.

### Методы перехвата контроллера

<img src="https://github.com/DSTGlobal/DST-Platform/blob/main/images/61.png" alt="DST Platform">

События — **единственный рекомендуемый способ** взаимодействия между компонентами.

### Пример: интеграция `shop` и `search`
1. Компонент `shop` сохраняет товар → вызывает `shop_after_add_item`
2. Компонент `search` слушает это событие → индексирует товар
3. Компонент `notifications` также слушает → отправляет уведомление админу

Никаких прямых вызовов `search::index()` из `shop` — только через событие.

Система событий и хуков обеспечивает слабосвязанное взаимодействие между компонентами, что является ключевым принципом модульной архитектуры DST Platform.

Схема взаимодействия через хуки:

### Ключевые преимущества

| Преимущество | Описание |
|--------------|----------|
| **Слабая связанность** | Компоненты не имеют прямых зависимостей, что позволяет разрабатывать и тестировать их независимо |
| **Расширяемость** | Новые компоненты могут подписываться на существующие события без изменения исходного кода |
| **Тестируемость** | Компоненты можно тестировать изолированно, подменяя или отключая обработчики событий |
| **Удобство поддержки** | Изменения в одном компоненте не требуют модификаций в других, если интерфейс события остаётся прежним |
| **Гибкость** | Функциональность можно включать или отключать, добавляя или удаляя файлы хуков |

## 9.10. Распространенные паттерны хуков

| Паттерн | Описание | Пример метода |
|---------|----------|---------------|
| **Обогащение данных** | Добавление дополнительных полей или вычисляемых значений | `hookProductBeforeDisplay($product)` |

| **Межкомпонентная синхронизация** | Синхронизация данных между компонентами | `hookShopOrderComplete($order)` |

## 9.12. Рекомендации и лучшие практики

### ✅ Делать
- Всегда возвращать данные из обработчика
- Использовать единый метод для одного события
- Документировать побочные эффекты в комментариях
- Валидировать и санитизировать входные данные
- Использовать флаги ошибок вместо исключений

### ❌ Не делать
- Генерировать исключения (прерывают цепочку)
- Предполагать порядок выполнения других хуков
- Выполнять тяжёлые операции без кэширования
- Изменять глобальное состояние вне переданных данных

### Пример хорошего хука
```php
public function hookOrderBeforeCreate($order) {
    // Валидация
    if ($order['total'] <= 0) {
        $order['errors']['total'] = 'Сумма заказа должна быть положительной';
    }

    // Обогащение
    $order['created_at'] = date('Y-m-d H:i:s');

    return $order; // обязательно
}
```

## 9.13. Отладка событий

### Как проверить, вызывается ли хук
Добавьте временную запись в лог:
```php
public function hookShopAfterAddItem($item) {
    error_log('[DEBUG] shop_after_add_item triggered for item ID: ' . $item['id']);
    return $item;
}
```

### Как найти все обработчики события
Выполните поиск по коду:
```bash
grep -r "hookShopAfterAddItem" system/controllers/
```

### Распространённые проблемы

| Проблема | Причина | Решение |
|---------|--------|--------|
| Хук не вызывается | Компонент отключён в админке | Включите компонент в таблице `controllers` |
| Хук не вызывается | Неправильное имя метода | Проверьте PascalCase-преобразование |
| Данные не изменены | Метод не возвращает данные | Добавьте `return $data;` |
| Цепочка прервана | Выброшено исключение | Замените на флаги ошибок |

## 9.14. Заключение

Система событий и хуков в DST Platform:
- Обеспечивает **гибкую и безопасную** интеграцию компонентов
- Поддерживает **расширяемость без модификации ядра**
- Реализует **конвейерную обработку данных** с возможностью валидации, трансформации и побочных эффектов
- Интегрирована как в **HTTP-запросы**, так и в **фоновые задачи**

### Основные выводы:
1. **Централизованное управление**: `cmsEventsManager` координирует запуск всех событий и выполнение обработчиков
2. **Соглашение об именовании**: события — snake_case, обработчики — hookCamelCase
3. **Конвейер обработки**: данные последовательно проходят через всех подписчиков
4. **Слабая связанность**: компоненты взаимодействуют без прямых зависимостей
5. **Интеграция с Cron**: запланированные задачи активно используют хуки

> **Важное правило**: методы-обработчики всегда должны возвращать данные для поддержания целостности конвейера.

Эта система обеспечивает "двойную архитектуру" DST Platform, в которой социальные и бизнес-компоненты беспрепятственно взаимодействуют посредством событий, сохраняя разделение задач и предоставляя мощные точки интеграции.
