## 3.1. Технический профиль

Прозрачный стек без скрытых зависимостей.

PHP 8+, MySQL/MariaDB, MVC и чистая PHP-шаблонизация — стандартные технологии, знакомые любой команде разработки. Ни проприетарных движков, ни компонентов, требующих отдельной экспертизы.

| Параметр | Значение |
|----------|----------|
| Язык разработки | PHP |
| Рекомендуемая версия | PHP 8+ |
| Режим совместимости | PHP 7+ |
| СУБД | MySQL 8+ / MariaDB 10+ |
| Режим совместимости СУБД | MySQL 5+ / MariaDB |
| Веб-сервер | Apache (mod_rewrite) / NGINX |
| Архитектурный паттерн | MVC (Model-View-Controller) |
| Шаблонизация | Чистый PHP (файлы `.tpl.php`) |
| Кэширование | OpCache, Redis, файловый кэш, CDN |
| Автозагрузка | Собственная система + поддержка namespaces |

Платформа эксплуатируется в двух режимах, определяемых при внедрении в зависимости от инфраструктуры заказчика:

- **Актуальный стек** (PHP 8+, MySQL 8+ / MariaDB 10+) — полная производительность: ряд оптимизаций кэширования и обработки данных задействует возможности PHP 8. Рекомендуется для проектов с ожидаемым ростом нагрузки и стандартной практикой обновления инфраструктуры.
- **Режим совместимости** (PHP 7+, MySQL 5+ / MariaDB) — для организаций, инфраструктура которых ограничена регламентами или техническими условиями: государственный сектор, предприятия с собственными серверными мощностями, действующие среды с давно не обновляемым окружением. Функциональность платформы сохраняется полностью; ограничения касаются только отдельных оптимизаций производительности.

Переход с режима совместимости на актуальный стек выполняется обновлением окружения — без замены платформы и без миграции данных. Целевой режим и конфигурацию сервера специалисты DST Global определяют на этапе внедрения под ожидаемый профиль нагрузки.

## 3.2. Архитектура: четыре уровня

Архитектура DST Platform описывается четырьмя уровнями — от инфраструктуры до ролей пользователей. Каждый уровень решает свою задачу, а связи между ними определены явно. 

```
УРОВЕНЬ 1. ИНФРАСТРУКТУРА
  Домен → Сервер (хостинг/VPS) → DST Platform (ядро + фреймворк) → БД (MySQL / MariaDB)

УРОВЕНЬ 2. ЯДРО И ФРЕЙМВОРК
  Маршрутизация + контроллеры (MVC): Frontend | Backend | Модели | Шаблоны
  Двойственная архитектура (единое ядро): Социальная часть | Бизнес-часть
  Модули (компоненты): контент | пользователи | геолокация | поиск | API | уведомления | и.т.д.

УРОВЕНЬ 3. ГОТОВЫЕ БИЗНЕС-РЕШЕНИЯ
  Интернет-магазин | Маркетплейс | Мультивендор | Мед Центр | LMS | Веб-портал |
  Доска объявлений | CRM | Социальная сеть | Мессенджер

УРОВЕНЬ 4. ПОЛЬЗОВАТЕЛИ
  Администратор | Покупатель | Продавец | Модератор | Преподаватель | Партнёр
```

### Уровень 1. Инфраструктура

Физическая и программная среда функционирования: доменное имя, серверное оборудование и ядро платформы над СУБД. DST Platform спроектирована для эффективного использования ресурсов: типовая конфигурация — один сервер с 8 vCPU и 32 ГБ RAM — стабильно обрабатывает до 400 000 посещений в сутки при пиковой нагрузке 120–150 RPS.\* Это достигнуто за счёт минималистичной архитектуры ядра и отсутствия избыточных прослоек, характерных для фреймворков общего назначения.

База данных хранит все сущности системы. Денормализованная структура таблиц и предрасчёт агрегатов (количество отзывов, средний рейтинг) сокращают число JOIN-операций: время ответа страниц каталога в условиях реальной нагрузки — 50–200 мс.\*

### Уровень 2. Ядро и фреймворк

- **Маршрутизация и контроллеры (MVC)** — frontend-контроллеры обрабатывают публичные запросы, backend-контроллеры обеспечивают административный интерфейс; модели инкапсулируют работу с данными; шаблоны отвечают за представление.
- **Двойственная архитектура** — единое ядро объединяет социальный домен (группы, лента, стена, комментарии, форум, сообщения) и бизнес-домен (магазин, маркетплейс, заказы, доставка, платежи, CRM, тендеры, LMS). Обе части используют общие подсистемы: пользователей, прав доступа и событий. Гибридные экосистемы — например, маркетплейс с обсуждениями товаров и рейтингами продавцов — строятся без стыковки разных систем через API, что снижает латентность и упрощает отладку.
- **Модульная структура** — каждый компонент владеет своими таблицами и обращается к данным других через события, а не прямые вызовы. Новый функционал (например, модуль платежей) подключается без изменения кода существующих компонентов (например, модуля заказов). При возникновении измеримой необходимости любой модуль выделяется в отдельный сервис с минимальными изменениями — границы и интерфейсы уже определены.

### Уровень 3. Готовые бизнес-решения

Над ядром и модулями надстраивается портфель из десяти коробочных продуктов — специализированных конфигураций модулей с предустановленными настройками, шаблонами и бизнес-процессами. Каждое решение использует общие базовые модули (пользователи, права, геолокация, поиск, уведомления) и наследует возможности платформы: SEO-управление, многоуровневое кэширование, права доступа, работу с высокими нагрузками. Развёртывание — от нескольких дней.

### Уровень 4. Пользователи

Роли взаимодействуют с системой после развёртывания и различаются наборами прав доступа и сценариями использования: **администратор** (управление платформой через backend), **покупатель** (каталог, заказы, личный кабинет), **продавец** (витрина, товары, заказы через кабинет `partner`), **модератор** (проверка контента), **преподаватель** (курсы и тесты в LMS), **партнёр** (внешние интеграции через API). Все роли используют единую систему аутентификации и авторизации.

## 3.3. Жизненный цикл запроса

Предсказуемый путь запроса и слабая связанность компонентов.

Каждый HTTP-запрос проходит явную последовательность шагов — от роутера до шаблона, один запрос соответствует одному контексту выполнения. Компоненты взаимодействуют через систему событий: расширение функциональности не требует правки ядра.

Каждое обращение пользователя проходит предсказуемую последовательность шагов:

1. Запускается точка входа — файл `index.php`.
2. Роутер анализирует URL и определяет запрошенные компонент и действие (action); ЧПУ-адреса реализуются правилами перенаправления без потери производительности.
3. Вызывается соответствующий контроллер — frontend или backend.
4. Контроллер получает параметры запроса (URL, POST-данные и другие).
5. При необходимости обращается к модели для получения или сохранения данных.
6. Обрабатывает данные и подготавливает их к выводу.
7. Передаёт данные в шаблон.
8. Шаблон генерирует HTML и возвращает его пользователю.

Бизнес-логика сосредоточена в контроллерах — это упрощает отладку и поддержку: один HTTP-запрос соответствует одному контексту выполнения, а не цепочке сервисов.

| `cmsUser` | Работа с текущим пользователем |
| `cmsCache`, `cmsCacheFiles`, `cmsCacheMemory` | Абстракция кэширования: файловый кэш и Memcached / Redis (бэкенд настраивается) |

## 3.5. Компоненты и модули

- **Компоненты** располагаются в `/system/controllers/{name}/`. Имя компонента — латинские буквы нижнего регистра, цифры и подчёркивание; начинается с буквы, минимальная длина — 3 символа.
- **Типы компонентов:** full-stack (frontend + backend + модель), headless/service (только модель — для API и служебной логики), event handler (только обработчики хуков) — или любая комбинация этих частей.

### Автозагрузка классов

Платформа использует собственную систему автозагрузки, основанную на соглашениях об именовании и расположении файлов:

| Директория | Префикс имени класса | Пример |
|---|---|---|
| `/system/core/` | `cms` | `cmsAction` → `action.php` |
| `/system/fields/` | `field` | `fieldDate` → `date.php` |
| `/system/controllers/NAME/model.php` | `model` | `modelUsers` → `users/model.php` |

Дополнительно поддерживается загрузка классов по пространствам имён (namespaces) — сторонние библиотеки подключаются без конфликтов с ядром и с использованием современных практик PHP-разработки.

### Именование компонентов-обработчиков событий

Если компонент создаётся только для обработки событий (хуков), рекомендуется выбирать имя, которое не конфликтует с существующими компонентами и не предполагает будущего расширения до полноценного frontend/backend. Например, вместо `content` лучше использовать `content_hooks` или `myproject_content_listener` — «чистые» имена остаются свободными для полноценных компонентов, если они появятся в проекте.

- **Модули (виджеты)** — независимые блоки контента в зонах страницы (header, sidebar, footer): общие (`/system/widgets/`) и виджеты компонентов (`/system/controllers/{component}/widgets/`). Каждый виджет состоит из PHP-класса (логика) и TPL-файла (шаблон).

## 3.6. Шаблоны и наследование

- Шаблоны хранятся в `/templates/{theme_name}/`; файлы шаблонов — `.tpl.php`.
- **Наследование тем** через `inherit.php`: дочерняя тема переопределяет только необходимые файлы (TPL, CSS, JS), остальные берутся из родительской — обновление базовой темы не затрагивает кастомизации.
- **Подключение ресурсов** через методы `cmsTemplate` (`addMainCSS`, `addCSS`, `addMainJS`, `addJS`) с объединением и минификацией CSS/JS; `getTplFilePath` учитывает наследование темы.

- **Подключение ресурсов** через методы `cmsTemplate`:
  - `addMainCSS()` — стили в `<head>`, участвуют в объединении и минификации;
  - `addCSS()` — стили в конец списка;
  - `addControllerCSS('styles.css', 'component_name')` — автоматический поиск CSS-файла компонента;
  - `addMainJS()` — скрипты в `<head>`;
  - `addJS()` — скрипты перед закрывающим `</body>`;
  - `getTplFilePath()` — путь к файлу с учётом наследования темы.

Если список методов в черновике оформлен не как вложенный перечень, а строкой — можно добавить `addControllerCSS` отдельным предложением: «Для стилей компонентов предусмотрен `addControllerCSS('styles.css', 'component_name')` — автоматический поиск CSS-файла компонента».

- **Управление мета-данными** из контроллеров: `setPageTitle()`, `setMeta()`, `setPageDescription()`, `addHead()` (Open Graph, canonical и произвольные теги).
- Шаблоны содержат только HTML-разметку и минимальный PHP (условия, циклы, форматирование) — логика данных строго разделена с контроллерами и моделями.

## 3.7. Система событий (хуки)

`cmsEventsManager` позволяет компонентам реагировать на действия других компонентов без прямой правки кода:

```php
// Инициировать событие (в контроллере или модели)
$updated_data = cmsEventsManager::hook('content_before_update', $item);

// Подписаться на событие (в hooks.php компонента)
public function hookContentBeforeUpdate($item) {
    $item['modified_by'] = cmsUser::getInstance()->id;
    return $item;
}
```

Такое взаимодействие даёт три эффекта: слабую связанность компонентов, расширение функциональности без изменения ядра и готовность к выделению модулей в отдельные сервисы — подписку на событие при необходимости заменяет HTTP-вызов без переписывания логики.

## 3.8. Работа с данными: контролируемый SQL вместо тяжёлого ORM

DST Platform сознательно не использует классический ORM (Eloquent, Doctrine и подобные). Причины практические:

- ORM порождает неоптимальные запросы: при загрузке списка товаров с изображениями, ценами и атрибутами типовой ORM генерирует 4 и более отдельных запроса, тогда как правильно написанный SQL с JOIN и GROUP BY выполняется за один проход.
- На каталоге из 5 млн товаров разница становится критической: на одинаковой конфигурации (8 vCPU, 32 ГБ RAM) типовые ORM-стеки выдают 12–60 RPS в зависимости от ORM-стека (Magento 2 — 12–15, Laravel — 45–60); DST Platform — 180–220 RPS при ответе 200 мс.\*

- Отказ от ORM даёт полный контроль над планом выполнения запросов, позволяет использовать оконные функции, подзапросы и денормализацию — критично для высоконагруженных систем.

**Пример эффекта на списке из 50 товаров:** типовой ORM выполняет 4 запроса с затратами времени 120–180 мс и памятью 2,5–5 МБ; прямой SQL в DST Platform — один запрос за 40–60 мс при памяти 0,5–1 МБ.\*

**Трёхуровневая стратегия доступа к данным:**

1. **Query Builder** — для типовых CRUD-операций: удобство и автоматическая защита от SQL-инъекций.
2. **Прямой SQL** — для сложных JOIN, подзапросов и агрегаций: контроль и производительность.
3. **Денормализация + кэширование** — для критических по производительности участков: предрасчёт агрегатов (например, количества отзывов и среднего рейтинга) и хранение в Redis и CDN.

Модель (`cmsModel`) обеспечивает автоматическую фильтрацию и валидацию входящих данных, защиту от SQL-инъекций через подготовленные выражения и поддержку событий `beforeSave`, `afterSave` и других.

## 3.9. Производительность и кэширование

Пять уровней кэширования:

| Уровень | Что кэшируется | Время жизни |
|---------|----------------|-------------|
| 1. OpCache | Скомпилированный байткод PHP | Постоянно (в памяти) до перезапуска PHP-FPM / сброса кэша |
| 2. Application Cache | Результаты внутри одного запроса | Один запрос |
| 3. Redis | Списки товаров — 10 мин; карточки — 1 час; статические данные — 24 часа | По типу данных |
| 4. Page Cache | HTML-фрагменты — 30 мин; целые страницы — 5 мин | По типу контента |
| 5. CDN | Статика и HTML на периферийных узлах | До 24 часов |

Эффект: cache hit rate 92–95 % — база данных получает до 5–8 % трафика; латентность кэшированных запросов — менее 10 мс.\*

Инфраструктура проекта: приложение — 1 сервер (8 vCPU, 32 ГБ RAM, NVMe); БД — master (8 vCPU, 64 ГБ) + 2 реплики для чтения; Redis (2 vCPU, 8 ГБ); CDN CloudFlare. Стоимость — порядка $650 в месяц. ## 3.12. Архитектурные принципы

Платформа следует прагматичному инженерному подходу: каждое решение обосновано измеримыми показателями, а не технологическими трендами.

**1. Модульный монолит как стартовая точка.** Единое развёртывание, жёсткие границы модулей (bounded contexts), слабая связанность через события. Внутренние вызовы выполняются на уровне методов — наносекунды вместо сетевых миллисекунд; транзакции поддерживаются средствами СУБД (ACID), что критично для коммерческих операций. Экономическое следствие: 400 000 посещений в сутки обрабатываются одним сервером ($200–300/мес), тогда как микросервисный аналог на этой нагрузке требует кластера оркестрации ($1 200–1 500/мес).\*

**2. Отказ от тяжёлого ORM в пользу контролируемого SQL.** Предсказуемый план выполнения запросов, оконные функции и денормализация доступны напрямую. См. раздел 3.8 — включая количественный эффект.

**3. Минималистичный фреймворк без избыточных прослоек.** Накладные расходы на пустой запрос — 3–8 мс против 25–35 мс у универсальных фреймворков; базовое потребление памяти — 5–8 МБ против 15–25 МБ. Один сервер обрабатывает в 2–3 раза больше запросов при той же вычислительной мощности.\*

**4. Принцип отложенной сложности.** Архитектура эволюционирует поэтапно: MVP с минимальными абстракциями → архитектурная дисциплина (границы модулей, событийная интеграция, инкапсуляция данных) → избирательное усложнение только при измеримых триггерах. Это исключает преждевременные архитектурные усложнения, которые по оценке DST Global — около 90 % случаев, и в то же время готовит систему к эволюции: границы модулей и события определены с первого дня.

**5. Многоуровневое кэширование как основа производительности.** Пять уровней кэша (раздел 3.9) снижают нагрузку на БД до долей процента трафика и делают производительность предсказуемой при пиковых нагрузках.

## 3.13. Отложенная сложность: триггеры для архитектурного усложнения

Усложнение инфраструктуры и декомпозиция в DST Platform допускаются по измеримым основаниям:

| Триггер | Метрика | Порог | Действие |
|---------|---------|-------|----------|
| Нагрузка модуля | Средняя загрузка CPU | > 70 % постоянно | Вертикальное → горизонтальное масштабирование |
| Латентность | 95-й перцентиль | > 500 мс | Профилирование → оптимизация узких мест |
| Кодовая база | Строк кода на модуль | > 10 000 | Рефакторинг → декомпозиция |
| Частота релизов | Релизов в неделю | > 10 | Выделение часто меняющихся модулей |
| Организационные границы | Разработчиков на модуль | > 8–10 | Разделение по командам |

Отдельное обоснование — нормативные требования к изоляции (например, обработка платежей в изолированном контуре). Для критических проектов предусмотрены архитектура высокой доступности, резервирование узлов, глубокая оптимизация БД и S3-совместимое хранилище (редакция Enterprise).

## 3.14. Операционный контур: DevOps и сопровождение

Производительность поддерживается процессами, а не только архитектурой:

- **Развёртывание и релизы:** предсказуемые атомарные деплои без оркестрации N сервисов; CI/CD, контейнеризация и оркестрация подключаются по мере необходимости (в рамках услуг DevOps DST Global).
- **Мониторинг:** метрики технического здоровья в административной панели — время отклика, доступность сервиса, cache hit rate, нагрузка сервера, версия PHP и СУБД, лимиты памяти; алертинг при отклонениях от целевых значений (редакции Премиум и Enterprise).
- **Высокая доступность:** резервирование узлов, репликация БД, регламенты реагирования на инциденты — для проектов с непрерывными бизнес-операциями.
- **Данные:** резервное копирование БД и файлов, S3-совместимое хранилище (Enterprise).
