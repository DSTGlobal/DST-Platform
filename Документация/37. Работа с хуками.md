# 37. Работа с хуками

Этот раздел представляет собой практическое руководство для разработчиков по созданию и использованию хуков в DST Platform. Хуки позволяют расширять функциональность системы без модификации ядра через событийную архитектуру на базе `cmsEventsManager`. Все операции выполняются в рамках принципа слабой связанности компонентов.

Для понимания архитектурных основ см. раздел *«Система событий и хуков»*. Инструкции по интеграции хуков в фоновые задачи — в разделе *«Создание запланированных задач»*.

---

## 37.1. Обзор системы хуков

Система хуков DST Platform обеспечивает расширяемость через именованные точки интеграции, где компоненты могут внедрять логику без прямых зависимостей. При вызове события все зарегистрированные обработчики выполняются последовательно, формируя конвейер обработки данных.

| Аспект | Реализация |
|--------|------------|
| **Класс управления** | `cmsEventsManager` (`/system/core/eventsmanager.php`) |
| **Расположение обработчиков** | `/system/controllers/{component}/hooks.php` |
| **Соглашение об именовании** | `hook{EventName}()` (camelCase: `hookContentBeforeUpdate`) |
| **Метод вызова** | `cmsEventsManager::hook($event_name, $data)` |
| **Возвращаемые значения** | Обработчики получают данные от предыдущего хука и возвращают модифицированные данные для следующего. При отсутствии изменений — возвращают исходные данные. |

**Типичные сценарии применения:**
- Модификация данных до/после операций (сохранение, удаление)
- Добавление кастомной валидации
- Запуск побочных эффектов: уведомления, логирование, инвалидация кэша
- Интеграция компонентов без прямых вызовов
- Реализация фоновых задач через cron-хуки

## 37.2. Последовательность выполнения хука

<img src="https://github.com/DSTGlobal/DST-Platform/blob/main/images/226.png" alt="Последовательность выполнения хука">

**Этапы обработки:**
1. Компонент инициирует событие через `cmsEventsManager::hook($name, $data)`
2. Система сканирует все активные компоненты на наличие файла `hooks.php`
3. Обработчики вызываются **в алфавитном порядке по имени компонента** (например: `analytics` → `notifications` → `search`)
4. Каждый обработчик получает результат предыдущего; данные передаются по цепочке
5. Финальный результат возвращается инициатору события

> ⚠️ **Важно:** Не полагайтесь на порядок выполнения для критической логики. Каждый хук должен работать автономно. Избегайте генерации исключений — используйте флаги ошибок в данных (см. раздел 37.14).

## 37.3. Создание обработчиков хуков

### Структура файла
```
/system/controllers/my_component/
├── controller.php
├── model.php
├── hooks.php          ← Обработчики хуков
└── backend/
```

### Соглашение об именовании методов

Преобразование имени события (`snake_case`) → имени метода (`camelCase`):

| Имя события | Имя метода обработчика |
|-------------|------------------------|
| `content_before_update` | `hookContentBeforeUpdate()` |
| `user_after_login` | `hookUserAfterLogin()` |
| `cron_export_products_job` | `hookCronExportProductsJob()` |
| `shop_order_placed` | `hookShopOrderPlaced()` |

### Пример реализации

```php
// Файл: /system/controllers/audit/hooks.php
class audit extends cmsAction {

    /**
     * Добавление аудит-полей перед сохранением контента
     * @param array $item Данные элемента контента
     * @return array Модифицированные данные
     */
    public function hookContentBeforeUpdate($item) {
        // Добавление служебных полей
        $item['modified_by'] = $this->cms_user->id; // Важно: $this->cms_user (с подчёркиванием)
        $item['modified_timestamp'] = time();
        
        // Валидация бизнес-правил
        if (isset($item['price']) && $item['price'] < 0) {
            $item['price'] = 0;
            $item['_validation_warning'] = 'Цена скорректирована на 0';
        }
        
        return $item; // Обязательный возврат данных
    }
    
    /**
     * Обработка события размещения заказа (побочный эффект)
     * @param array $order Данные заказа
     */
    public function hookShopOrderPlaced($order) {
        $this->sendOrderNotification($order);
        $this->updateSalesStats($order);
        // Возврат не требуется для хуков с побочными эффектами
    }
}
```

## 37.4. Контекст выполнения обработчика

Все классы обработчиков наследуются от `cmsAction`, что предоставляет доступ к ключевым сервисам платформы:

| Свойство | Тип | Назначение |
|----------|-----|------------|
| `$this->cms_core` | `cmsCore` | Доступ к ядру фреймворка |
| `$this->cms_config` | `cmsConfig` | Чтение конфигурации |
| `$this->cms_user` | `cmsUser` | Текущая сессия пользователя |
| `$this->cms_template` | `cmsTemplate` | Работа с шаблонами |
| `$this->model` | `cmsModel` | Экземпляр модели текущего компонента |

## 37.5. Запуск хуков

### Через cmsEventsManager (универсальный способ)

```php
// Простой вызов без данных
cmsEventsManager::hook('user_logged_in');

// Передача одиночного параметра
$item = cmsEventsManager::hook('content_before_update', $item);

// Передача нескольких параметров (как ассоциативный массив)
$result = cmsEventsManager::hook('shop_calculate_price', [
    'product' => $product,
    'quantity' => $quantity,
    'user' => $this->cms_user
]);
```

### Через runHook() контроллера (для cron и внутренних вызовов)

```php
// Выполнение хука конкретного компонента
$controller = cmsCore::getController('shop');
if ($controller && $controller->isEnabled()) {
    $controller->runHook('cron_export_products_job');
}

// Пример из cron.php (строка 88)
$controller->runHook("cron_{$task['hook']}");
```

### Поведение при обработке данных

| Сценарий | Результат |
|----------|-----------|
| Нет зарегистрированных обработчиков | Возвращаются исходные данные |
| Один обработчик | Возвращается результат его работы |
| Несколько обработчиков | Данные передаются по цепочке (алфавитный порядок компонентов) |
| Обработчик вернул `null` | Следующему передаются исходные данные события |
| Обработчик не вернул данные | Следующему передаётся `null` (избегайте такого поведения) |

## 37.6. Соглашения об именовании событий

### Шаблоны именования

| Шаблон | Пример | Назначение |
|--------|--------|------------|
| `{component}_{before\|after}_{action}` | `content_before_save` | Валидация/модификация данных |
| `{component}_{object}_{event}` | `user_profile_updated` | События жизненного цикла |
| `cron_{task_identifier}` | `cron_yml_create_files` | Фоновые задачи |
| `core_{event}` | `core_start` | Системные события инициализации |

### Пары хуков «до/после»

```php
// Хук «до»: модификация и валидация
$item = cmsEventsManager::hook('content_before_save', $item);
if (!empty($item['_validation_error'])) {
    // Обработка ошибки
}

// Выполнение операции
$result = $this->model->saveItem($item);

// Хук «после»: побочные эффекты
cmsEventsManager::hook('content_after_save', $result);
```

## 37.7. Распространённые паттерны использования

### 1. Модификация данных

```php
// В контроллере
$data = cmsEventsManager::hook('product_before_price_update', $data);
$this->model->updatePrice($data);

// В обработчике
public function hookProductBeforePriceUpdate($data) {
    $data['updated_at'] = date('Y-m-d H:i:s');
    $data['updated_by'] = $this->cms_user->id;
    return $data;
}
```

### 2. Валидация с флагами ошибок

```php
public function hookContentBeforeUpdate($item) {
    if (empty($item['title'])) {
        $item['_validation_errors'][] = 'Поле "Заголовок" обязательно для заполнения';
    }
    if (!$this->cms_user->isAdmin() && !empty($item['is_featured'])) {
        $item['is_featured'] = false;
        $item['_validation_warnings'][] = 'Поле "Рекомендуемое" доступно только администраторам';
    }
    return $item; // Всегда возвращаем данные
}
```

### 3. Побочные эффекты (без модификации данных)

```php
public function hookShopOrderPlaced($order) {
    $this->sendEmailToCustomer($order);
    $this->notifyVendor($order['vendor_id']);
    $this->logOrderEvent($order['id'], 'placed');
    // Возврат не требуется
}
```

### 4. Cron-задачи

```php
public function hookCronExportProductsJob() {
    $products = $this->model->getProductsForExport();
    $filename = $this->generateXLSX($products);
    $this->uploadToFTP($filename);
    $this->logExport($filename, count($products));
}
```

## 37.8. Обнаружение и регистрация хуков

### Автоматическая регистрация

Система обнаруживает обработчики по следующим правилам:
1. Файл точно назван `hooks.php`
2. Расположен в корне компонента: `/system/controllers/{component}/hooks.php`
3. Класс компонента наследует `cmsAction`
4. Имя класса совпадает с именем компонента (в нижнем регистре)
5. Методы начинаются с префикса `hook` и соответствуют шаблону именования

<img src="https://github.com/DSTGlobal/DST-Platform/blob/main/images/229.png" alt="Процесс обнаружения хуков">

### Ручной вызов для тестирования

```php
// test_hook.php
require_once 'bootstrap.php';

$controller = cmsCore::getController('audit');
if ($controller && $controller->isEnabled()) {
    $test_item = ['id' => 123, 'title' => 'Тест'];
    $result = cmsEventsManager::hook('content_before_update', $test_item);
    print_r($result);
}
```

## 37.9. Передача параметров и обработка возвратов

### Одиночный параметр

```php
// Вызов
$item = cmsEventsManager::hook('content_process', $item);

    $item['processed'] = true;
```

```php
// Вызов
$params = cmsEventsManager::hook('shop_apply_discount', [
    'product' => $product,
    'user' => $this->cms_user,
    'discount_code' => $code

// Обработчик
public function hookShopApplyDiscount($params) {
    if ($this->isValidCode($params['discount_code'])) {

    }
    return $params; // Возвращаем полный массив
}
```

## 37.10. Интеграция с планировщиком Cron

### Схема именования cron-хуков

Все cron-хуки следуют шаблону: `cron_{описательное_имя}`

| Имя хука | Метод обработчика | Назначение |
|----------|-------------------|------------|
| `cron_export_products_job` | `hookCronExportProductsJob()` | Экспорт товаров в XLSX |
| `cron_yml_create_files` | `hookCronYmlCreateFiles()` | Генерация YML-фида (универсальный) |
| `cron_yml_market_create_files` | `hookCronYmlMarketCreateFiles()` | YML-фид для Яндекс.Маркет |
| `cron_partner_import_job` | `hookCronPartnerImportJob()` | Импорт данных партнёров |
| `cron_set_change_price` | `hookCronSetChangePrice()` | Массовое обновление цен |

### Архитектура выполнения в cron.php

<img src="https://github.com/DSTGlobal/DST-Platform/blob/main/images/231.png" alt="Схема выполнения cron-хуков">

**Ключевые этапы:**
1. Проверка файловой блокировки (предотвращение параллельного запуска)
2. Загрузка контроллера компонента
3. Вызов `$controller->runHook("cron_{$task['hook']}")`
4. Обновление времени последнего выполнения в БД
5. Отключение задачи при критической ошибке (с логированием)

> 💡 **Примечание:** Для ресурсоёмких операций используйте специализированные cron-скрипты (`cron_*.php`), а не универсальный планировщик. Подробнее — в разделе *«Архитектура планировщика Cron»*.

## 37.11. Практические примеры

### Пример 1: Аудит операций с контентом

```php
// /system/controllers/audit/hooks.php
class audit extends cmsAction {
    public function hookContentBeforeAdd($item) {
        $item['created_at'] = date('Y-m-d H:i:s');
        $item['created_by'] = $this->cms_user->id;
        $item['created_ip'] = $_SERVER['REMOTE_ADDR'] ?? 'unknown';
        return $item;
    }
    
    public function hookContentBeforeUpdate($item) {
        $item['updated_at'] = date('Y-m-d H:i:s');
        $item['updated_by'] = $this->cms_user->id;
        return $item;
    }
}
```

### Пример 2: Логирование событий заказов

```php
// /system/controllers/order_logger/hooks.php
class order_logger extends cmsAction {
    public function hookShopOrderPlaced($order) {
        $this->model->insert('order_event_log', [
            'order_id' => $order['id'],
            'event_type' => 'placed',
            'user_id' => $this->cms_user->id,
            'timestamp' => time(),
            'metadata' => json_encode($order)
        ]);
    }
}
```

### Пример 3: Инвалидация кэша

```php
// /system/controllers/cache_manager/hooks.php
class cache_manager extends cmsAction {
    public function hookContentAfterUpdate($item) {
        $cache = cmsCache::getInstance();
        $cache->delete("content_item_{$item['id']}");
        if (!empty($item['category_id'])) {
            $cache->delete("category_{$item['category_id']}_items");
        }
        $cache->delete('content_list_*');
    }
}
```

```php
public function hookShopOrderPlaced($order) {
```

```php
public function hookContentAfterUpdate($item) {

    }
}
```

## 37.13. Отладка и тестирование хуков

### Проверка регистрации обработчика

```php
// В debug-режиме
$hooks_file = PATH . '/system/controllers/audit/hooks.php';
if (file_exists($hooks_file)) {
    echo "Файл hooks.php найден для компонента audit\n";
    $component = new audit();
    if (method_exists($component, 'hookContentBeforeUpdate')) {
        echo "Метод hookContentBeforeUpdate зарегистрирован\n";
    }
}
```

### Логирование выполнения

```php
public function hookContentBeforeUpdate($item) {
    error_log("[HOOK] content_before_update: item_id={$item['id']}, user={$this->cms_user->id}");
    
    // ... логика обработки ...
    
    error_log("[HOOK] content_before_update: завершено для item_id={$item['id']}");
    return $item;
}
```

### Тестирование cron-хука

```php
// test_cron_hook.php (запускать через CLI)
require_once __DIR__ . '/bootstrap.php';

$controller = cmsCore::getController('shop');
if (!$controller || !$controller->isEnabled()) {
    die("Компонент shop недоступен или отключён\n");
}

echo "Запуск хука cron_export_products_job...\n";
try {
    $controller->runHook('cron_export_products_job');
    echo "Хук выполнен успешно\n";
} catch (Exception $e) {
    error_log("Ошибка выполнения хука: " . $e->getMessage());
    echo "Ошибка: " . $e->getMessage() . "\n";
}
```

## 37.14. Рекомендации и лучшие практики

### ✅ Рекомендуется

| Практика | Обоснование |
|----------|-------------|
| **Одна ответственность на хук** | Упрощает тестирование и поддержку |
| **Всегда возвращать данные** | Сохраняет целостность конвейера обработки |
| **Проверять наличие ключей** | Избегает ошибок `Undefined index` |
| **Использовать флаги ошибок** | `$item['_validation_errors'][] = '...'` вместо исключений |
| **Документировать параметры** | PHPDoc с описанием структуры данных |
| **Проверять существование компонентов** | `cmsCore::isControllerExists('search')` перед использованием |
| **Кэшировать тяжёлые операции** | Использовать `cmsCache` для повторяющихся вычислений |

### ❌ Избегайте

| Антипаттерн | Риск |
|-------------|------|
| Генерация исключений в хуках | Прерывает цепочку выполнения для всех последующих обработчиков |
| Тяжёлые синхронные операции | Замедляет обработку запроса (используйте cron для ресурсоёмких задач) |
| Жёсткие зависимости от других компонентов | Нарушает принцип слабой связанности |
| Неопределённые имена методов | `hookProcess()`, `hookDoStuff()` — неочевидная логика |
| Отсутствие возврата данных | Нарушает конвейер обработки |

### Пример корректной обработки ошибок

```php
public function hookContentBeforeUpdate($item) {
    try {
        $item['computed_value'] = $this->heavyCalculation($item);
    } catch (Exception $e) {
        error_log("Ошибка в хуке content_before_update: " . $e->getMessage());
        $item['_hook_errors'][] = [
            'component' => 'my_component',
            'message' => 'Не удалось рассчитать значение'
        ];
        // Возвращаем данные с флагом ошибки — цепочка продолжит работу
    }
    return $item;
}
```

## 37.15. Справочник системных хуков

| Имя хука | Точка срабатывания | Параметры | Возвращаемое значение |
|----------|---------------------|-----------|------------------------|
| `content_before_add` | Перед созданием контента | `array $item` | Модифицированный `$item` |
| `content_after_add` | После создания контента | `array $item` (с `id`) | Побочные эффекты |
| `content_before_update` | Перед обновлением | `array $item` | Модифицированный `$item` |
| `content_after_update` | После обновления | `array $item` | Побочные эффекты |
| `content_before_delete` | Перед удалением | `int $item_id` | `false` для отмены операции |
| `user_before_login` | Перед аутентификацией | `array $user` | Модифицированные данные |
| `user_after_login` | После успешного входа | `array $user` | Побочные эффекты |
| `shop_order_placed` | После создания заказа | `array $order` | Побочные эффекты |
| `shop_order_status_changed` | При смене статуса | `['order_id', 'old_status', 'new_status']` | Побочные эффекты |
| `cron_*` | Выполнение задачи | Зависит от задачи | Зависит от логики |

> ℹ️ **Примечание:** Это не исчерпывающий список. Каждый компонент может определять собственные хуки. Для изучения доступных точек расширения анализируйте исходный код компонентов, поиск по шаблону `cmsEventsManager::hook(`.

## 37.16. Заключение

Система хуков DST Platform предоставляет мощный и безопасный механизм расширения функциональности:
- Обработчики размещаются в `/system/controllers/{component}/hooks.php`
- Именование методов следует шаблону `hook{EventName}()` в camelCase
- Вызов осуществляется через `cmsEventsManager::hook($name, $data)` или `$controller->runHook($name)`
- Данные передаются по цепочке обработчиков в алфавитном порядке компонентов
- Для фоновых задач используются cron-хуки с префиксом `cron_`
- Критически важные операции должны использовать флаги ошибок вместо исключений

**Дальнейшее изучение:**
- *«Система событий и хуков»* — архитектурные основы событийной модели
- *«Создание компонентов»* — интеграция хуков в пользовательские модули
- *«Архитектура планировщика Cron»* — использование хуков в фоновых задачах
- *«Безопасность и контроль доступа»* — валидация данных в хуках

Грамотное применение хуков позволяет создавать гибкие, поддерживаемые и масштабируемые решения без вмешательства в ядро платформы.
