# Часть I. Основы

## 60.1. Зачем обновлять платформу

DST Platform — живая платформа. Регулярные обновления решают четыре задачи:

| Задача | Что происходит без обновлений |
|---|---|
| **Безопасность** | Накопление уязвимостей, риск взлома |
| **Совместимость** | Устаревшие версии PHP/MySQL перестают поддерживаться (см. раздел 2) |
| **Функциональность** | Новые возможности, оптимизации, исправления |
| **Поддержка** | Техподдержка DST работает только с актуальными версиями (см. раздел 61) |

## 60.2. Типы обновлений

### 60.2.1. Классификация

```
┌──────────────────────────────────────────────────────────────────┐
│                    ТИПЫ ОБНОВЛЕНИЙ DST                           │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│  Security-патчи (PATCH: 1.42.0 → 1.42.1)                         │
│  ├─ Только исправления уязвимостей                               │
│  ├─ Срочные (вне плана)                                          │
│  ├─ Риск: минимальный                                            │
│  └─ Откат: редко нужен                                           │
│                                                                  │
│  Minor-обновления (MINOR: 1.42.0 → 1.43.0)                       │
│  ├─ Новая функциональность (обратно совместимая)                 │
│  ├─ Багфиксы                                                     │
│  ├─ Плановые (раз в квартал)                                     │
│  ├─ Риск: низкий                                                 │
│  └─ Откат: возможен                                              │
│                                                                  │
│  Major-обновления (MAJOR: 1.x.x → 2.0.0)                         │
│  ├─ Breaking changes                                             │
│  ├─ Изменения API, схемы БД                                      │
│  ├─ Плановые (раз в год-два)                                     │
│  ├─ Риск: высокий                                                │
│  └─ Откат: сложный, требует плана                                │
└──────────────────────────────────────────────────────────────────┘
```

### 60.2.2. Рекомендуемый график

| Тип | Частота | Окно |
|---|---|---|
| **Security-патчи** | По мере выхода | В течение 24–72 часов |
| **Minor** | Раз в квартал | Плановое (ночь/выходные) |
| **Major** | Раз в 1–2 года | Отдельный проект |

## 60.3. Политика релизов DST

### 60.3.1. Каналы

| Канал | Описание | Кому |
|---|---|---|
| **stable** | Стабильные релизы | Production |
| **beta** | Бета-версии (тестирование) | Staging, добровольцы |
| **alpha** | Альфа-версии (ранние) | Разработчики |

**По умолчанию** используется **stable**. Переключение на beta — по запросу (для тестирования новых функций).

### 60.3.2. Поддержка версий

| Версия | Поддержка |
|---|---|
| **Текущая major** | Полная (функционал + security) |
| **Предыдущая major** | Security-патчи (12 месяцев) |
| **Более старые** | По запросу (платно) |

**Пример:**

- Текущая: 2.x
- Предыдущая: 1.x — security-патчи до 2026-12-31
- Более старые: 0.x — только платно

## 60.4. Версионирование (SemVer)

DST Platform использует **Semantic Versioning 2.0**:

```
MAJOR.MINOR.PATCH
```

| Компонент | Когда увеличивается | Пример |
|---|---|---|
| **MAJOR** | Breaking changes (API, схема БД) | 1.42.0 → 2.0.0 |
| **MINOR** | Новая функциональность (обратно совместимая) | 1.42.0 → 1.43.0 |
| **PATCH** | Bugfix, security | 1.42.0 → 1.42.1 |

**Проверка версии:**

```bash
# Через CLI
php -r "require '/var/www/dst/bootstrap.php'; echo cmsConfig::get('version');"

# Через админку
# Админка → Настройки → О системе

# Через файл
cat /var/www/dst/VERSION
```

### 60.6.1. Что важно

Кастомизация — главный источник рисков при обновлении. Перед обновлением нужно **знать**, что изменено.

**Файл:** `/docs/upgrade_inventory.md`

```markdown
# Инвентаризация кастомизаций

## 1. Ядро

  - Если есть: список файлов и изменений

## 2. Компоненты
- [ ] Кастомные компоненты (`/system/controllers/{custom}/`)
- [ ] Изменённые стандартные компоненты
- [ ] Кастомные `hooks.php`

## 3. Шаблоны
- [ ] Кастомная тема (`/templates/{custom}/`)
- [ ] Изменения в `/templates/default/`

## 4. Конфигурация
- [ ] `config.php` — изменения
- [ ] `.env` — переменные
- [ ] `composer.json` — зависимости

## 5. БД
- [ ] Кастомные таблицы
- [ ] Изменения в стандартных таблицах
- [ ] Триггеры, процедуры, события

## 6. Интеграции
- [ ] Внешние API (1С, CRM, платежи)
- [ ] Вебхуки
- [ ] Cron-задачи
```

### 60.6.3. Автоматическая проверка

**Скрипт проверки изменений в ядре:**

```bash
#!/usr/bin/env bash
# /opt/dst/check_core_modifications.sh

CORE="/var/www/dst/system/core"
ORIGINAL="/opt/dst/original_core"  # эталон

if [ ! -d "$ORIGINAL" ]; then
    echo "No original core found. Copy current core first."
    exit 1
fi

echo "=== Modified files in core ==="
diff -rq "$ORIGINAL" "$CORE" | grep -v "^Only in $CORE" || echo "No modifications"
```

**Регулярное сохранение эталона:**

```bash
# При первой установке
cp -r /var/www/dst/system/core /opt/dst/original_core
cp -r /var/www/dst/templates/default /opt/dst/original_template
```

## 60.7. Бэкап перед обновлением

### 60.7.1. Что бэкапить

Полный гайд — в разделе **56 «Резервное копирование и восстановление»**. Перед обновлением:

| Компонент | Обязательно | Как |
|---|---|---|
| **MySQL** | ✅ | `mysqldump` (см. 56.7) |
| **Файлы** (`/upload/`) | ✅ | `rsync` / `restic` (см. 56.15) |
| **Код** | ✅ | `git` / `tar` / Docker image |
| **Конфиги** | ✅ | `config.php`, `.env` |
| **Версия** | ✅ | `VERSION` файл |

### 60.7.2. Скрипт бэкапа перед обновлением

**Файл:** `/opt/dst/pre_upgrade_backup.sh`

```bash
#!/usr/bin/env bash
# ─────────────────────────────────────────────────────────────
# Бэкап перед обновлением DST Platform.
# Запуск: ./pre_upgrade_backup.sh <new_version>
# ─────────────────────────────────────────────────────────────

set -euo pipefail

NEW_VERSION="${1:?Usage: $0 <new_version>}"
OLD_VERSION=$(php -r "require '/var/www/dst/bootstrap.php'; echo cmsConfig::get('version');")
BACKUP_DIR="/backups/upgrades/${OLD_VERSION}_to_${NEW_VERSION}_$(date +%Y%m%d_%H%M%S)"

mkdir -p "$BACKUP_DIR"

echo "=== Pre-upgrade backup ==="
echo "  From: $OLD_VERSION"
echo "  To:   $NEW_VERSION"
echo "  Dir:  $BACKUP_DIR"

# ─── 1. БД ────────────────────────────────────────────────────
echo "[1/5] Backing up database..."
DB_NAME=$(php -r "require '/var/www/dst/bootstrap.php'; echo cmsConfig::get('db_base');")
DB_USER=$(php -r "require '/var/www/dst/bootstrap.php'; echo cmsConfig::get('db_user');")
DB_PASS=$(php -r "require '/var/www/dst/bootstrap.php'; echo cmsConfig::get('db_pass');")

mysqldump --single-transaction --quick --routines --triggers \
    --user="$DB_USER" --password="$DB_PASS" \
    "$DB_NAME" | gzip > "${BACKUP_DIR}/database.sql.gz"

echo "  OK: $(du -h "${BACKUP_DIR}/database.sql.gz" | cut -f1)"

# ─── 2. Код ───────────────────────────────────────────────────
echo "[2/5] Backing up code..."
tar -czf "${BACKUP_DIR}/code.tar.gz" \
    -C /var/www \
    --exclude='dst/cache' \
    --exclude='dst/upload' \
    --exclude='dst/exports' \
    dst/

echo "  OK: $(du -h "${BACKUP_DIR}/code.tar.gz" | cut -f1)"

# ─── 3. Upload ────────────────────────────────────────────────
echo "[3/5] Backing up upload..."
rsync -a /var/www/dst/upload/ "${BACKUP_DIR}/upload/"

echo "  OK: $(du -sh "${BACKUP_DIR}/upload" | cut -f1)"

# ─── 4. Конфиги ───────────────────────────────────────────────
echo "[4/5] Backing up config..."
mkdir -p "${BACKUP_DIR}/config"
cp /var/www/dst/system/config/config.php "${BACKUP_DIR}/config/" 2>/dev/null || true
cp /var/www/dst/.env "${BACKUP_DIR}/config/" 2>/dev/null || true
cp /var/www/dst/composer.json "${BACKUP_DIR}/config/" 2>/dev/null || true
cp /var/www/dst/composer.lock "${BACKUP_DIR}/config/" 2>/dev/null || true

# ─── 5. Метаданные ────────────────────────────────────────────
echo "[5/5] Metadata..."
cat > "${BACKUP_DIR}/metadata.json" <<EOF
{
  "old_version": "${OLD_VERSION}",
  "new_version": "${NEW_VERSION}",
  "created_at": "$(date -u +%Y-%m-%dT%H:%M:%SZ)",
  "php_version": "$(php -r 'echo PHP_VERSION;')",
  "mysql_version": "$(mysql --version)",
  "hostname": "$(hostname)"
}
EOF

# ─── Checksums ────────────────────────────────────────────────
cd "$BACKUP_DIR"
find . -type f ! -name "*.sha256" | sort | xargs sha256sum > SHA256SUMS

echo ""
echo "=== Backup complete: $BACKUP_DIR ==="
echo ""
echo "Next steps:"
echo "  1. Verify backup:"
echo "     cd $BACKUP_DIR && sha256sum -c SHA256SUMS"
echo "  2. Proceed with upgrade (see section 60.11)"
```

**Запуск:**

```bash
./pre_upgrade_backup.sh 1.43.0
```

## 60.8. Staging-стенд

> ⚠️ **Правило.** Обновление **всегда** тестируется на staging с копией прод-данных.

**Схема:**

```
┌──────────────────┐        ┌──────────────────┐
│  PROD            │        │  STAGING         │
│  (не трогаем)    │        │                  │
└──────────────────┘        └──────────────────┘
        │                            │
        │ 1. Дамп БД + копия файлов  │
        └───────────────────────────▶│
                                     │
                                     │ 2. Обновление
                                     ▼
                            ┌──────────────────┐
                            │  STAGING v{NEW}  │
                            └──────────────────┘
                                     │
                                     │ 3. Тесты
                                     ▼
                            ┌──────────────────┐
                            │  Отчёт           │
                            └──────────────────┘
```

**Процесс:**

```bash
# 1. Восстановить копию прод на staging
mysql staging_db < /backups/prod_latest.sql
rsync -a /var/www/dst/upload/ staging:/var/www/dst/upload/

# 2. Обновить staging
ssh staging 'cd /var/www/dst && ./scripts/upgrade.sh 1.43.0'

# 3. Прогнать тесты
ssh staging 'cd /var/www/dst && phpunit --testsuite integration'

# 4. Smoke-тесты
bash /opt/dst/smoke.sh --url=https://staging.example.com
```

> ℹ️ Один сервер staging может обслуживать несколько проектов через изолированные окружения (Docker, `php-fpm` pools).

```bash
#!/usr/bin/env bash
# Проверка окружения перед обновлением.

set -euo pipefail

echo "=== Environment check for DST Platform ==="
echo ""

# PHP
echo "PHP: $(php -r 'echo PHP_VERSION;')"

echo ""
echo "PHP Extensions:"

        echo "  $ext: OK"

    fi
done

# MySQL
echo ""
DB_VERSION=$(mysql --version | awk '{print $5}')
echo "MySQL: $DB_VERSION"

# Redis
echo ""
REDIS_VERSION=$(redis-cli --version | awk '{print $3}')
echo "Redis: $REDIS_VERSION"

# Nginx
echo ""
echo "Nginx: $(nginx -v 2>&1 | awk -F'/' '{print $2}')"

# Диск
echo ""
echo "Disk:"
df -h /var/www/dst | tail -1

# Свободное место (минимум 2x размера БД)
DB_SIZE=$(du -sh /var/lib/mysql 2>/dev/null | awk '{print $1}')
echo "  DB size: $DB_SIZE"

echo ""
echo "=== Done ==="
```

## 60.11. Способы обновления

| Способ | Когда |
|---|---|
| **Админ-панель** | Малые обновления (PATCH), простые конфигурации |

## 60.12. Через админ-панель

### 60.12.1. Процесс

1. **Админка → Настройки → Обновления**.
2. Платформа проверяет доступные версии.
3. Нажать «Обновить до 1.43.0».
4. Платформа:
   - Скачивает дистрибутив.
   - Проверяет checksums.
   - Применяет миграции.
   - Очищает кэш.
5. Показать результат.

### 60.12.2. Ограничения

- **Не работает** при больших объёмах изменений.
- **Не работает**, если есть модификации ядра (см. 60.6).
- **Не работает** для major-обновлений.
- **Не работает** в Docker.

> ⚠️ **Не рекомендуется** для production. Используйте CLI (60.13).

## 60.13. Через CLI

### 60.13.1. Скрипт обновления

**Файл:** `/scripts/upgrade.sh`

```bash
#!/usr/bin/env bash
# ─────────────────────────────────────────────────────────────
# Обновление DST Platform через CLI.
#
# Использование:
#   ./upgrade.sh <new_version>              # обновить до версии
#   ./upgrade.sh <new_version> --dry-run    # показать, что будет сделано
#   ./upgrade.sh <new_version> --force      # без подтверждения
# ─────────────────────────────────────────────────────────────

set -euo pipefail

NEW_VERSION="${1:?Usage: $0 <new_version> [--dry-run] [--force]}"
DRY_RUN=0
FORCE=0

shift || true
for arg in "$@"; do
    case "$arg" in
        --dry-run) DRY_RUN=1 ;;
        --force)   FORCE=1 ;;
        *)         echo "Unknown arg: $arg" >&2; exit 1 ;;
    esac
done

APP_DIR="/var/www/dst"
CURRENT_VERSION=$(php -r "require '$APP_DIR/bootstrap.php'; echo cmsConfig::get('version');")

echo "=== DST Platform Upgrade ==="
echo "  Current: $CURRENT_VERSION"
echo "  Target:  $NEW_VERSION"
echo ""

# ─── 1. Проверка возможности обновления ──────────────────────
echo "[1/7] Checking upgrade path..."

if ! php -r "
    require '$APP_DIR/bootstrap.php';
    \$checker = new \cmsUpgrade\VersionChecker();
    exit(\$checker->canUpgrade('$CURRENT_VERSION', '$NEW_VERSION') ? 0 : 1);
"; then
    echo "ERROR: Cannot upgrade from $CURRENT_VERSION to $NEW_VERSION" >&2
    echo "Check CHANGELOG for breaking changes." >&2
    exit 1
fi

echo "  OK: upgrade path valid"

# ─── 2. Проверка окружения ───────────────────────────────────
echo "[2/7] Checking environment..."

if ! /opt/dst/check_environment.sh; then
    echo "ERROR: Environment check failed" >&2
    exit 1
fi

# ─── 3. Бэкап ─────────────────────────────────────────────────
echo "[3/7] Creating pre-upgrade backup..."

if [ "$DRY_RUN" = "0" ]; then
    /opt/dst/pre_upgrade_backup.sh "$NEW_VERSION"
else
    echo "  [DRY-RUN] Would create backup"
fi

# ─── 4. Скачивание ────────────────────────────────────────────
echo "[4/7] Downloading version $NEW_VERSION..."

TEMP_DIR=$(mktemp -d)
DIST_URL="https://repo.dstglobal.ru/releases/${NEW_VERSION}/dst-${NEW_VERSION}.tar.gz"
DIST_FILE="${TEMP_DIR}/dst-${NEW_VERSION}.tar.gz"

if [ "$DRY_RUN" = "0" ]; then
    if ! curl -fsSL "$DIST_URL" -o "$DIST_FILE"; then
        echo "ERROR: Failed to download $DIST_URL" >&2
        exit 1
    fi

    # Проверка checksum
    CHECKSUM_URL="${DIST_URL}.sha256"
    EXPECTED=$(curl -fsSL "$CHECKSUM_URL" | awk '{print $1}')
    ACTUAL=$(sha256sum "$DIST_FILE" | awk '{print $1}')

    if [ "$EXPECTED" != "$ACTUAL" ]; then
        echo "ERROR: Checksum mismatch" >&2
        echo "  Expected: $EXPECTED" >&2
        echo "  Actual:   $ACTUAL" >&2
        exit 1
    fi

    echo "  OK: downloaded and verified"
else
    echo "  [DRY-RUN] Would download $DIST_URL"
fi

# ─── 5. Распаковка ────────────────────────────────────────────
echo "[5/7] Extracting..."

if [ "$DRY_RUN" = "0" ]; then
    tar -xzf "$DIST_FILE" -C "$TEMP_DIR"
    NEW_DIR="${TEMP_DIR}/dst-${NEW_VERSION}"

    if [ ! -d "$NEW_DIR" ]; then
        echo "ERROR: Invalid archive structure" >&2
        exit 1
    fi
else
    echo "  [DRY-RUN] Would extract to $TEMP_DIR"
fi

# ─── 6. Применение ────────────────────────────────────────────
echo "[6/7] Applying update..."

if [ "$DRY_RUN" = "0" ]; then
    # 6.1. Сохранение пользовательских данных
    echo "  - Preserving user data..."
    rsync -a --ignore-existing \
        "$NEW_DIR/system/core/" "$APP_DIR/system/core/"
    rsync -a "$NEW_DIR/system/fields/" "$APP_DIR/system/fields/"
    rsync -a "$NEW_DIR/system/controllers/" "$APP_DIR/system/controllers/"

    # 6.2. Копирование новых файлов ядра
    echo "  - Copying new core files..."
    rsync -a --delete \
        --exclude='config/config.php' \
        "$NEW_DIR/system/core/" "$APP_DIR/system/core/"

    # 6.3. Копирование стандартных компонентов (только если не изменялись)
    echo "  - Copying standard components..."
    for comp in $(ls "$NEW_DIR/system/controllers/"); do
        if [ ! -d "$APP_DIR/system/controllers/$comp" ]; then
            # Новый компонент — копируем
            cp -r "$NEW_DIR/system/controllers/$comp" "$APP_DIR/system/controllers/"
        fi
    done

    # 6.4. Копирование документации
    echo "  - Copying documentation..."
    cp -r "$NEW_DIR/docs/" "$APP_DIR/docs/" 2>/dev/null || true

    # 6.5. Обновление VERSION
    echo "  - Updating VERSION..."
    cp "$NEW_DIR/VERSION" "$APP_DIR/VERSION"

    echo "  OK: files applied"
else
    echo "  [DRY-RUN] Would apply files"
fi

# ─── 7. Миграции БД ──────────────────────────────────────────
echo "[7/7] Running database migrations..."

if [ "$DRY_RUN" = "0" ]; then
    if ! php "$APP_DIR/scripts/migrate.php"; then
        echo "ERROR: Migrations failed" >&2
        echo "Check the error above. Rollback with:" >&2
        echo "  $APP_DIR/scripts/rollback.sh" >&2
        exit 1
    fi

    # Очистка кэша
    echo "  - Clearing cache..."
    php -r "require '$APP_DIR/bootstrap.php'; cmsCache::getInstance()->clean();"

    # Перезагрузка PHP-FPM (если validate_timestamps=0)
    echo "  - Reloading PHP-FPM..."
    sudo systemctl reload php8.1-fpm 2>/dev/null || true

    echo "  OK: migrations applied"
else
    echo "  [DRY-RUN] Would run migrations"
fi

# ─── Итог ─────────────────────────────────────────────────────
echo ""
echo "=== Upgrade complete ==="
echo "  From: $CURRENT_VERSION"
echo "  To:   $NEW_VERSION"
echo ""

if [ "$DRY_RUN" = "0" ]; then
    echo "Next steps:"
    echo "  1. Run smoke tests:"
    echo "     bash /opt/dst/smoke.sh --url=https://example.com"
    echo "  2. Check logs:"
    echo "     tail -100 /var/www/dst/cache/logs/$(date +%Y-%m-%d).log"
    echo "  3. Monitor for 30 minutes (see section 57)"
    echo ""

    # Очистка
    rm -rf "$TEMP_DIR"
fi
```

## 60.17. Независимость компонентов

### 60.17.1. Принцип

Компоненты DST Platform — **независимы** (см. раздел 8). Это значит:

- Обновление ядра не ломает компоненты.

```bash
  require '/var/www/dst/bootstrap.php';
```

## 60.19. Порядок обновления

### 60.19.1. Рекомендуемый порядок

```
1. Ядро (core)
2. Системные компоненты (users, auth, admin)
3. Бизнес-компоненты (shop, partner, orders)
4. Социальные компоненты (content, comments, forum)
```

### 60.19.2. Почему такой порядок

- **Системные** — используются бизнес-компонентами.
- **Бизнес** — зависят от системных.
- **Социальные** — независимы, но могут зависеть от users.
- **Кастомные** — могут зависеть от всего.
- **Шаблоны** — зависят от компонентов.

## 60.28. Откат кода (bare-metal)

### 60.28.1. Скрипт

**Файл:** `/scripts/rollback_code.sh`

```bash
#!/usr/bin/env bash
# ─────────────────────────────────────────────────────────────
# Откат кода DST Platform (bare-metal).
# ─────────────────────────────────────────────────────────────

set -euo pipefail

BACKUP_DIR="${1:?Usage: $0 <backup_dir>}"
APP_DIR="/var/www/dst"

echo "=== Code rollback ==="
echo "  Backup: $BACKUP_DIR"
echo "  Target: $APP_DIR"

# 1. Проверка
if [ ! -f "${BACKUP_DIR}/code.tar.gz" ]; then
    echo "ERROR: code.tar.gz not found in $BACKUP_DIR" >&2
    exit 1
fi

read -r -p "Type 'YES' to confirm rollback: " confirm
if [ "$confirm" != "YES" ]; then
    echo "Aborted"
    exit 1
fi

# 2. Остановить сервисы
echo "[1/5] Stopping services..."
systemctl stop php8.1-fpm || true

# 3. Восстановить код
echo "[2/5] Restoring code..."
cd /var/www
tar -xzf "${BACKUP_DIR}/code.tar.gz" -C /var/www

# 4. Восстановить конфиги (если были изменены)
echo "[3/5] Restoring config..."
cp "${BACKUP_DIR}/config/config.php" "$APP_DIR/system/config/" 2>/dev/null || true
cp "${BACKUP_DIR}/config/.env" "$APP_DIR/" 2>/dev/null || true

# 5. Права
echo "[4/5] Fixing permissions..."
for d in cache upload exports; do
    chown -R dst:dst "$APP_DIR/$d" 2>/dev/null || true
    chmod -R 775 "$APP_DIR/$d" 2>/dev/null || true
done

# 6. Запуск
echo "[5/5] Starting services..."
systemctl start php8.1-fpm
systemctl reload nginx

echo ""
echo "=== Rollback complete ==="
echo "Run smoke tests to verify."
```

### 60.28.2. Использование

## 60.30. Полный откат

### 60.30.1. Когда

- Катастрофа (потеря данных, критические баги).
- Невозможность частичного отката.
- Полная несовместимость.

### 60.30.2. Скрипт

**Файл:** `/scripts/full_rollback.sh`

```bash
#!/usr/bin/env bash
# ─────────────────────────────────────────────────────────────
# Полный откат DST Platform.
# ─────────────────────────────────────────────────────────────

set -euo pipefail

BACKUP_DIR="${1:?Usage: $0 <backup_dir>}"

echo "=== FULL ROLLBACK ==="
echo "  Backup: $BACKUP_DIR"
echo ""
echo "⚠ WARNING: This will:"
echo "  - Restore database (ALL changes after backup will be lost)"
echo "  - Restore code"
echo "  - Restore upload files"
echo "  - Restart services"
echo ""

read -r -p "Type 'YES' to confirm: " confirm
if [ "$confirm" != "YES" ]; then
    echo "Aborted"
    exit 1
fi

# 1. Обслуживание
echo "[1/6] Enabling maintenance mode..."
touch /var/www/dst/templates/default/assets/errors/offline.html

# 2. Код
echo "[2/6] Restoring code..."
/scripts/rollback_code.sh "$BACKUP_DIR"

# 3. БД
echo "[3/6] Restoring database..."
DB_NAME=$(php -r "require '/var/www/dst/bootstrap.php'; echo cmsConfig::get('db_base');")
DB_USER=$(php -r "require '/var/www/dst/bootstrap.php'; echo cmsConfig::get('db_user');")
DB_PASS=$(php -r "require '/var/www/dst/bootstrap.php'; echo cmsConfig::get('db_pass');")

mysql -u"$DB_USER" -p"$DB_PASS" -e "DROP DATABASE IF EXISTS $DB_NAME"
mysql -u"$DB_USER" -p"$DB_PASS" -e "CREATE DATABASE $DB_NAME CHARACTER SET utf8mb4"
gunzip -c "${BACKUP_DIR}/database.sql.gz" | mysql -u"$DB_USER" -p"$DB_PASS" "$DB_NAME"

# 4. Upload
echo "[4/6] Restoring upload files..."
rsync -a --delete "${BACKUP_DIR}/upload/" /var/www/dst/upload/

# 5. Кэш
echo "[5/6] Clearing cache..."
rm -rf /var/www/dst/cache/*
php -r "require '/var/www/dst/bootstrap.php'; cmsCache::getInstance()->clean();"

# 6. Запуск
echo "[6/6] Starting services..."
systemctl reload php8.1-fpm
systemctl reload nginx

rm -f /var/www/dst/templates/default/assets/errors/offline.html

echo ""
echo "=== Rollback complete ==="
```


## 60.34. Кластерные обновления

### 60.34.1. Rolling update

```
Сервер 1 → обновить → health → OK?
    ↓
Сервер 2 → обновить → health → OK?
    ↓
Сервер 3 → обновить → health → OK?
```

**Nginx upstream:**

```nginx
upstream dst_php {
    server 10.0.0.1:9000;
    server 10.0.0.2:9000;
    server 10.0.0.3:9000;
}
```

**Скрипт:**

```bash
for server in 10.0.0.1 10.0.0.2 10.0.0.3; do
    echo "Updating $server..."
    ssh deploy@$server "cd /var/www/dst && ./scripts/upgrade.sh 1.43.0"
    
    # Убрать из upstream
    sed -i "s/server $server:9000;/# server $server:9000;/" /etc/nginx/conf.d/dst.conf
    nginx -s reload
    
    # Подождать drain (30 сек)
    sleep 30
    
    # Обновить
    ssh deploy@$server "cd /var/www/dst && ./scripts/upgrade.sh 1.43.0"
    
    # Вернуть в upstream
    sed -i "s/# server $server:9000;/server $server:9000;/" /etc/nginx/conf.d/dst.conf
    nginx -s reload
    
    # Проверить
    curl -fsS "http://$server:8080/healthz" || exit 1
done
```

### 60.36.2. Скрипт быстрого отката

**Файл:** `/scripts/quick_rollback.sh`

```bash
#!/usr/bin/env bash
# Быстрый откат (Docker).

set -euo pipefail

PREV_VERSION=$(cat /opt/dst/previous_version 2>/dev/null || echo "")

if [ -z "$PREV_VERSION" ]; then
    echo "ERROR: No previous version found" >&2
    exit 1
fi

echo "Rolling back to $PREV_VERSION..."

# Docker
DST_VERSION="$PREV_VERSION" docker compose up -d --no-deps app cron

# Health-check
for i in {1..30}; do
    if curl -fsS https://example.com/healthz > /dev/null; then
        echo "OK: rolled back to $PREV_VERSION"
        exit 0
    fi
    sleep 2
done

echo "ERROR: health-check failed" >&2
exit 1
```

## 60.40. Заключение

Обновление DST Platform строится на трёх принципах:

1. **Регулярность.** Обновляйтесь по плану (security — по выходу, minor — раз в квартал, major — раз в 1–2 года), а не «когда сломается».

2. **Безопасность.** Бэкап → staging → smoke-тесты → откат при проблемах. Никаких «обновим сразу на проде» — только через проверенную цепочку.

3. **Обратимость.** Docker-образ, blue-green, бэкап — всегда есть способ откатиться. Время отката — минуты, а не часы.

**Ключевые инструменты:**

| Инструмент | Назначение |
|---|---|
| **`upgrade.sh`** | Обновление через CLI |
| **`rollback.sh`** | Откат (Docker) |
| **`rollback_code.sh`** | Откат кода (bare-metal) |
| **`full_rollback.sh`** | Полный откат |
| **`pre_upgrade_backup.sh`** | Бэкап перед обновлением |
| **`check_environment.sh`** | Проверка окружения |
| **`smoke.sh`** | Smoke-тесты после обновления |
| **`migrate.php`** | Миграции БД |
| **Docker / blue-green** | Zero-downtime |

**Рекомендации:**

1. **Автоматизируйте.** CI/CD + скрипты обновления (см. 50).
2. **Тестируйте на staging.** Копия прод — обязательна.
3. **Мониторьте после.** 24 часа — ключевой период.
4. **Ведите CHANGELOG.** Что обновили, когда, чем закончилось.
5. **Учитесь на инцидентах.** Post-mortem после каждого отката.
