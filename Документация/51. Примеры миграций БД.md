# Часть I. Основы

## 51.1. Зачем нужны миграции

DST Platform — модульный монолит с 10+ коробочными решениями. Схема БД развивается вместе с платформой:

- добавляются новые компоненты (LMS, CRM, тендеры);
- расширяются существующие (`shop`, `partner`, `content`);
- изменяются типы полей (например, `price` из `DECIMAL(10,2)` в `DECIMAL(15,2)` для крупных маркетплейсов);
- переносятся данные при интеграции с внешними системами (СБИС, 1С).

**Без миграций** каждое изменение схемы — это:

- ручной SQL на каждом сервере (staging, prod, DR);
- риск расхождения схем между средами;
- невозможность воспроизвести состояние БД на момент бага;
- «тихие» поломки при обновлении.

**С миграциями**:

- схема БД — **код**, версионируется в git;
- состояние БД воспроизводимо на любой среде;
- откат — за минуты;
- CI/CD применяет миграции автоматически (см. раздел 50).

> 💡 **Правило DST.** Схема БД — это артефакт кода. Любое изменение (DDL или DML) оформляется миграцией. Ручные `ALTER TABLE` на продакшене — запрещены (кроме аварийного восстановления, с последующей фиксацией миграцией).

## 51.2. Типы миграций

| Тип | Что делает | Пример | Обратимость |
|---|---|---|---|
| **DDL (schema)** | Изменяет структуру | `CREATE TABLE`, `ALTER TABLE`, `DROP INDEX` | Обычно обратима (rollback-миграция) |
| **DML (data)** | Изменяет данные | `INSERT`, `UPDATE`, `DELETE` | Часто **необратима** (нужен бэкап) |
| **Смешанная** | DDL + DML | Добавить колонку + заполнить | Разделяется на две миграции |
| **Идемпотентная** | Можно запускать повторно | `CREATE TABLE IF NOT EXISTS` | — |

**Рекомендация:** DDL и DML — **разделять** на отдельные файлы. Это упрощает откат и тестирование.

```
❌ Плохо:
2024_01_15_120000_add_and_fill_price.sql       # DDL + DML в одном

✅ Хорошо:
2024_01_15_120000_add_price_column.sql         # DDL: ALTER TABLE
2024_01_15_120001_fill_price_column.sql        # DML: UPDATE
```

**Почему:**

- DDL можно откатить (`DROP COLUMN`), DML — нет (нужен бэкап).
- DDL обычно быстрое, DML на больших таблицах — долго (см. 51.18).
- Тестирование DDL (схема) и DML (данные) — разное.

## 51.3. Жизненный цикл миграции

```
┌────────────────────────────────────────────────────────────────┐
│                    ЖИЗНЕННЫЙ ЦИКЛ МИГРАЦИИ                     │
├────────────────────────────────────────────────────────────────┤
│                                                                │
│  1. Разработка                                                │
│     • Написание миграции                                      │
│     • Локальный запуск                                        │
│     • Unit-тест (см. 49)                                      │
│                                                                │
│  2. Code review                                               │
│     • Ревью SQL (индексы, транзакции, обратимость)            │
│     • Проверка на long-running операции                       │
│                                                                │
│  3. Merge в develop                                           │
│     • Автодеплой на staging (см. 50)                          │
│     • Прогон на копии данных prod                             │
│                                                                │
│  4. Приёмка                                                   │
│     • Миграция на staging прошла                              │
│     • Smoke-тесты зелёные                                     │
│     • Метрики (latency, error rate) не изменились             │
│                                                                │
│  5. Продакшн                                                  │
│     • Бэкап БД (см. 56)                                       │
│     • Применение миграции (см. 51.36)                         │
│     • Health-check + smoke                                    │
│                                                                │
│  6. Закрепление                                               │
│     • Запись в cms_migrations                                 │
│     • Checksum зафиксирован                                   │
│     • Файл — в git (навсегда)                                 │
└────────────────────────────────────────────────────────────────┘
```

**Важно:** миграция, применённая на продакшене, **никогда не изменяется**. Изменение файла → расхождение checksum → падение раннера (см. 51.5). Если нужна правка — создаётся **новая** миграция.

## 51.4. Структура и расположение файлов

### 51.4.1. Вариант A: централизованная директория (рекомендуется)

```
/migrations/
├── 2024_01_15_100000_create_cms_migrations_table.sql
├── 2024_01_15_120000_create_mycomp_items_table.sql
├── 2024_01_15_120001_create_mycomp_idempotency_table.sql
├── 2024_01_20_090000_add_price_to_shop_products.sql
├── 2024_01_20_090001_fill_price_from_old_price.sql
├── 2024_02_01_140000_add_index_to_shop_orders_created_at.sql
└── 2024_02_10_080000_create_lms_courses_table.sql
```

**Плюсы:**

- Единая история изменений — легко увидеть эволюцию БД.
- Простой раннер (один `glob`).
- Порядок применения гарантирован (лексикографическая сортировка).

**Минусы:**

- В большой команде — конфликты при мерже (редко, решается timestamp).
- Нет прямой связи с компонентом.

### 51.4.2. Вариант B: по компонентам

```
/system/controllers/shop/migrations/
├── 2024_01_20_090000_add_price_to_products.sql
└── 2024_02_01_140000_add_index_to_orders.sql

/system/controllers/partner/migrations/
├── 2024_02_05_100000_add_commission_rate.sql
└── ...
```

**Плюсы:**

- Миграции компонента — рядом с кодом.
- Отключил компонент — можно не применять его миграции.

**Минусы:**

- Сложнее гарантировать глобальный порядок (что если `partner` ссылается на `shop`?).
- Раннер должен обходить все компоненты.

### 51.4.3. Рекомендация для DST Platform

**Используйте Вариант A (централизованный)**, но с префиксом компонента в имени файла:

```
2024_01_20_090000_shop__add_price_to_products.sql
2024_02_01_140000_shop__add_index_to_orders.sql
2024_02_05_100000_partner__add_commission_rate.sql
2024_02_10_080000_lms__create_courses_table.sql
```

Это даёт:

- Глобальный порядок (по timestamp).
- Фильтрацию по компоненту (`grep shop__`).
- Возможность откатывать миграции конкретного компонента.

**Формат имени:**

```
{YYYY_MM_DD}_{HHMMSS}_{component}__{description}.sql
```

| Часть | Назначение | Пример |
|---|---|---|
| `YYYY_MM_DD` | Дата создания | `2024_01_20` |
| `HHMMSS` | Время (UTC) | `090000` |
| `component` | Компонент (`core` для ядра) | `shop` |
| `description` | Краткое описание (`snake_case`) | `add_price_to_products` |

# Часть II. Система миграций

## 51.5. Раннер миграций

Базовый раннер приведён в разделе 50.22.3. Здесь — **расширенная версия** с поддержкой:

- фильтрации по компоненту;
- dry-run режима;
- проверки checksum;
- прогона на копии БД;
- логирования.

**Файл:** `/scripts/migrate.php` (расширенный)

```php
#!/usr/bin/env php
<?php
/**
 * Раннер миграций DST Platform.
 *
 * Использование:
 *   php scripts/migrate.php                 # применить все новые
 *   php scripts/migrate.php --dry-run       # показать, что будет применено
 *   php scripts/migrate.php --component=shop # только миграции shop
 *   php scripts/migrate.php --status        # статус всех миграций
 *   php scripts/migrate.php --rollback=2024_01_20_090000_shop__add_price_to_products.sql
 */

declare(strict_types=1);

require_once __DIR__ . '/../bootstrap.php';

// ─────────────────────────────────────────────
// 1. Разбор аргументов
// ─────────────────────────────────────────────
$options = getopt('', ['dry-run', 'component::', 'status', 'rollback::', 'help']);

if (isset($options['help'])) {
    echo "Использование: php migrate.php [опции]\n";
    echo "  --dry-run                 Показать, что будет применено\n";
    echo "  --component=NAME          Только миграции компонента\n";
    echo "  --status                  Статус всех миграций\n";
    echo "  --rollback=FILE           Откатить миграцию (если есть .rollback.sql)\n";
    exit(0);
}

$dryRun       = isset($options['dry-run']);
$component    = $options['component'] ?? null;
$showStatus   = isset($options['status']);
$rollbackFile = $options['rollback'] ?? null;

// ─────────────────────────────────────────────
// 2. Инициализация
// ─────────────────────────────────────────────
$db = cmsDatabase::getInstance();
$migrationsDir = __DIR__ . '/../migrations';

// Создаём таблицу учёта, если её нет
$db->query("
    CREATE TABLE IF NOT EXISTS `cms_migrations` (
        `id` INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
        `name` VARCHAR(255) NOT NULL UNIQUE,
        `component` VARCHAR(50) DEFAULT NULL,
        `applied_at` DATETIME NOT NULL,
        `execution_time` FLOAT NOT NULL DEFAULT 0,
        `checksum` CHAR(32) NOT NULL,
        INDEX `idx_component` (`component`),
        INDEX `idx_applied` (`applied_at`)
    ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4
");

// ─────────────────────────────────────────────
// 3. Режим --status
// ─────────────────────────────────────────────
if ($showStatus) {
    $applied = [];
    foreach ($db->query("SELECT name, applied_at, checksum FROM cms_migrations ORDER BY name")->getRows() as $row) {
        $applied[$row['name']] = $row;
    }

    $files = glob($migrationsDir . '/*.sql');
    sort($files, SORT_STRING);

    printf("%-80s %-20s %s\n", 'MIGRATION', 'STATUS', 'APPLIED AT');
    printf("%s\n", str_repeat('-', 120));

    foreach ($files as $file) {
        $name = basename($file);
        $status = isset($applied[$name]) ? '✓ applied' : '○ pending';
        $appliedAt = $applied[$name]['applied_at'] ?? '—';
        printf("%-80s %-20s %s\n", $name, $status, $appliedAt);
    }

    exit(0);
}

// ─────────────────────────────────────────────
// 4. Режим --rollback
// ─────────────────────────────────────────────
if ($rollbackFile !== null) {
    $rollbackFile = basename($rollbackFile);
    $rollbackPath = $migrationsDir . '/' . str_replace('.sql', '.rollback.sql', $rollbackFile);

    if (!file_exists($rollbackPath)) {
        fwrite(STDERR, "✗ Rollback file not found: $rollbackPath\n");
        exit(1);
    }

    echo "▶ Rolling back: $rollbackFile\n";
    $sql = file_get_contents($rollbackPath);

    try {
        $db->beginTransaction();
        $db->query($sql);
        $db->query("DELETE FROM cms_migrations WHERE name = ?", [$rollbackFile]);
        $db->commit();
        echo "✓ Rolled back: $rollbackFile\n";
        exit(0);
    } catch (\Throwable $e) {
        $db->rollback();
        fwrite(STDERR, "✗ Rollback failed: {$e->getMessage()}\n");
        exit(1);
    }
}

// ─────────────────────────────────────────────
// 5. Список миграций
// ─────────────────────────────────────────────
$applied = [];
foreach ($db->query("SELECT name, checksum FROM cms_migrations")->getRows() as $row) {
    $applied[$row['name']] = $row['checksum'];
}

$files = glob($migrationsDir . '/*.sql');
sort($files, SORT_STRING);

// Фильтр по компоненту
if ($component !== null) {
    $files = array_filter($files, function ($file) use ($component) {
        return str_contains(basename($file), "_{$component}__");
    });
    $files = array_values($files);
}

// ─────────────────────────────────────────────
// 6. Применение
// ─────────────────────────────────────────────
$applied_count = 0;
$skipped_count = 0;

foreach ($files as $file) {
    $name     = basename($file);
    $checksum = md5_file($file);

    // Уже применена
    if (isset($applied[$name])) {
        if ($applied[$name] !== $checksum) {
            fwrite(STDERR, "✗ Checksum mismatch: $name\n");
            fwrite(STDERR, "  Applied: {$applied[$name]}\n");
            fwrite(STDERR, "  Current: $checksum\n");
            fwrite(STDERR, "  Файл изменён после применения. Откатите и создайте новую миграцию.\n");
            exit(1);
        }
        $skipped_count++;
        continue;
    }

    // Dry-run
    if ($dryRun) {
        echo "  → Would apply: $name\n";
        continue;
    }

    // Извлекаем компонент из имени
    $componentName = null;
    if (preg_match('/^\d{4}_\d{2}_\d{2}_\d{6}_(\w+)__/', $name, $m)) {
        $componentName = $m[1];
    }

    echo "▶ Applying: $name\n";
    $start = microtime(true);
    $sql = file_get_contents($file);

    try {
        // DDL в MySQL не транзакционен — но мы всё равно оборачиваем,
        // чтобы DML-миграции (UPDATE, INSERT) были атомарными.
        // Для чистого DDL транзакция — no-op.
        $db->beginTransaction();
        $db->query($sql);
        $executionTime = microtime(true) - $start;
        $db->insert('cms_migrations', [
            'name'           => $name,
            'component'      => $componentName,
            'applied_at'     => date('Y-m-d H:i:s'),
            'execution_time' => round($executionTime, 3),
            'checksum'       => $checksum,
        ]);
        $db->commit();
        $applied_count++;
        printf("  ✓ Applied in %.3f sec\n", $executionTime);
    } catch (\Throwable $e) {
        $db->rollback();
        fwrite(STDERR, "✗ Failed: $name\n");
        fwrite(STDERR, "  Error: {$e->getMessage()}\n");
        exit(1);
    }
}

if ($dryRun) {
    echo "=== Dry-run complete. $skipped_count already applied. ===\n";
} else {
    echo "=== Done. Applied: $applied_count, skipped: $skipped_count ===\n";
}
```

## 51.6. Соглашения об именовании

### 51.6.1. Формат

```
{YYYY_MM_DD}_{HHMMSS}_{component}__{description}.sql
```

**Rollback-файл (опционально):**

```
{YYYY_MM_DD}_{HHMMSS}_{component}__{description}.rollback.sql
```

### 51.6.2. Примеры

| Файл | Что делает |
|---|---|
| `2024_01_15_100000_core__create_cms_migrations_table.sql` | Создаёт таблицу учёта миграций |
| `2024_01_15_120000_mycomp__create_items_table.sql` | Создаёт таблицу компонента `mycomp` |
| `2024_01_20_090000_shop__add_price_to_products.sql` | Добавляет колонку `price` |
| `2024_01_20_090001_shop__fill_price_from_old_price.sql` | Заполняет новую колонку |
| `2024_02_01_140000_shop__add_index_to_orders_created_at.sql` | Добавляет индекс |
| `2024_02_10_080000_lms__create_courses_table.sql` | Создаёт таблицу LMS |
| `2024_02_15_100000_partner__add_commission_rate.sql` | Миграция партнёрского компонента |

### 51.6.3. Правила `description`

- `snake_case`, латиница, цифры, `_`.
- Начинается с глагола: `create`, `add`, `drop`, `fill`, `rename`, `migrate`.
- Достаточно информативно: `add_price_to_products`, а не `update_products`.

## 51.7. Версионирование

| Формат | Когда | Пример |
|---|---|---|
| `YYYY_MM_DD_HHMMSS` | Всегда (сортировка) | `2024_01_15_120000` |
| SemVer для платформы | В `CHANGELOG.md` | `v1.42.0` |

**Соответствие платформе:**

Миграции применяются **вместе** с релизом. Например, релиз `v1.42.0` включает миграции от `2024_01_15` до `2024_02_10`.

## 51.8. Организация миграций в модульном монолите

DST Platform — 10+ коробочных решений. Каждое использует свой набор компонентов. Миграции должны быть **изолированы**, чтобы:

- Старые решения не применяли миграции новых компонентов.
- Можно было откатить компонент без отката ядра.
- Схема оставалась консистентной между решениями.

**Решение — префикс компонента + флаг `component` в `cms_migrations`:**

```sql
SELECT * FROM cms_migrations WHERE component = 'shop';
```

**Правила:**

1. Миграции ядра — префикс `core__`.
2. Миграции компонента — префикс `{component}__`.
3. Миграции, затрагивающие несколько компонентов — **не допускаются** (разделить на отдельные, с явными зависимостями через FK).
4. Если миграция нужна только для одного решения — вынести в отдельную директорию `migrations/solutions/{solution}/`.

```
/migrations/
├── 2024_01_15_100000_core__create_migrations_table.sql
├── 2024_01_15_120000_shop__create_products_table.sql
├── 2024_01_20_090000_shop__add_price.sql
├── 2024_02_01_140000_partner__add_commission_rate.sql
└── solutions/
    └── marketplace/
        └── 2024_03_01_100000_marketplace__create_vendor_payouts.sql
```

# Часть III. Schema Migrations (DDL)

## 51.9. Создание таблиц

### 51.9.1. Базовый пример

**Файл:** `2024_01_15_120000_mycomp__create_items_table.sql`

```sql
-- Создание таблицы элементов компонента mycomp
-- Автор: backend-team
-- Обратимость: DROP TABLE cms_mycomp_items

CREATE TABLE IF NOT EXISTS `cms_mycomp_items` (
    `id` INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    `title` VARCHAR(255) NOT NULL,
    `content` TEXT,
    `category_id` INT UNSIGNED NOT NULL DEFAULT 0,
    `user_id` INT UNSIGNED NOT NULL,
    `is_published` TINYINT(1) NOT NULL DEFAULT 0,
    `created_at` DATETIME NOT NULL,
    `updated_at` DATETIME DEFAULT NULL,

    INDEX `idx_user` (`user_id`),
    INDEX `idx_category` (`category_id`),
    INDEX `idx_published_created` (`is_published`, `created_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

**Файл:** `2024_01_15_120000_mycomp__create_items_table.rollback.sql`

```sql
DROP TABLE IF EXISTS `cms_mycomp_items`;
```

**Пояснения:**

| Параметр | Значение | Почему |
|---|---|---|
| `IF NOT EXISTS` | Идемпотентность | Миграция может запускаться на БД, где таблица уже есть (вручную созданная) |
| `ENGINE=InnoDB` | Транзакции, FK | Обязательно для DST Platform |
| `CHARSET=utf8mb4` | Unicode 4 байта | Эмодзи, кириллица, иероглифы |
| `COLLATE=utf8mb4_unicode_ci` | Регистронезависимое сравнение | Корректная сортировка в кириллице |
| `DATETIME` | Без TZ | Платформа хранит UTC (см. `date.timezone=UTC`) |
| `idx_published_created` | Композитный | Оптимизация `WHERE is_published=1 ORDER BY created_at DESC` |
| `TINYINT(1)` | Boolean | Стандарт MySQL для `bool` |

### 51.9.2. Пример с внешним ключом

**Файл:** `2024_01_15_120001_mycomp__create_comments_table.sql`

```sql
-- Комментарии к элементам mycomp
-- Зависимости: cms_mycomp_items (id), cms_users (id)
-- Обратимость: DROP TABLE cms_mycomp_comments

CREATE TABLE IF NOT EXISTS `cms_mycomp_comments` (
    `id` INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    `item_id` INT UNSIGNED NOT NULL,
    `user_id` INT UNSIGNED NOT NULL,
    `content` TEXT NOT NULL,
    `created_at` DATETIME NOT NULL,

    INDEX `idx_item` (`item_id`),
    INDEX `idx_user` (`user_id`),

    CONSTRAINT `fk_mycomp_comments_item`
        FOREIGN KEY (`item_id`) REFERENCES `cms_mycomp_items` (`id`)
        ON DELETE CASCADE ON UPDATE CASCADE,

    CONSTRAINT `fk_mycomp_comments_user`
        FOREIGN KEY (`user_id`) REFERENCES `cms_users` (`id`)

) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

**Правила для FK в DST Platform:**

| Правило | Почему |
|---|---|
| Всегда именованный FK (`fk_{table}_{ref}`) | Упрощает откат и диагностику |
| `ON DELETE CASCADE` для зависимых | Удалили элемент — удалились комментарии |
| `ON DELETE RESTRICT` для справочников | Нельзя удалить пользователя, если у него есть элементы (по умолчанию) |
| Не FK на таблицы других компонентов без `core` | Слабая связанность (см. раздел 6) |
| Индекс на FK-колонку | MySQL создаёт автоматически, но явное лучше |

> ⚠️ **Слабая связанность.** FK между компонентами допустим только в исключительных случаях (например, `partner` → `users` — оба `core`). Если компонент может быть отключён — FK не создавать, хранить `id` без ограничения (см. раздел 6 «Базовая архитектура»).

### 51.10.4. Проверка существования (идемпотентность)

MySQL не поддерживает `ADD COLUMN IF NOT EXISTS` (до 8.0.29 — тоже нет). Решение — процедура-обёртка:

```sql
-- Только для MySQL 5.7+
DROP PROCEDURE IF EXISTS _dst_add_column;

DELIMITER //

CREATE PROCEDURE _dst_add_column(
    IN p_table VARCHAR(64),
    IN p_column VARCHAR(64),
    IN p_definition VARCHAR(255)
)
BEGIN
    IF NOT EXISTS (
        SELECT 1 FROM information_schema.COLUMNS
        WHERE TABLE_SCHEMA = DATABASE()
          AND TABLE_NAME = p_table
          AND COLUMN_NAME = p_column
    ) THEN
        SET @sql = CONCAT('ALTER TABLE `', p_table, '` ADD COLUMN `', p_column, '` ', p_definition);
        PREPARE stmt FROM @sql;
        EXECUTE stmt;
        DEALLOCATE PREPARE stmt;
    END IF;
END //

DELIMITER ;

CALL _dst_add_column('cms_shop_products', 'price', 'DECIMAL(10,2) NOT NULL DEFAULT 0.00 AFTER `title`');

DROP PROCEDURE _dst_add_column;
```

**Когда использовать:** если миграция применяется на БД, где колонка могла быть создана вручную. В большинстве случаев достаточно `ALTER TABLE ... ADD COLUMN` без проверки — раннер гарантирует однократное применение.

|---|---|

| `INT` → `BIGINT` | INPLACE, безопасно |
| `TEXT` → `VARCHAR(255)` | COPY (медленно), риск обрезки |
| `DATETIME` → `TIMESTAMP` | COPY, риск TZ-сдвига |

**Перед изменением — проверка данных:**

## 51.12. Безопасное переименование

> ⚠️ **`RENAME COLUMN` в MySQL** (8.0+) — INPLACE, но **ломает** старый код, который обращается к колонке по имени. При zero-downtime деплое (см. раздел 50) это **недопустимо**.

### 51.12.1. Безопасный паттерн (Expand-Migrate-Contract)

**Цель:** переименовать `name` → `title` без простоя.

**Релиз 1 (Expand):**

```sql
-- 2024_04_01_100000_shop__add_title_to_products.sql
-- Шаг 1: добавить новую колонку
ALTER TABLE `cms_shop_products`
    ADD COLUMN `title` VARCHAR(255) DEFAULT NULL AFTER `name`;

-- 2024_04_01_100001_shop__copy_name_to_title.sql
-- Шаг 2: скопировать данные
UPDATE `cms_shop_products`
SET `title` = `name`
WHERE `title` IS NULL;
```

**Код (релиз 1):** пишет **в обе** колонки, читает из **новой** (или из обеих с fallback):

```php
// modelShop::updateProduct()
$data['name']  = $data['title'] ?? $data['name'];
$data['title'] = $data['title'] ?? $data['name'];
$this->update('shop_products', $id, $data);

// modelShop::getProduct()
$item = $this->getItem('shop_products', $id);
$item['title'] = $item['title'] ?? $item['name']; // fallback
return $item;
```

**Релиз 2 (Migrate):** код читает только из `title`, пишет только в `title`. Колонка `name` больше не используется.

```sql
-- 2024_05_01_100000_shop__make_title_not_null.sql
ALTER TABLE `cms_shop_products`
    MODIFY COLUMN `title` VARCHAR(255) NOT NULL;
```

**Релиз 3 (Contract):** удаляем `name`.

```sql
-- 2024_06_01_100000_shop__drop_name_from_products.sql
ALTER TABLE `cms_shop_products`
    DROP COLUMN `name`;
```

**Итого — 3 релиза, ~2 месяца, zero-downtime.**

### 51.12.2. Быстрое переименование (для непубличных таблиц)

Если таблица используется только в одном месте (например, лог-таблица), можно переименовать сразу:

```sql
-- 2024_04_01_100000_audit__rename_log_table.sql
-- Быстрое переименование (рискованно только если код обращается напрямую)
RENAME TABLE `cms_audit_log` TO `cms_audit_events`;
```

**Риск:** старый код получит `Table 'cms_audit_log' doesn't exist`. Поэтому — только в комбинации с деплоем (атомарно) или для непубличных таблиц.

## 51.18. Бэкфилл батчами

**Проблема:** `UPDATE` на 5M строк заблокирует таблицу на минуты. На продакшене — недопустимо.

**Решение:** батчи по 1000–10000 строк с паузами.

**Файл:** `2024_02_10_100000_shop__backfill_price_batch.sql`

Этот файл **не выполняется** раннером напрямую (он для больших таблиц). Вместо него — PHP-скрипт:

**Файл:** `/scripts/backfill_price.php`

```php
<?php
/**
 * Бэкфилл price батчами.
 * Запуск: php scripts/backfill_price.php
 * Cron: */10 * * * * php /var/www/dst/scripts/backfill_price.php
 */

declare(strict_types=1);

require_once __DIR__ . '/../bootstrap.php';

$db = cmsDatabase::getInstance();

$batchSize = 1000;
$sleepMicros = 100000; // 0.1 сек между батчами
$totalUpdated = 0;

while (true) {
    // Захватываем батч
    $rows = $db->query("
        SELECT id FROM cms_shop_products
        WHERE price = 0.00 AND old_price > 0.00
        LIMIT ?
    ", [$batchSize])->getRows();

    if (empty($rows)) {
        break;
    }

    $ids = array_column($rows, 'id');
    $placeholders = implode(',', array_fill(0, count($ids), '?'));

    $db->query("
        UPDATE cms_shop_products
        SET price = old_price
        WHERE id IN ($placeholders)
    ", $ids);

    $updated = $db->getAffectedRows();
    $totalUpdated += $updated;

    printf("Updated %d (total: %d)\n", $updated, $totalUpdated);

    usleep($sleepMicros);
}

echo "=== Done. Total updated: $totalUpdated ===\n";
```

**Преимущества:**

- Не блокирует таблицу надолго.

## 51.19. Трансформация данных

### 51.19.1. Изменение формата

**Задача:** телефон хранился как `+7 (999) 123-45-67`, нужно `79991234567`.

**Файл:** `2024_03_01_110000_users__normalize_phones.sql` (PHP-скрипт, не SQL):

```php
<?php
declare(strict_types=1);

require_once __DIR__ . '/../bootstrap.php';

$db = cmsDatabase::getInstance();

$batchSize = 1000;
$total = 0;

while (true) {
    $rows = $db->query("
        SELECT id, phone FROM cms_users
        WHERE phone LIKE '%+%' OR phone LIKE '%-%' OR phone LIKE '% %' OR phone LIKE '%(%'
        LIMIT ?
    ", [$batchSize])->getRows();

    if (empty($rows)) {
        break;
    }

    $db->beginTransaction();
    foreach ($rows as $row) {
        // Нормализация: убрать всё, кроме цифр
        $normalized = preg_replace('/\D/', '', $row['phone']);
        // Заменить ведущую 8 на 7
        if (str_starts_with($normalized, '8')) {
            $normalized = '7' . substr($normalized, 1);
        }
        $db->query("UPDATE cms_users SET phone = ? WHERE id = ?", [$normalized, $row['id']]);
    }
    $db->commit();

    $total += count($rows);
    printf("Normalized %d (total: %d)\n", count($rows), $total);

    usleep(50000); // 0.05 сек
}

echo "=== Done. Total: $total ===\n";
```

# Часть VI. Zero-downtime

## 51.29. Принцип «N и N+1»

См. также раздел 50.22.1. Кратко:

| Фаза | Что делаем | Что видит старая версия | Что видит новая версия |
|---|---|---|---|
| **1. Expand** | Добавить новую колонку (nullable) | ✅ (не замечает) | ✅ |
| **2. Deploy** | Раскатать новый код | ✅ (старая схема) | ✅ (новая схема) |
| **3. Migrate** | Заполнить новую колонку | ✅ (старая схема) | ✅ (новая схема) |
| **4. Contract** | Удалить старую (следующий релиз) | ❌ | ✅ |

## 51.31. Online DDL в MySQL

**Проверка, что операция онлайн:**

```sql
-- Перед применением — сухой прогон
ALTER TABLE cms_shop_products
    ADD INDEX idx_new (column),
    ALGORITHM=INPLACE, LOCK=NONE;
```

**Если MySQL ответит ошибкой** (`ALGORITHM=INPLACE is not supported`) — операция требует копирования таблицы. Варианты:

1. **Окно обслуживания** (downtime 5–30 мин).
2. **`pt-online-schema-change`** (Percona Toolkit).
3. **`gh-ost`** (GitHub).
4. **Blue-green на уровне БД** (реплика → переключение).

**Таблица поддерживаемых операций (MySQL 8.0):**

| Операция | INPLACE | LOCK=NONE |
|---|---|---|
| `ADD COLUMN` (в конце) | ✅ | ✅ |
| `ADD COLUMN` (в середине) | ❌ | ❌ |
| `ADD INDEX` | ✅ | ✅ |
| `DROP INDEX` | ✅ | ✅ |
| `MODIFY COLUMN` (расширение) | ✅ | ✅ |
| `MODIFY COLUMN` (сужение) | ❌ | ❌ |
| `RENAME COLUMN` | ✅ | ✅ |
| `DROP COLUMN` | ✅ | ✅ |
| `ADD FOREIGN KEY` | ❌ | ❌ |
| `CHANGE COLUMN` (тип) | ❌ | ❌ |

## 51.32. Миграции больших таблиц

**Правила для таблиц >10M строк:**

1. **Не делайте DDL в один `ALTER`** — разбейте на несколько.
2. **Используйте `ALGORITHM=INPLACE, LOCK=NONE`** — всегда.
3. **DML — только батчами** (см. 51.18).
4. **Тестируйте на копии prod** — время может быть 10–60 мин.
5. **Мониторьте replication lag** — при >5 сек пауза.
6. **Используйте `pt-online-schema-change` / `gh-ost`** для сложных изменений.

**Скрипт проверки размера таблиц:**

```sql
SELECT
    table_name,
    ROUND(((data_length + index_length) / 1024 / 1024), 2) AS size_mb,
    table_rows
FROM information_schema.TABLES
WHERE table_schema = DATABASE()
ORDER BY (data_length + index_length) DESC
LIMIT 20;
```

```php
        $sql = file_get_contents($this->migrationFile);
        $this->pdo->exec($sql);

        // Assert
        $columns = $this->pdo->query("SHOW COLUMNS FROM cms_shop_products LIKE 'price'")->fetchAll();
        $this->assertCount(1, $columns);
        $this->assertSame('price', $columns[0]['Field']);
        $this->assertSame('0.00', $columns[0]['Default']);
        $this->assertSame('NO', $columns[0]['Null']);
    }

    public function testMigrationIsIdempotent(): void
    {
        // Arrange
        $this->createTableWithoutPrice();
        $sql = file_get_contents($this->migrationFile);

        // Act — применяем дважды
        $this->pdo->exec($sql);
        // Второй раз должен упасть (ADD COLUMN без IF NOT EXISTS)
        // Поэтому используем процедуру-обёртку (см. 51.10.4) или проверяем ошибку
        $this->expectException(\PDOException::class);
        $this->pdo->exec($sql);
    }

    public function testRollbackRemovesColumn(): void
    {
        // Arrange
        $this->createTableWithoutPrice();
        $sql = file_get_contents($this->migrationFile);
        $this->pdo->exec($sql);

        // Act
        $rollbackSql = file_get_contents(
            str_replace('.sql', '.rollback.sql', $this->migrationFile)
        );
        $this->pdo->exec($rollbackSql);

        // Assert
        $columns = $this->pdo->query("SHOW COLUMNS FROM cms_shop_products LIKE 'price'")->fetchAll();
        $this->assertEmpty($columns);
    }

    private function createTableWithoutPrice(): void
    {
        $this->pdo->exec("
            CREATE TABLE IF NOT EXISTS cms_shop_products (
                id INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
                title VARCHAR(255) NOT NULL,
                vendor_id INT UNSIGNED NOT NULL DEFAULT 0,
                created_at DATETIME NOT NULL
            ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4
        ");
    }
}
```

## 51.34. Стратегии отката

| Ситуация | Стратегия | Время |
|---|---|---|
| Ошибка в DML (данные) | Восстановление из бэкапа | 5–30 мин |
| Ошибка в DDL (схема) | `.rollback.sql` | секунды |
| Ошибка в коде (не в схеме) | Откат образа (см. 50.23) | 30 сек |
| Проблема в данных + схеме | Бэкап + откат образа | 5–30 мин |

**Правила:**

1. **DDL-миграции** — всегда с `.rollback.sql` (если возможно).
2. **DML-миграции** — бэкап перед применением.
3. **Если `.rollback.sql` нет** — восстановление из бэкапа.

## 51.35. Обратимость

### 51.35.1. Что обратимо

| Операция | Обратимо | Rollback |
|---|---|---|
| `CREATE TABLE` | ✅ | `DROP TABLE` |
| `ADD COLUMN` | ✅ | `DROP COLUMN` |
| `ADD INDEX` | ✅ | `DROP INDEX` |
| `RENAME TABLE` | ✅ | `RENAME TABLE` обратно |
| `INSERT` | ⚠️ | `DELETE` (если есть PK) |
| `UPDATE` | ⚠️ | Только из бэкапа |
| `DELETE` | ❌ | Только из бэкапа |
| `DROP COLUMN` | ❌ | Восстановление из бэкапа |
| `DROP TABLE` | ❌ | Восстановление из бэкапа |

### 51.35.2. Пример `.rollback.sql`

**Прямой:**

```sql
-- 2024_01_20_090000_shop__add_price_to_products.rollback.sql
ALTER TABLE `cms_shop_products` DROP COLUMN `price`;
```

**С бэкапом:**

```sql
-- 2024_01_20_090001_shop__fill_price_from_old_price.rollback.sql
-- ⚠ Откат UPDATE невозможен без сохранения старых значений
-- Варианты:
-- 1. Восстановление из бэкапа (рекомендуется)
-- 2. Если старые значения были 0 — можно:
UPDATE `cms_shop_products` SET `price` = 0.00 WHERE `price` = `old_price`;
```

```bash

# 6. Health-check + smoke
curl -fsS https://example.com/healthz
bash scripts/smoke.sh
```

> ⚠️ **Откат DML = восстановление из бэкапа.** Это значит, что все данные, созданные после бэкапа, будут потеряны. Поэтому:

- Бэкап — **непосредственно перед** миграцией.
- Если миграция долгая — бэкап на момент **до начала**.
- После отката — повторный бэкап для аудита.

## 51.38. Типичные ошибки

| Ошибка | Симптом | Решение |
|---|---|---|
| **`ALTER TABLE` без `ALGORITHM`** | Блокировка таблицы на минуты | `ALGORITHM=INPLACE, LOCK=NONE` |
| **`UPDATE` без `WHERE`** | Обновило всю таблицу | Всегда `WHERE`, `LIMIT` для батчей |
| **`UPDATE` в транзакции на 10M строк** | `ERROR 1205: Lock wait timeout` | Батчи по 1000 |
| **`DROP COLUMN` без бэкапа** | Потеря данных | `CREATE TABLE _backup_... AS SELECT` |
| **`ADD FOREIGN KEY` на большой таблице** | Блокировка | `pt-online-schema-change` |
| **`MODIFY COLUMN` сужение** | Обрезка данных | Проверить `MAX(LENGTH())` |
| **`TRUNCATE` на большой таблице** | Блокировка | `DELETE ... LIMIT` батчами |
| **Забыли `.rollback.sql`** | Нельзя откатить | Всегда создавать |
| **Изменение применённой миграции** | Checksum mismatch | Никогда не менять, создавать новую |
| **`DROP TABLE` без `RENAME`** | Потеря данных | `RENAME` → бэкап → `DROP` |
| **`INSERT` без `ON DUPLICATE KEY`** | Дубли при повторном запуске | Идемпотентность |
| **`UPDATE` с `JOIN` на 5M+** | Долго | Батчи / `pt-archiver` |
| **Миграция на prod без теста на копии** | Сюрпризы | Всегда тестировать |
| **`SET FOREIGN_KEY_CHECKS=0`** | Нарушение целостности | Не отключать без крайней необходимости |

## 51.40. Заключение

Миграции DST Platform строятся на трёх принципах:

1. **Версионирование.** Схема БД — код в git. Любое изменение — миграция.
2. **Безопасность.** Бэкап перед применением. Expand-Migrate-Contract для переименований. Батчи для больших таблиц. `ALGORITHM=INPLACE` где возможно.
