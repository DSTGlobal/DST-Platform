## 1.2. Идентичность платформы

DST Platform — это гибридная система на основе PHP, объединяющая:

Возможности CMS (система управления контентом) для контент-ориентированных веб-сайтов
CMF (Content Management Framework) , предоставляющий низкоуровневые API для пользовательской разработки.
Платформа обеспечивает поддержку проектов от блогов и защищенных сайтов до высоконагруженных социальных сетей, маркетплейсов, B2B-порталов и цифровых экосистем.

Основная философия: Платформа отказывается от дихотомии «простая CMS против сложного фреймворка», вместо этого учитывается многоуровневая модель разработки:

### Уровни разработки в DST Platform

| Уровень               | Подход                              | Сценарий использования                                |
|----------------------|-------------------------------------|--------------------------------------------------------|
| **Конфигурация**     | Настройка через админ-панель без кода | Создание стандартных сущностей: статьи, каталоги, страницы |
| **Расширение**       | Хуки, переопределение классов       | Модификация поведения существующих компонентов         |
| **Разработка**       | Полная реализация контроллеров и моделей | Реализация сложной бизнес-логики: платежи, доставка, интеграции |

## 1.4. Точки входа в систему

DST Platform обрабатывает запросы через несколько точек входа, каждая из которых инициализирует ядро через общий загрузчик `bootstrap.php`.

<img src="https://dstglobal.ru/img/git/2.png" alt="DST Platform">

Диаграмма: Точки входа в систему, соответствующие файлам кода

### Точки входа

| Тип входа                     | Файл                      | Назначение                                              |
|------------------------------|---------------------------|---------------------------------------------------------|
| HTTP-запросы                 | `index.php`               | Фронт-контроллер для всех веб-запросов                  |
| Запланированные задачи       | `cron.php`                | Выполнение регулярных задач из очереди в БД             |
| Экспорт данных               | `cron_export.php`         | Автоматизированный экспорт данных в табличные форматы   |
| Генерация YML-фида (магазин) | `cron_yml_create.php`     | Формирование фида для Яндекс.Маркета (режим «магазин»)  |
| Генерация YML-фида (маркет)  | `cron_yml_market_create.php` | Формирование фида для Яндекс.Маркета (режим «маркет») |
| Импорт партнёрских данных    | `cron_partner_import.php` | Синхронизация данных от внешних поставщиков             |

> **Примечание.** Все точки входа загружают общий инициализационный скрипт `bootstrap.php`.

### Маршрутизация URL

Файл `.htaccess` в корне проекта перенаправляет все динамические запросы на `index.php`, при этом статические ресурсы обслуживаются напрямую:

- **Статические ресурсы** (`*.css`, `*.js`, изображения и т.п.) → отдаются веб-сервером без участия PHP.
- **Динамические запросы** → переписываются на `index.php` для обработки маршрутизатором платформы.

## 1.6. MVC-архитектура приложений

Платформа реализует шаблон **Model-View-Controller (MVC)**, где логика приложения организована по компонентам. Каждый компонент представляет собой автономный модуль с собственными контроллерами, моделями и шаблонами.

### Структура

<img src="https://dstglobal.ru/img/git/4.png" alt="DST Platform">

Диаграмма: Структура компонентов каталогов и отношений классов.

### Структура компонента

Компонент размещается в `/system/controllers/{component_name}/` и может включать следующие элементы:

| Элемент                     | Путь к файлу                                      | Имя класса                                 | Назначение                                                                 |
|----------------------------|--------------------------------------------------|--------------------------------------------|----------------------------------------------------------------------------|
| Фронтенд-контроллер        | `controller.php`                                 | `class {componentName} extends cmsFrontend`| Обработка публичных HTTP-запросов                                          |
| Бэкенд-контроллер          | `backend/controller.php`                         | `class backend{ComponentName} extends cmsBackend` | Административный интерфейс компонента                                  |
| Модель (фронтенд)          | `model.php`                                      | `class model{ComponentName} extends cmsModel` | Работа с данными и бизнес-логика                                         |
| Модель (бэкенд)            | `backend/model.php`                              | `class modelBackend{ComponentName} extends model{ComponentName}` | Расширение модели для админ-панели                                    |
| Шаблоны (фронтенд)         | `/templates/{theme}/controllers/{component}/*.tpl.php` | —                                        | HTML-представление для публичной части                                   |
| Шаблоны (бэкенд)           | `/templates/{theme}/controllers/{component}/backend/*.tpl.php` | —                              | HTML-представление для админ-панели                                      |
| Виджеты                    | `widgets/{widget_name}/widget.php`               | `class {componentName}{WidgetName} extends cmsWidget` | Переиспользуемые UI-блоки, привязанные к компоненту                   |

> **Примечание.** Имена классов используют PascalCase, даже если имя компонента в нижнем регистре (например, компонент `my_shop` → класс `myShop`).

### Требования к имени компонента

- Минимум 3 символа
- Только строчные буквы, цифры и символ подчёркивания (`_`)
- Должно начинаться с буквы

**Допустимые примеры:** `shop`, `users`, `content`, `forum`, `my_component`

## 1.8. Декларативная разработка (без кода)

Платформа позволяет создавать типы контента **без написания кода** через встроенный генератор в компоненте `content`.

### Процесс создания

1. Перейти в админ-панель → **Генератор контента** → «Создать новый тип»  
2. Определить поля: текст, изображения, даты, связи с другими сущностями  
3. Настроить формы ввода и правила валидации  
4. Создать шаблоны отображения: список и детальная страница  
5. При необходимости — настроить таксономии (категории, теги)

### Автоматически генерируемые артефакты

- Таблица в БД с индексами  
- CRUD-операции через `cmsModel`  
- Интерфейс управления в админ-панели  
- Шаблоны фронтенда  
- Поддержка поиска и комментариев  
- SEO-поля (title, description, meta)

### Расположение

Логика реализована в компоненте:  
`/system/controllers/content/`

### Типовые сценарии

- Новостные ленты и блоги  
- Простые каталоги товаров  
- Базы знаний и документация  
- Портфолио и галереи  
- Календари событий  
- Справочники и FAQ

## 1.10. Гибридная стратегия разработки

На практике рекомендуется **комбинировать оба подхода**:

1. **Начните декларативно**: создайте базовую сущность через генератор контента.  
2. **Расширьте императивно**: добавьте кастомный контроллер или модель для специфичной логики.  
3. **Подключите события**: используйте `cmsEventsManager` для внедрения кода в стандартные рабочие процессы.  
4. **Кастомизируйте представление**: замените сгенерированные `.tpl.php`-файлы на свои шаблоны.

Такой подход обеспечивает **быстрый старт** и **гибкость масштабирования** без дублирования усилий.

> Каталоги `/cache/`, `/upload/`, `/exports/` и `/vendor/` должны быть добавлены в `.gitignore`.

## 1.12. Процесс инициализации системы

Каждый запрос — HTTP (`index.php`) или CLI (`cron_*.php`) — проходит через стандартизированную последовательность инициализации.

Последовательность бутстрапа

<img src="https://dstglobal.ru/img/git/7.png" alt="DST Platform">

Диаграмма: Последовательность инициализации системы

### Этапы загрузки

1. **Автозагрузка Composer**  
   - Подключает `vendor/autoload.php`  
   - Регистрирует PSR-4 автозагрузчики

2. **Загрузка конфигурации (`cmsConfig`)**  
   - Читает `/system/config/config.php`  
   - Настраивает подключение к БД, режим отладки, кэш, часовой пояс

3. **Инициализация ядра (`cmsCore`)**  
   - Создаёт синглтоны всех базовых сервисов  
   - Выступает как service locator

4. **Подключение к БД (`cmsDatabase`)**  
   - Устанавливает соединение с MySQL/MariaDB  
   - Инициализирует query builder

5. **Система кэширования (`cmsCache`)**  
   - Настраивает бэкенд (Redis, Memcached или файлы)  
   - Готовит интерфейс кэширования

6. **Система событий (`cmsEventsManager`)**  
   - Регистрирует обработчики из `hooks.php`  
   - Вызывает событие `core_start` для ранней инициализации компонентов

7. **Пользовательская сессия (`cmsUser`)**  
   - Запускает PHP-сессию  
   - Загружает данные авторизованного пользователя или создаёт гостевой объект

8. **Шаблонный движок (`cmsTemplate`)**  
   - Определяет активную тему  
   - Настраивает цепочку наследования шаблонов  
   - Подготавливает управление assets

### После инициализации

- **HTTP-запросы**:  
  Маршрутизатор определяет компонент и действие → создаёт контроллер → вызывает метод → рендерит шаблон → выводит HTML.

- **CLI-задачи (cron)**:  
  Скрипт напрямую вызывает метод контроллера → выполняет бизнес-логику (экспорт, импорт, генерация фидов) → завершается.

## 1.14. Механизмы маршрутизации запросов

### Перезапись URL (.htaccess)

- **Статические ресурсы** (`.css`, `.js`, `.jpg`, `.png`, `.svg`, `.woff`, `.ttf` и др.) обслуживаются напрямую Apache.
- **Динамические запросы** перенаправляются на `index.php`.

Пример:
```
/shop/item/product-123 → index.php?controller=shop&action=item&slug=product-123
```

Исключения: запросы к `/cache/`, `/upload/`, `/css/`, `/js/`, `/images/`, `/templates/` не попадают в маршрутизатор.

### Диспетчеризация

После загрузки `index.php`:

1. Парсится URL → извлекаются `controller` и `action`.
2. Создаётся экземпляр контроллера (например, `shop`).
3. Вызывается метод действия (например, `item_view_action()`).
4. Контроллер передаёт данные в шаблон.
5. Результат выводится (HTML, JSON или редирект).

#### Пример разрешения

| URL                     | Контроллер                                 | Метод                     | Шаблон                                              |
|------------------------|--------------------------------------------|---------------------------|-----------------------------------------------------|
| `/shop/item/123`       | `/system/controllers/shop/controller.php`  | `shop::item_view_action()`| `/templates/default/controllers/shop/item_view.tpl.php` |

> Подробнее см. раздел «Маршрутизация URL и настройка веб-сервера».

## 1.15. Взаимодействие компонентов через события

Платформа использует систему событий (`cmsEventsManager`) для слабосвязанной интеграции компонентов.

Шаблон обработчика событий

<img src="https://dstglobal.ru/img/git/8.png" alt="DST Platform">

Диаграмма: Взаимодействие компонентов, управляемое событиями

### Пример использования

**Генерация события** (в компоненте `shop`):

```php
$item = cmsEventsManager::hook('shop_before_add_item', $item);
```

**Обработчик события** (в `search/hooks.php`):

```php
class search {
    public function hookShopBeforeAddItem($item) {
        $this->model->indexProduct($item);
        return $item; // обязательно возвращать данные
    }
}
```

### Соглашение об именовании событий

| Шаблон события               | Время срабатывания | Типичное использование                     |
|------------------------------|--------------------|--------------------------------------------|
| `{component}_before_{action}`| До выполнения      | Валидация, модификация данных, логирование |
| `{component}_after_{action}` | После выполнения   | Индексация, уведомления, инвалидация кэша  |
| `{component}_on_{event}`     | Синхронно          | Реакция на внутренние события системы      |

> Обработчики регистрируются автоматически через файлы `hooks.php` в компонентах.

## 1.16. Заключение

DST Platform представляет собой зрелую гибридную систему **CMS/CMF**, сочетающую:

- **Двойную архитектуру**: единое ядро для социальной платформы и бизнес-экосистемы.
- **Чёткую MVC-структуру**: компоненты с контроллерами, моделями и шаблонами.
- **Гибкие парадигмы разработки**: декларативный (без кода) и императивный (на основе кода) подходы.
- **Событийную интеграцию**: слабосвязанное взаимодействие через систему хуков.
- **Масштабируемую инфраструктуру**: синглтон-сервисы, многоуровневый кэш, фоновые задачи.

Архитектура обеспечивает баланс между **скоростью запуска типовых проектов** и **гибкостью для сложных enterprise-решений**.
